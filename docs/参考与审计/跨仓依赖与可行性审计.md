## 1. 当前架构决策

以下决策作为本仓当前基线，优先于本审计中任何早期建议：

- 每个 Skill 必须有 SKILL.md；Assurance 可选，位于 assurance/。
- 无 Assurance Artifact 仅 LLM-guided；有效发布 Assurance Artifact 支持 Deterministic 和 LLM-guided；无效 Artifact 导入失败。
- when 是 assurance/contract.yaml 的可选纯 CEL 选择表达式；predicates.yaml 仍是执行期业务判断。
- 作者源由外部 Compiler 构建并发布；Next 只消费发布 Artifact，不调用 Compiler Check/Build/Inspect/Verify，不建立 Skill Admission。
- LLM Action 经过统一 Runtime Action Boundary，不编译为临时 Procedure。
- 全系统只有一个 Plugin Manager；Tool 是 Plugin 的 Operation；ca-client-tools 作为 tools Extension 接入。
- 不建立 Domain Contract Package、TaskContract Package、第二 Skill Descriptor、Tool Registry 或 Provider Manager。
- SBI Event Plugin 负责 JSON/multipart 和 Content-ID；Host 托管原始二进制；Codec 由 Skill 按需调用。
- SkillCatalog 属于 Python Agent Core/Host，是进程内不可变快照；缓存 SKILL.md、候选元数据、发布 Artifact 引用和已反序列化 when 程序。
- when 在发布前编译和类型检查；Agent 导入时反序列化一次，每个新 Event 使用当前输入求值；不缓存 Event 结果。
- 显式 Skill import/update 构建新 Catalog generation 并原子激活；Invocation 固定 generation；不要求文件监视器或分布式缓存。

## 3. 成熟外部项目的复用决策

### 3.1 ca-skill-compiler：外部工具链，不复制

证据：

- v2.1.0 是独立 Go Compiler。
- 支持 CA-SL v1alpha5 的冻结 Build/Verify 和 Development Build/Verify v1alpha1。
- Compiler 负责源码静态检查、Interface Linking、Schema 闭包和 Artifact 发布。
- 当前 v2.1.0 尚未证明支持 PR #88 提议的 Contract.when 及 Python 可消费的 CheckedExpr Artifact。
- ca-skill-compiler Issue #61 跟踪 Development Artifact Manifest v1alpha2、CheckedExpr Any 和 FileDescriptorSet。

决策：

- 不复制 Go Compiler 源码，不在 Python 重写 Parser、Type Checker、Linker 或 CEL Interpreter。
- Compiler/发布流程在 Agent 外部执行。
- Next 只消费正式发布 Artifact，做基本结构、必需文件、类型数据和本地依赖检查。
- Next 不调用 Compiler 命令，不做 Skill Admission。
- 运行时加载已发布 CheckedExpr 和类型环境，保存于 SkillCatalog；每个新 Event 独立求值。
- Issue #61 中如仍保留 Next Inspect/Verify/Admission 设想，需要由 Compiler/Next 文档共同对齐；本仓本轮不修改 Compiler Issue。

### 3.2 ca-client-tools：Tool Plugin 外部依赖

证据：

- v1.2.0 是独立 Go Tool/Provider 发布物。
- Provider v2 使用长生命周期 stdio/NDJSON 进程协议。
- Go-owned Tool Interface Package 是 Callable/Schema/Effect/Capability 的权威源。
- Owner backend、私有参数投影和 Owner Receipt 交互由 Go Provider 负责。
- protocol/nas5gsm 是有限范围纯 Go Codec 库，不自动等于 Agent 可调用 Codec Tool。

决策：

- 将 ca-client-tools 作为导出 tools Extension 的 Plugin。
- 初期可在唯一 Plugin Manager 内适配 provider/v2。
- 不把 Go 实现翻译到 Python，不复制 ToolCatalog 或私有 Owner binding。
- Codec Operation 必须先进入权威 Interface Package 并通过精确消息子集验收，Skill 才能调用。
- 不创建独立 Codec Plugin/Manager。

### 3.3 ca-skills：Skill 作者源与 CA-SL 规范

证据：

- main b06f72ba 包含 Establish、Modify、Release MAS Skill 源。
- CA-SL 作者格式为 v1alpha5。
- PR #88 OPEN，提出同标识 v1alpha5 的可选 Assurance 和 Contract.when 刷新。

决策：

- Skill 作者源由 ca-skills 维护。
- Next 消费发布后的 SKILL.md + Runtime Artifact。
- 不复制 Create/Modify/Release 业务逻辑到 Agent Core。
- PR #88 未合并前，不宣称新 when 规范已正式发布；发布 Artifact 互操作必须以正式 Compiler 契约为准。

### 3.4 ca-openamsm-plugin：Event ingress/Delivery Plugin

证据：

- 主线 eb83c8f2 当时只有 README。
- PR #1 OPEN/DRAFT，为设计提案。
- 目标是对齐 Next Plugin Package/IPC v1alpha1 和 Host Artifact Handoff。

决策：

- 独立 Go Plugin 负责 SBI ingress、JSON/multipart、Content-ID、原始 N1/N2 暂存和响应 Delivery。
- 不实现 Owner Tool、Skill Resolver、RunStore、Runtime 或授权。
- 不选择 Skill。
- 不复制 Codec；按需调用 ca-client-tools 的 Codec Tool。
- 共享 UpdateSMContext 只提取必要 NAS discriminator，避免完整协议深度解码和业务决策进入 Event Plugin。

## 5. 可行性与关键风险

**总体判断：可行，但必须按 Echo → OpenAMSM 分阶段实施。**

主要风险不是 Python/Go 进程互操作，而是架构边界回退：

1. 重新引入 Provider Manager 或 Tool Registry。
2. Agent 运行时再次调用 Compiler，或引入 Skill Admission。
3. 把 Event→Root/Skill 路由表搬入 Core。
4. 将 OpenAMSM Owner、NsmfRunExecutor、Receipt/Reconcile 业务逻辑放进 Event Plugin。
5. 在 Agent Core 复制 3GPP Schema 或 Codec。
6. 将 Synthetic Owner G5 误报为真实隔离 Owner E2E。
7. 将有限 NAS/N2 codec coverage 误报为完整 NGAP 支持。

控制措施：先通过 Echo；每个机制有 Example/Acceptance；发布 Artifact 和 Tool Interface Package 以外部权威契约为准；真实 OpenAMSM E2E 独立验收。

## 7. 证据等级与使用限制

- EVIDENCE：直接核对的源码、发布物、PR/Issue 状态或测试结果。
- INFERENCE：基于证据作出的架构判断。
- PROPOSAL：建议的 Next 实施方向。
- NOT_RUN：没有执行证据。
- NOT_VERIFIED：尚未证明契约/链路成立。
- BLOCKED：存在明确外部依赖或环境阻塞。

本审计不是生产资格认证，也不是对所有仓库测试的重新执行。实施时必须刷新所有外部状态并记录准确 SHA。
