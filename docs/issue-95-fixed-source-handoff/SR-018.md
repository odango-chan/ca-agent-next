## 3. 差异、缺失与排除

### 3.1 AC-018-01：声明与实现定位不一致

1. `operations.yaml` 将 `SSM.PARSE_N1_MODIFY` 的 `source` 声明为 `src/smf/mas/ssm/ssm_ue.c`；但固定 `0007-ssm-n1-modify-parse.patch` 第 1～2 行明确修改 `src/smf/mas/ssm/ssm_ran.c`，并在该文件新增 `ssm_parse_n1_modify`。声明路径本身存在并不等于声明准确。
2. 同一 operation 声明步骤为 `c-parse` / `c-apply`；固定 `0008-nw-agent-scheme-c-modify.patch` 的 `run_c_modify` 实际使用 `m-parse` / `m-qos`。这会影响 Receipt/ trace 的步骤身份对照，不能静默视为同值。
3. 因此 23+2 清点可通过，但 AC-018-01 所要求的“真实源路径准确、可复核”不能整体通过。

来源：[operations Modify 声明](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/operations.yaml#L279-L330)、[0007 实际补丁](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/patches/openamsm/0007-ssm-n1-modify-parse.patch)、[0008 实际编排](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/patches/openamsm/0008-nw-agent-scheme-c-modify.patch)。

### 3.2 AC-018-02：Receipt/Proof/Reconcile/QoS 静态缺陷

**采用的有效证据**：0023 确有 PREPARED 在首次 dispatch 前的临时文件/fsync/原子 rename/目录 fsync、精确 key 的重复拒绝、终态写回和 UNKNOWN 保持；0021 的 `require_binding` 确有 SUPI/PSI/generation/epoch/step/correlation/SEID/UPF 比对；0006/0007/0008/0010 确有 0xC9、typed QoS delta、PFCP 52/53 与 N1/N2 失败闭合设计。

**但以下缺陷阻止 AC-018-02 通过：**

1. **两个 Evidence Guarantee 引用不存在的参数。** `MAS.RECEIPT_QUERY` 输入仅为 `originalInvocationId/deploymentId/ownerInstanceId`，`MAS.RECONCILE` 输入仅为上述三项加 `operator/reason`；二者在 `evidence-guarantees.yaml` 却都有 `scope.subject.equals=arguments.ue_identity`。`publish.py` 对所有 operation 无条件生成该 subject 映射。静态脚本实得 `evidenceArgumentReferenceErrors=2`。
2. **resolved Reconcile decision 不符合自有 Schema。** `reconcile-decision.schema.json` 将 `resolved`、`reDispatched` 都列为 required；0023 在终态 Receipt 直接返回及 PFCP 解出终态的两个 `resolved=true` 分支只返回 `resolved + receipt`，没有 `reDispatched:false`。只有未解决分支补了该字段。
3. **MAS.RECONCILE 包装层没有完整执行 exact-original 再绑定。** `find_exact_session` 只按 SUPI/PSI 找当前 Session；随后按当前 bundle 的 `pfcp_del_state/recon_state` 写 COMMITTED 或 NOT_COMMITTED，既没有核对原 Receipt 可见的 `releaseGeneration/frameEpoch/correlationId/n4Seid/releaseTxn`，也没有核对 0021 原事务绑定的 UPF 身份。0021 的底层严格校验不能自动弥补 0023 这一调用路径；旧原调用可能借同 SUPI/PSI 的新 Session 状态解除 UNKNOWN，违反 SR018-D/E 与 F04/F06。
4. 上述均为静态代码/Schema 证据，**不是本轮动态复现**；但也绝不能以历史“真实 ac PASS”抵销这些固定源码差异。

来源：[Evidence Guarantees 的两条证据 READ](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/v1alpha4/evidence-guarantees.yaml#L757-L816)、[publish.py 的统一 scope 生成](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/publish.py#L363-L395)、[Reconcile decision Schema](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/v1alpha4/reconcile-decision.schema.json)、[0023 reconcile 实现](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/patches/openamsm/0023-mas-durable-receipt.patch#L1113-L1252)、[0021 严格绑定实现](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/patches/openamsm/0021-pfcp-unknown-reconcile.patch#L332-L421)。
