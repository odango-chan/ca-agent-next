# 技能目录与编译器运行时接口设计说明书

**文档状态：** Next 架构集成要求；Compiler 实施任务已登记，尚未实现  
**适用范围：** CA-SL v1alpha5、Python Agent Core / Skill Importer / Skill Resolver、ca-skill-compiler Development Build、Python CEL Runtime  
**关联任务：** [ca-skill-compiler Issue #61](https://github.com/odango-chan/ca-skill-compiler/issues/61)  
**规范依赖：** [ca-skills PR #88](https://github.com/odango-chan/ca-skills/pull/88)，当前仍为 OPEN

## 1. 设计结论

SkillCatalog 是 Python Agent Core / Host 自己拥有的进程内只读快照。Plugin Manager 只管理 Plugin 生命周期、IPC 和扩展分发，不拥有 Skill，也不负责 Skill 选择。

所有 Skill（包括没有 Assurance 的 SKILL.md-only Skill）在启动、导入或显式更新时进入同一个 Catalog。导入时读取 SKILL.md 和 Assurance；Compiler 对 Assurance 的 \`contract.when\` 完成一次解析与静态检查，输出可供 Python Runtime 消费的已检查 CEL 程序。每个新 Event 只对内存中的程序求值，不读取包文件、不调用 Compiler、不缓存前一个 Event 的布尔结果。

**Compiler 契约版本决策：** 保留 CA-SL \`connectionagent.io/v1alpha5\` 语言标识及所有已冻结契约。建议只新增 Development Artifact Manifest v1alpha2；不原地修改冻结的 Development v1alpha1，也不修改 v1alpha5 Build/Verify Artifact。

## 2. 对现有 Compiler v2.1.0 的源码审计

以下结论来自当前 \`ca-skill-compiler/main\` 和 v2.1.0 正式发布记录：

1. 冻结 v1alpha5 Build/Verify API 与 Artifact 字节保持 v2.0.2 基线；不能为 \`when\` 修改。
2. Development Build v1alpha1 的五份机器契约随 v2.1.0 发布并冻结；不能直接给 v1alpha1 Manifest 加字段。
3. \`internal/compiler/cel_check.go\` 使用 \`cel-go v0.33.2\` 做 Predicate CEL 的解析、类型检查及 G.4 AST 白名单检查。当前该文件不是 Contract.when 实现。
4. 现有 Predicate 的外部 Schema 参数路径使用 \`cel.DynType\`，不能直接证明 \`when\` 对 Request Schema 字段的静态类型。
5. \`ContractAST\` 当前没有 \`when\` 节点；继承语义管线目前调用 \`checkPredicateCEL\`，没有生成 Skill 选择程序。
6. \`schema_registry.go\` 已负责 Request Schema 的解析、闭包与包作用域；新增 \`when\` 必须复用该结果，不得另建 Schema Resolver。
7. \`development_build.go\` 已有统一 Build / Verify 重建路径；\`development_artifact.go\` 当前输出 Procedure、Ingress 投影及既有 Manifest/Requirement 文件，没有选择程序文件。

SKILL.md-only 导入是 Next Skill Importer 的责任，不是 Compiler 功能；该路径不得调用 Compiler。

## 3. 冻结契约与新增契约边界

| 契约 | 处理方式 |
|---|---|
| CA-SL languageTarget | 保持 \`connectionagent.io/v1alpha5\` |
| 冻结 v1alpha5 BuildRequest / BuildResult / Artifact | 完全不变，保持 v2.0.2 Artifact 字节 |
| Development BuildRequest | 保持 \`compiler-development-build-request/v1alpha1\` |
| Development BuildResult | 保持 \`compiler-development-build-result/v1alpha1\`；输出文件仍是不透明字节列表 |
| Interface Package / Dependency Lock | 保持 v1alpha1 |
| Development Artifact Manifest | 新增 \`compiler-development-artifact/v1alpha2\` |
| Development Artifact v1alpha1 | 保留原 Schema、Golden 和 Verify 语义，不覆写 |

BuildRequest 的 JSON 形状无需变化；BuildResult 的输出文件封套也无需变化。变化只发生在新构建生成的 Manifest 与文件布局，因此先单独版本化 Artifact Manifest 是最小变更。若 Compiler 实施审查发现 BuildResult DTO 也必须变化，须说明具体字段变化及其必要性，不能为了版本整齐而复制升级其余契约。

## 4. Compiler 的 when 静态编译要求

CA-SL v1alpha5 Appendix M 规定：

- \`event.type\` 是规范化 Event 类型字符串。
- \`input\` 的静态类型来自该 Skill 的 \`Contract.requestSchema\`。
- \`when\` 读取任何 \`input\` 成员时必须声明 \`requestSchema\`，否则报 \`CEL_INVALID\`。
- 表达式必须符合 G.4 CEL 子集，且最终静态类型为 bool。
- 未知字段、错误类型、非 bool、缺少可选/可空字段守卫、禁止的 CEL 结构均阻止 Assurance 编译。
- \`when\` 是纯选择表达式，不访问 Runtime Context、Observation、Tool Result、Evidence、时钟、环境变量或可变 Host 状态。

Compiler 应复用现有 Go \`cel-go\` Parser/Type Checker 与 AST 白名单基础，并通过现有 Schema Registry 为 \`input\` 建立精确的 G.4 类型环境。不能把 \`input\` 设为 \`DynType\` 来绕过字段检查，也不能因为 CEL 引擎支持更多语法而扩大 CA-SL G.4。

## 5. Compiler → Python Runtime 的标准 CEL 交换格式

### 5.1 选定的技术路线

优先使用 CEL 标准的已检查 AST Protobuf：

- Go Compiler 使用 \`cel-go\` 的 \`AstToCheckedExpr\` 导出 \`google.api.expr.CheckedExpr\`。
- 将 CheckedExpr 封装为标准 \`google.protobuf.Any\` 并序列化。
- Python Runtime 使用 \`cel-expr-python\`（CEL-C++ 的 Python Wrapper）通过 \`Env.deserialize()\` 读取同一个 Any。其公开实现可识别 \`google.api.expr.CheckedExpr\`，并从 CheckedExpr 建立可重复执行的 CEL Program。
- Runtime 使用 Artifact 附带的标准 Protobuf \`FileDescriptorSet\` 建立 DescriptorPool 和与 CheckedExpr 一致的类型环境。
- 对同一个反序列化 Expression 重复传入不同 Event activation；不解析原始 CEL 字符串，不重新做静态类型检查。

这条路线复用标准 CEL AST 和现有 CEL 实现，不自创字节码、不自制解释器、不在每个 Event 上启动 Compiler。

参考：
- [cel-go AstToCheckedExpr](https://pkg.go.dev/cel.dev/cel-go/cel#AstToCheckedExpr)
- [cel-expr-python 的 CheckedExpr 序列化与反序列化实现](https://github.com/cel-expr/cel-python/blob/main/cel_expr_python/py_cel_expression.cc)
- [CEL 标准 AST Protobuf 互操作规范](https://github.com/cel-expr/cel-spec)

### 5.2 Artifact 文件建议

以下是 Compiler Issue #61 的实施提案，最终字段名以 Compiler 发布的机器契约为准：

| 文件 | 内容 |
|---|---|
| \`skills/<skill>/compiled/when.checked.pb\` | 标准 \`google.protobuf.Any\`，payload 为已检查的 \`google.api.expr.CheckedExpr\` |
| \`skills/<skill>/compiled/when.types.pb\` | 标准 \`google.protobuf.FileDescriptorSet\`，包含 Event 类型及该 Skill 的 Request Schema 类型闭包 |

新 Manifest v1alpha2 为每个声明 \`when\` 的 Skill 提供索引，至少绑定 Skill Identity、CheckedExpr 路径、DescriptorSet 路径、精确 Request Schema 身份（若使用 input）、源码路径和表达式位置。语言标识 \`connectionagent.io/v1alpha5\` 固定其 G.4 Profile，不额外创造一个可自由变化的 CEL 方言。

这两个文件纳入 Manifest 现有 \`files[]\` 文件清单和现有 Artifact 自校验。不得新增另一套 SHA-256、签名、Trust Registry 或包完整性机制。

### 5.3 类型环境与数据映射

- \`event\` 与 \`input\` 必须按 CheckedExpr 中的类型身份构造 CEL activation；\`event.type\` 精确为 string。
- \`input\` 类型来自已解析的 Request Schema，而不是动态字典或任意 JSON 对象。
- 复用 Schema Registry 的闭合 G.4 Schema 结果，确定性生成可由 Go 与 Python CEL 实现共同加载的 DescriptorSet。
- Runtime 在求值前仍须验证 Event Schema 和候选 Skill 的 requestSchema。
- Protobuf Descriptor 映射必须保留 G.4 中“字段缺失”与“字段为 null”的差异、可选字段 has 守卫、nullable 字段 null 守卫、int64/binary64 精度与不混合规则。
- 若 DescriptorSet 无法无损表达某种 G.4 语义，先做最小互操作 PoC 并停下来评审；不得退化为 \`DynType\`、自制 CEL Runtime 或静默改变规范。

Compiler 需要先完成 Go CheckedExpr → Any → Python \`cel-expr-python\` 的真实往返 PoC，再冻结 Manifest v1alpha2 的具体 JSON Schema。

## 6. SkillCatalog 生命周期

### 6.1 初始化 / 导入 / 更新

1. 读取配置的 Skill Package。
2. 读取并校验 SKILL.md；完整文本与轻量语义候选元数据进入 Catalog。
3. 没有 \`assurance/\`：登记 Agent-only Skill，不调用 Compiler。
4. 存在 \`assurance/\`：必须包含完整的 \`contract.yaml\`、\`procedure.yaml\`、\`predicates.yaml\`；调用 Compiler。无效 Assurance 是导入失败，不得降级。
5. 对源码编译产物执行 Inspect/Verify 和 Host Admission；已编译 Artifact 不重新 Build。
6. 构建候选不可变 Catalog Generation，成功后一次性原子切换。
7. 更新失败时旧 Generation 保持激活，不允许部分替换。

### 6.2 Event 热路径

1. 校验并去重 Event。
2. 精确 continuation 优先，续接原 Run，不重新选择 Skill。
3. 新 Invocation 固定当前 Catalog Generation。
4. 对该 Generation 中声明 \`when\` 的 Assurance Skill，使用已反序列化的 Expression 对当前 Event 的 \`event.type\` 和 \`input\` 求值。
5. 一个 true 候选直接选中；多个 true 候选只允许在该集合内由 LLM 消歧。
6. 没有 true 候选时，只对没有声明 \`when\` 的 Skill 做 SKILL.md 语义选择。
7. false 或运行期错误的 Skill 排除，不得重新进入无条件语义候选集。
8. 绑定 Skill、Artifact、Capability 和完整 SKILL.md 后再选择执行模式。

热路径不读 Skill 文件、不扫描目录、不调用 Compiler、不解析 CEL。不同 Event 必须独立求值，不能缓存上一个 Event 的 true/false/error 结果。

### 6.3 代际与懒加载

- Catalog 保留 Skill Identity、完整 SKILL.md、语义候选元数据、反序列化 Expression、DescriptorPool、Request Schema 类型信息、已准入 Artifact 引用。
- \`references/\` 和大型知识资产仅在选中 Skill 确实需要时加载。
- 每个 Invocation 固定选中时的 Generation；更新激活新 Generation 不改变运行中的 Invocation。
- 旧 Generation 在最后一个引用它的 Invocation 结束后回收。
- 只需要进程内单调递增 Generation 编号；不引入 Redis、分布式缓存、文件监听或通用 Plugin Hot Reload。

## 7. 求值结果与候选语义

| CEL 结果 | Resolver 行为 |
|---|---|
| true | 显式候选 |
| false | 排除该 Skill |
| 求值错误 / UNKNOWN | fail-closed，排除该 Skill 并记录诊断 |
| 多个 true | 仅在精确 true 集合内由 LLM 消歧 |
| 无 true 且存在未声明 when 的 Skill | 对未声明 when 的集合做 SKILL.md 语义选择 |
| 无任何候选 | 停止或请求必要输入，不创建未绑定的 Generic Agent 路径 |

Continuation 使用原 Run 的 Skill/Artifact/Capability 和 Catalog Generation，不重新求值。

## 8. 验收要求

Compiler 侧：
- CA-SL PR #88 合并并固定规范 SHA 后，新增 \`contract.when\` AST 与 G.4 Schema-aware 静态校验。
- SA-004/SA-005 与 G.4 可选、可空、数值、禁止语法 fixtures 通过。
- Development Artifact Manifest v1alpha2 输出 CheckedExpr Any 和 DescriptorSet；旧 v1alpha1 与冻结 v1alpha5 Artifact Golden 不变。
- Build/Verify 重建逐字节一致。
- Native / WASM / Chromium 输出一致。
- Go → Python CheckedExpr 真实互操作 fixtures 通过。

Next 侧：
- EX-21：Core-owned Catalog 包含 Agent-only 与 Assurance Skill。
- EX-22：Event 热路径无文件读取、目录扫描和 Compiler 调用。
- EX-23：编译一次、每个 Event 独立求值。
- EX-24：Replay / Continuation 不重新选择。
- EX-25：Catalog 原子更新和失败回滚。
- EX-26：Invocation Generation 固定。
- EX-27：语义元数据与完整 SKILL.md 均来自内存。
- EX-28：references 懒加载。

以上均是设计验收要求，不代表现有 Compiler 或 Next 已经实现。

## 9. 实施依赖和停止条件

当前状态：

- ca-skills PR #88：OPEN，尚未形成新的正式规范发布记录。
- ca-skill-compiler v2.1.0：已发布；不支持新 \`when\` Artifact 的证据尚未建立。
- [Compiler Issue #61](https://github.com/odango-chan/ca-skill-compiler/issues/61)：已建立，跟踪 Development Artifact v1alpha2 与跨语言 CEL CheckedExpr。
- ca-agent-next PR #1：本仓只负责消费 Compiler 发布的接口，不复制 Compiler 语义。

以下任一条件出现时，Harness 必须停止相关阶段并上报证据，不得绕过：
1. CA-SL PR #88 尚未合并且无法固定候选规范 SHA；
2. CheckedExpr Any 无法由目标 Python CEL Runtime 反序列化；
3. DescriptorSet 无法保留 G.4 类型、字段缺失与 null 语义；
4. Python 求值结果与 Go / CA-SL 规范 fixtures 不一致；
5. 新 Artifact 需要修改已冻结契约；
6. 任何实现试图新增第二套 CEL Parser/Interpreter、额外信任机制或 per-Event Compiler 调用。

完成后，Next 才能把 Assurance Source Import 和 \`when\` Resolver 标记为可实施/可验收。

## 10. 非目标

- 不引入 CA-SL v1alpha6 或旧版本兼容。
- 不修改冻结 v1alpha5 Build/Artifact 与 Development v1alpha1 契约。
- 不把 SkillCatalog 放进 Plugin Manager。
- 不增加 \`activation.yaml\`、\`constraint.yaml\`、第二份 Skill descriptor、Domain Contract Package 或 Event→Skill 表。
- 不把 \`when\` 放入 \`predicates.yaml\`。
- 不增加额外 SHA-256、签名、Trust Registry、分布式缓存、文件监听或自动下载。
- 不在 Compiler 中执行 CEL，不让 Python 自行实现 CA-SL 静态语义。
