## 1. 目标与设计原则

功能树是 CA Agent 系统的统一入口。它同时覆盖：

1. ca-agent-next 自有功能：由 Next 负责需求、架构、设计、实现和验收。
2. 外部能力域：由其他仓库设计和实现，Next 只定义消费边界、集成需求和依赖关系。
3. 外部参考与演进目标：用于代码复用、标准对照和后续晋级，不作为 Next 的运行时功能。
4. 工程治理支撑：文档、SR、评审上下文自动生成等非运行时能力。

必须遵守：

- **设计文档按功能维护，不按 SR 或 Issue 拆分。** 一个 Feature 有一份长期设计说明书；功能增强刷新原文档，只有独立功能才新增文档。
- SR 是可独立实施、验收和追踪的需求记录；SR 文档不是第二份设计说明书。
- 一个 SR 可关联一个或多个 Issue；一个 Issue 可覆盖多个相关 SR，但必须列出逐项覆盖关系。
- Issue、PR、Commit 和 Test 都要回链到 SR；Issue Closed、PR Merged 不自动代表 SR 已验收。
- 外部能力的内部设计不复制到 Next；只维护权威来源、版本/Commit、消费边界和集成 SR。
- 架构设计和设计说明书在 docs 下同级；总体架构只有一份。
- SR ID 不重排、不复用；废弃需求保留记录和原因。

## 8. Feature → SR → Issue → Code → Test 追踪规则

### 8.1 SR 与设计文档

- Feature 表示长期功能领域；SR 表示可独立实施和验收的需求。
- 一个 Feature 通常维护一份功能设计说明书；多个 SR 可以引用同一份设计说明书的不同章节。
- SR 文件只记录需求目标、范围、非目标、前置条件、验收条件和实施关联；详细机制仍由功能设计说明书定义。
- 新增独立功能时新增 Feature/设计文档；既有功能增强更新原文档并分析 SR 影响。
- 不因新增一个 Issue 就新增设计说明书。

### 8.2 Issue 与 PR

创建 Next Issue 时必须包含：

~~~text
Feature ID：
SR ID（一个或多个）：
需求 / 缺陷：
本 Issue 范围：
明确非目标：
设计说明书及章节：
外部能力依赖（EC ID / 外部 Issue 或 PR）：
实现任务：
验收条件（Acceptance ID / Test ID）：
测试计划：
交付物（PR / Commit）：
阻塞和 NOT_RUN 项：
~~~

一个 SR 可拆成多个 Issue；一个 Issue 可覆盖多个相关 SR，但必须逐项列出覆盖内容和验收证据。外部仓库 Issue/PR 只能登记为 EC 依赖，不能伪装成 Next 实现 Issue。

### 8.3 代码和验收

- PR 必须引用 Feature、SR、Issue 和验收项。
- Commit message 推荐包含 Feature/SR ID；无法写入 Commit 时在 PR 中补齐。
- 现有 EX/OM 编号保持不变；新增测试使用 TC-Fxx-nnn-yy。
- 每个验收结果记录 Commit SHA、命令、环境、实际结果和证据位置。
- Issue Closed / PR Merged 只能证明任务交付状态；所有必需验收通过后 SR 才能 VERIFIED。
- 未执行标记 NOT_RUN；环境阻断标记 BLOCKED；失败标记 FAIL；证据不足标记 UNVERIFIED。

## 9. 按功能识别与按需阅读

所有 Agent/Harness 先读本文，再按任务读取：

1. 从用户任务、Issue、PR 或变更文件识别 Feature。
2. 找到对应 SR 和状态；DRAFT 或 BLOCKED 不得直接实施。
3. 读取该 Feature 的功能设计说明书相关章节。
4. 读取该功能引用的规范。
5. 涉及 EC 时读取对应外部仓的权威文档和固定版本/Commit。
6. 读取对应 Acceptance 和测试。
7. 完成后回填 SR、Issue、PR、Commit、Test 和状态。

示例：Skill when 改动读取 F02 设计、Skill 格式规范和 EC01/EC02；Plugin IPC 改动读取 F03 设计和 Plugin IPC 规范；OpenAMSM multipart 改动读取 F05/F06、EC04 和 REF02。不要让每项任务加载所有功能文档。
