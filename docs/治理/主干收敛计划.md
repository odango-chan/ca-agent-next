## 1. 目标与边界

目标是把恢复设计基线和仍有价值的开放设计/治理/实施增量整合为一个可独立评审的 Draft PR，最终只通过该统一 PR 进入 `main`。本计划不以分支数量或提交数量作为收编依据，逐项按文件差异、依赖关系和语义有效性决定。

保持以下架构不变量：

- CA-SL 仅采用 1.6.0，不兼容或迁移旧版。
- `when` 唯一位于 `assurance/contract.yaml`。
- Skill-facing Capability 与公开 Callable 双向一对一。
- 原版 3GPP OpenAPI 3.0 YAML 不修改、不投影；SBI JSON 与 NAS/NGAP 二进制 Codec 边界明确。
- Request Schema、Owner Contract、Provider Runtime Binding 的权责分离。
- Demo 排除项不扩张；未运行的产品 AC 保持 NOT_RUN/BLOCKED。
- 进入临时集成分支不等于进入 main；设计评审或 CI 不等于产品验收。

## 5. 收编批次

1. **第一批：核心设计** — #48、#52、#101、#113；并逐文件吸收 F09/SR-015 等有效设计。重点统一 3GPP OAS3、SBI JSON、NAS/NGAP Codec、Request Schema/Owner Contract 和 Capability-first 作者规范。
2. **第二批：SR-028 工具链** — #99、#112、#97。uv 实施、共享 lock、CI、状态回填必须互相一致；产品验收未实际运行的 AC 不升级。
3. **第三批：跨仓 Owner** — #107、#114。固定源审计和 SR-018 handoff 统一；缺少 Owner 原始证据继续 BLOCKED。
4. **第四批：治理** — #109、#51。证据归档规则、主干同步、分支清理自动化与治理索引对齐。
5. **证据留存** — #18、evidence/*、review/*、verify/* 仅在证据引用完整且确认不再需要后再清理，不作为功能合并批次。

## 6. 合并后分支清理

仓库治理规范 §8 定义删除门槛。最终 main PR 正文通过显式清单标记待清理分支；自动化检查保护状态和 OPEN PR head/base 依赖。未列入清单的分支不自动删除。证据/评审/验证分支默认保留。最终 main merge SHA、删除前 SHA、分支名和清理结果写入 Issue #50。

## 7. 验收与停止条件

- 每批次固定来源 SHA，检查完整 diff、文件级语义、修订记录、内部锚点、SR/IR/功能树/索引状态。
- 更新后重新读取 GitHub 远端 SHA，验证分支实际内容。
- 对集成分支当前 Head 运行必需 CI；Review Context SUCCESS 只表示上下文检查通过。
- 对每项产品 AC 分别记录 PASS/FAIL/NOT_RUN/BLOCKED；不得从文档或 CI 推断产品通过。
- 遇到未知 Owner 契约、源仓事实缺失、无法确定是否替代的文件或用户未决语义冲突，保留 BLOCKED 并报告，不猜测。
- 不修改 main，不强推，不提前删除分支，不把历史 Review 外推到新 Head。
