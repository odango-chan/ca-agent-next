## 1. 目标

实现唯一 Plugin Manager，统一管理独立 Plugin 进程、Package、IPC 和 event.ingress / event.delivery / tools Extension。

## 2. 实施范围

- 加载 Plugin Package v1alpha1 YAML Manifest 并执行基础字段、Schema、路径和版本检查。
- 实现 Plugin 进程启动、握手、NDJSON IPC、消息关联、超时和关闭。
- 同一 Plugin 可导出多个 Extension 和多个 Tool Operation。
- 为同一 Manager 固定**与协议无关的** `ToolsExtensionDriver` 接口边界，并提供 `ProviderV2ToolsExtensionDriver` 适配扩展点（只固定协议标识 `ca-client-tools.provider/v2` 与 `tools` Extension）。Provider v2 的 wire DTO——catalog 的 supported/unsupported 分区与 backend descriptor、Effect、request/response media type、参数或 generic Schema、Source Pin、Artifact Slot、绝对 RFC3339 UTC deadline、`producerInvocationId`、typed MAS 可选 `hostInvocation`——**不在本 SR 冻结**，其定义与实施统一归 SR-010。

## 3. 非目标

- 不建立第二 Provider Manager、Tool Registry、Codec Manager 或第二套 IPC。
- 不在 Plugin Manager 中做 Skill 选择、Callable Scope 授权或 Owner outcome 推断。
- 不冻结、也不伪实现 Provider v2 的完整 wire contract。F03.05 v0.3.9 为“目标设计；SR-015 设计移交 IMPLEMENTED”，其 Provider v2 数据合同由 SR-010 在其设计门禁完成后定义；本 SR 不提供 Provider v2 的 initialize/catalog/invoke/cancel 真实帧实现。

## 4. 依赖与前置条件

**实施依赖：SR-002 VERIFIED（已满足；证据基线 `b3fafa1ab402018f8bff06046049c7958b91c68a`）。** 设计依赖为 F01 v0.3.6 已冻结的公开契约。SR-003 必须复用 F01 v0.3.6 的公开 `Event`、`Host.handle_event(Event) -> HostResult` 和 `ModelClient` 注入边界；不得另建 Host、AgentLoop 或 ModelClient，也不得让 Plugin Manager 直接创建模型 Provider。

## 5. 验收条件

1. 一个 Plugin 进程完成启动、握手、请求/响应关联和关闭。
2. 同一 Plugin 进程可暴露 Event、Delivery、Tools；只有一个 Manager 负责发现与分发。
3. 错误版本、畸形 Manifest、重复/未知字段、路径逃逸和关联错误均有拒绝测试。
4. 验证 Host 对规范化 Event 类型和 payload 的检查，以及 Event 与 Skill ID、业务 Contract Package 解耦（EX-04）。
5. Tool 调用前的 Callable Scope 检查由 Runtime 执行，而非 Manager。
6. Event ingress 将 IPC `ingress.event` 映射为 F01 `Event`，再调用既有 `Host.handle_event`；不得绕过 Host 直接调用 ModelClient 或 Runtime。
7. 应用组合入口负责创建并注入唯一 ModelClient；Plugin Manager 不持有 Provider 凭据、不创建第二个模型客户端。

IPC → F01 Event 字段映射固定如下；仅外层 IPC 字段转为 Python snake_case，`source` 内部的协议字段保持原样：

| Plugin IPC `ingress.event.payload` | F01 `Event` 字段 | 转换规则 |
|---|---|---|
| `eventId` | `event_id` | 原值映射；必须为非空字符串 |
| `ingressId` | `ingress_id` | 原值映射；必须为非空字符串 |
| `eventType` | `event_type` | 原值映射；必须为非空字符串 |
| `externalRequestId` | `external_request_id` | 缺省映射为 `None`；存在时必须为非空字符串 |
| `responseChannelId` | `response_channel_id` | 缺省映射为 `None`；存在时必须为非空字符串 |
| `source` | `source` | 作为 JSON object 原样传递；其中 `protocol`、`peerId` 等 key 不改名 |
| `payload` | `payload` | 作为规范化 JSON object 原样传递，并按 F01 JSONValue 校验 |

Plugin IPC v1alpha1 的 `ingress.event.source` 必须存在且为 JSON object，其中 `protocol`、`peerId` 必须是非空字符串；缺失或格式错误必须在 IPC 边界拒绝，再构造 F01 Event。F01 通用 Event 的 source 可选/默认空 Mapping 只适用于非 Plugin IPC 的调用方，不得用于绕过 IPC schema 校验。

IPC `artifacts` 描述符不得直接复制到 `Event.artifact_refs`；`stagingPath`、本地路径和原始 bytes 也不得进入该字段。只有 F05 Host ArtifactStore 创建 Host-owned opaque reference 后，后续对应 SR 才能填入 `artifact_refs`。本 SR 的 Echo IPC fixture 使用 `artifacts: []`；二进制 staging / Handoff 不属于 SR-003 的本切片验收。

### AC-003-04 与 Driver 缝的验收边界（P1-A）

AC-003-04 验收的是 **Native Plugin 经唯一 Manager 完成的 tools/delivery/cancel 行为**（双 Callable、pending cancel、too_late/unsupported 后原操作终态、迟到结果隔离），它不验收 Provider v2 协议。Provider v2 在本 SR 中只固定一条边界：它也是 `ToolsExtensionDriver`，因此由同一个 Manager 管理。

因此本 SR 的 Driver 验收范围是：

1. `ProviderV2ToolsExtensionDriver` 继承唯一 `ToolsExtensionDriver`，只固定 `protocol = ca-client-tools.provider/v2` 与 `extensions = {"tools"}`，**不**声明 Provider v2 专用抽象方法，也**不**导出 Provider v2 私有 DTO。
2. Manager 仅依赖通用 Driver 能力（`start`、`invoke_tool_async`、`dispatch_delivery`、`cancel_operation`、`close` 与状态属性）即可完成全部调用；缺少 SR-010 的字段不影响本 SR 的稳定接口。
3. Manager 代码与导出中不出现 Provider v2 私有 DTO，不存在第二个 Manager、Tool Registry 或授权路径。
4. Native Plugin 的既有 `PluginProcess`/IPC 行为不因该缝改变。

Provider v2 的完整数据合同（catalog descriptor、Effect、media type、Schema、Source Pin、Artifact Slot、绝对 deadline、`producerInvocationId`、typed MAS `hostInvocation`）、initialize/catalog/invoke/cancel 真实帧、进程与跨仓适配，由 **SR-010** 在 F03.05 设计门禁完成后定义并实施；本 SR 不提前冻结、不验收。

### Shutdown `inFlightCount` 的语义边界（P2-04）

[插件包与进程通信协议规范](../规范/插件包与进程通信协议规范.md) v0.2.5 §5.1 只规定 `plugin.stopped.payload.inFlightCount` 为**非负整数**，未规定它等于 Host 侧待决数。本 SR 据此固定以下解释，且**不修改、不扩展 IPC 协议**：

1. `inFlightCount` 是 **Plugin 进程在停止瞬间自报的进程内在途操作数**，属于 Plugin 侧诊断值。
2. Host 侧待决计数的权威来源是 Manager 进程内的 `PendingRegistry`；不得用 `inFlightCount` 判定 Host 状态或提升任何操作终态。
3. 两者不一致时，Manager 记录诊断 `SHUTDOWN_INFLIGHT_DIVERGENCE plugin=<n> host=<m>`；这不是协议违规，不改变任何操作的终态判定。
4. 无论自报值为何，`plugin.stopped` 到达时 Host 侧仍未获终态的 Tool/Delivery 一律收敛为 `UNKNOWN`；优雅关闭中途退出时同样保持 `UNKNOWN`，不用 `ABORTED` 冒充“确定未完成”。

### 实施位置与复验入口

以下路径为本 SR 的目标交付物。在 ca-agent-next 仓根运行，测试通过公开入口调用受测组件。目标位置为 `src/ca_agent_next/plugins/`、`examples/echo/plugin/`。经真实子进程 stdin/stdout 依次握手、收 Event、发 tools 请求、关联响应并关闭。读取 IPC §5.1 的逐帧记录，分别从 Host 与 Go Plugin 两端回放，检查乱序、断线、超时和取消后迟到结果；保留原始 12 帧 golden，并额外执行 `echo.read`/`echo.describe` 双 Callable 与 `echo.wait` active-cancel fixture。断言三类 Extension 及两个 Callable 来自同一 PID，版本、路径或 correlation 错误时进程被拒绝，后续 dispatch 数为 0。此处 Provider v2 只确认唯一 Manager 内的**通用 Driver 缝**，Provider v2 的 wire contract 由 SR-010 定义。Driver 边界测试必须验证：`ProviderV2ToolsExtensionDriver` 继承唯一 `ToolsExtensionDriver`，且不额外声明 Provider v2 专用抽象方法或私有 DTO；Manager 拥有 `pluginId -> driver` 的进程内派发映射与关闭生命周期；Manager 只通过通用 Driver 完成 tool/delivery/cancel 调用，且 Manager 模块内不出现 Provider v2 私有 DTO；不存在第二个 Manager、Tool Registry 或授权路径；Native Plugin 的既有 PluginProcess/IPC 行为不因该接口改变。Provider v2 的 initialize/catalog/invoke/cancel 真实帧、Catalog Descriptor、Artifact Slot、跨仓适配不在本 SR 实施或验收。
