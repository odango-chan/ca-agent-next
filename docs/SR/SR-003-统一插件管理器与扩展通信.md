## 1. 目标

实现唯一 Plugin Manager，统一管理独立 Plugin 进程、Package、IPC 和 event.ingress / event.delivery / tools Extension。

## 2. 实施范围

- 加载 Plugin Package v1alpha1 YAML Manifest 并执行基础字段、Schema、路径和版本检查。
- 实现 Plugin 进程启动、握手、NDJSON IPC、消息关联、超时和关闭。
- 同一 Plugin 可导出多个 Extension 和多个 Tool Operation。
- 为现有 provider/v2 固定同一 Manager 内的 Driver 接口边界；实际 Provider 进程适配由 SR-010 接入。

## 3. 非目标

- 不建立第二 Provider Manager、Tool Registry、Codec Manager 或第二套 IPC。
- 不在 Plugin Manager 中做 Skill 选择、Callable Scope 授权或 Owner outcome 推断。

## 4. 依赖与前置条件

**实施依赖：SR-002 VERIFIED（已满足；证据基线 `b3fafa1ab402018f8bff06046049c7958b91c68a`）。** 设计依赖为 F01 v0.3.6 已冻结的公开契约。SR-003 必须复用 F01 v0.3.6 的公开 `Event`、`Host.handle_event(Event) -> HostResult` 和 `ModelClient` 注入边界；不得另建 Host、AgentLoop 或 ModelClient，也不得让 Plugin Manager 直接创建模型 Provider。

SR-003 的设计评审及 DRAFT→READY 转换只检查自身设计、范围、模块验收和稳定的 F01 接口，不等待 SR-002 代码实施或 AC 完成。SR-002 VERIFIED 实施门禁已满足。代码实施由 Issue #28 追踪，实施分支必须从包含本设计的恢复分支集成提交派生，并在 Issue #28 固定该提交 SHA；模块 AC 与系统 EX 分别取证。外部依赖必须有可核对的版本、接口和可用证据。

## 5. 验收条件

1. 一个 Plugin 进程完成启动、握手、请求/响应关联和关闭。
2. 同一 Plugin 进程可暴露 Event、Delivery、Tools；只有一个 Manager 负责发现与分发。
3. 错误版本、畸形 Manifest、重复/未知字段、路径逃逸和关联错误均有拒绝测试。
4. 验证 Host 对规范化 Event 类型和 payload 的检查，以及 Event 与 Skill ID、业务 Contract Package 解耦（EX-04）。
5. Tool 调用前的 Callable Scope 检查由 Runtime 执行，而非 Manager。
6. Event ingress 将 IPC `ingress.event` 映射为 F01 `Event`，再调用既有 `Host.handle_event`；不得绕过 Host 直接调用 ModelClient 或 Runtime。
7. 应用组合入口负责创建并注入唯一 ModelClient；Plugin Manager 不持有 Provider 凭据、不创建第二个模型客户端。

模块验收按下表独立取证。固定对端为 [Go Echo 示例源码](https://github.com/odango-chan/ca-agent-next/tree/c1268b4fea4fa181edfac3236cbb103161586013/examples/echo/plugin)，沿用其 Manifest、Schemas、main.go 和 go.mod。该提交只提供测试对端。目标分支缺少这些文件时，仅引入示例目录，不合入其测试 Host。Windows 使用 bin/echo-plugin.exe，其他平台使用 bin/echo-plugin。从示例目录运行 go build -trimpath -o 对应路径 .，由测试通过 Manifest 的 serve 参数启动。

|---|---|---|
| AC-003-01 | 先校验 Manifest、路径和 Schema，再握手。字段非法或 ready 与 Manifest 不一致时，已注册 Extension 数为 0，业务派发数为 0。 | EX-18 |
| AC-003-02 | 一个进程注册三类 Extension。按 IPC §5.1 关联请求；shutdown 后挂起数为 0。错关联、迟到或重复结果不能完成其他请求。 | EX-02、EX-03 |
| AC-003-03 | 先以 ingress 的声明和 Schema 检查 eventType、source、payload，再将合法 Event 交给同一 Host 一次。畸形 Event 的 Host 调用数为 0。ack 仅含协议允许的字段。 | EX-04 |

四个 AC 的命令与证据入口见本节末尾。IPC 规范中的 12 帧是固定协议 golden：Host 发送 m1/m4/m5/m7/m9/m11，Plugin 发送其余六帧；该 12 帧逐帧一致性不得因模块扩展而改写。它只证明协议基本轨迹，不单独证明多 Callable 或运行中取消。

除固定 12 帧 golden 外，AC-003-04 必须增加独立模块 fixture：同一 Plugin PID 至少注册并处理 `echo.read` 与 `echo.describe` 两个不同 Callable ID，分别发送 tools.invoke 并校验各自 invocationId、callableId、结果和终态；不得以同一 Callable 的两次重复调用替代。另提供受控挂起的 `echo.wait` 测试操作，在操作仍 pending 时发送 host.cancel，校验 plugin.cancelled 的 correlationId 指向取消帧、targetOperationId 指向原操作；随后注入该操作的迟到 tools.result，确认它不能完成其他请求或重复产生结果。原 12 帧中 m9/m10 的 too_late 轨迹继续单独验证“已完成后取消”语义。允许在 SR-003 实施分支扩展 Go Echo test peer，但必须保留 c1268b4 原始 12 帧 golden 不变，并将扩展 fixture 的源文件与命令纳入测试。

IPC → F01 Event 字段映射固定如下；仅外层 IPC 字段转为 Python snake_case，`source` 内部的协议字段保持原样：

| Plugin IPC `ingress.event.payload` | F01 `Event` 字段 | 转换规则 |
|---|---|---|
| `eventId` | `event_id` | 原值映射；必须为非空字符串 |
| `ingressId` | `ingress_id` | 原值映射；必须为非空字符串 |
| `eventType` | `event_type` | 原值映射；必须为非空字符串 |
| `externalRequestId` | `external_request_id` | 缺省映射为 `None`；存在时必须为非空字符串 |
| `responseChannelId` | `response_channel_id` | 缺省映射为 `None`；存在时必须为非空字符串 |
| `source` | `source` | 作为 JSON object 原样传递；其中 `protocol`、`peerId` 等 key 不改名 |
| `payload` | `payload` | 作为规范化 JSON object 原样传递，并按 F01 JSONValue 校验 |

Plugin IPC v1alpha1 的 `ingress.event.source` 必须存在且为 JSON object，其中 `protocol`、`peerId` 必须是非空字符串；缺失或格式错误必须在 IPC 边界拒绝，再构造 F01 Event。F01 通用 Event 的 source 可选/默认空 Mapping 只适用于非 Plugin IPC 的调用方，不得用于绕过 IPC schema 校验。

IPC `artifacts` 描述符不得直接复制到 `Event.artifact_refs`；`stagingPath`、本地路径和原始 bytes 也不得进入该字段。只有 F05 Host ArtifactStore 创建 Host-owned opaque reference 后，后续对应 SR 才能填入 `artifact_refs`。本 SR 的 Echo IPC fixture 使用 `artifacts: []`；二进制 staging / Handoff 不属于 SR-003 的本切片验收。

验收时必须引用演示验收基线中的对应 Acceptance ID，并记录真实执行命令、测试结果、Example 和覆盖范围。未执行项保持 NOT_RUN。

### 实施位置与复验入口

以下路径为本 SR 的目标交付物。在 ca-agent-next 仓根运行，测试通过公开入口调用受测组件。目标位置为 `src/ca_agent_next/plugins/`、`examples/echo/plugin/`。经真实子进程 stdin/stdout 依次握手、收 Event、发 tools 请求、关联响应并关闭。读取 IPC §5.1 的逐帧记录，分别从 Host 与 Go Plugin 两端回放，检查乱序、断线、超时和取消后迟到结果；保留原始 12 帧 golden，并额外执行 `echo.read`/`echo.describe` 双 Callable 与 `echo.wait` active-cancel fixture。断言三类 Extension 及两个 Callable 来自同一 PID，版本、路径或 correlation 错误时进程被拒绝，后续 dispatch 数为 0。此处 Provider v2 只确认唯一 Manager 内 Driver 接口，实际 Provider/Channel 互操作归 SR-010。

验收命令为 `python -m unittest discover -s tests -p test_plugin.py -v`。必须发现并执行本节正反例；发现 0 个测试或跳过必需用例时，退出码 0 也不能计入 PASS。逐个 Acceptance ID 回填受测 SHA、命令、预期与实测值及日志位置。
