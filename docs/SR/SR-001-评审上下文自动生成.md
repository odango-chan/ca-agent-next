## 1. 目标

建立由 CI 驱动的统一评审上下文生成机制。CI 从根目录 Agent.md 的唯一机器可读 review_scope 区块提取项目目标、必须范围、始终必须满足的正确性要求、明确非目标和评审策略，并与本次 PR 的变更信息、任务级 SR/Acceptance 组合，生成可供不同评审 Agent 使用的上下文和提示词。

## 2. 范围

### 2.1 必须交付

- Agent.md review_scope 区块解析与 Schema 校验。
- 生成标准化 JSON 范围文件。
- 生成项目评审上下文 Markdown。
- 生成可直接交给评审 Agent 的完整提示词 Markdown。
- 在 Pull Request Workflow 中执行解析、校验和生成。
- 将生成物作为 Workflow Artifact 保存，并在 Workflow Summary 展示摘要和获取入口。
- 检查本次新增或修改的正式架构、设计说明书、SR、验收及决策文档是否声明继承全局评审范围。
- 检测本次 PR 是否修改项目范围，并显式展示范围变更。
- 为解析器、生成器和文档头部检查提供自动化测试。

### 2.2 明确不在本 SR 范围内

- 不调用大模型，不自动产生 AI Review 结论。
- 不自动批准或合并 PR。
- 不自动修改 Agent.md 或其他源文档。
- 不向每份文档复制整段项目范围。
- 不建设通用评审平台、独立服务、数据库或分布式任务系统。
- 不引入包签名、额外 SHA-256、Trust Registry 或生产级权限治理。
- 不改变 Agent Runtime、Plugin、Skill 或业务执行机制。

## 3. 输入契约

只读取根目录 Agent.md 中由 REVIEW_SCOPE:BEGIN 与 REVIEW_SCOPE:END 标记包围的 YAML 区块。不得从自由文本猜测范围，不得在 CI 脚本、Workflow、PR 模板或测试 Fixture 中维护另一份可覆盖 Agent.md 的项目级范围。

必需字段：

~~~yaml
review_scope:
  schema_version: 1
  profile: demo_prototype
  target: {}
  in_scope: []
  always_required: []
  non_goals: []
  review_policy: {}
  finding_classes: []
~~~

字段含义和允许值以《文档编写与治理规范》为准。

## 4. 生成物

| 文件 | 内容 |
|---|---|
| review-scope.json | YAML 解析、Schema 校验后的标准化 JSON |
| 评审上下文.md | 项目目标、必须范围、正确性要求、非目标、分类规则、本次 PR 变更文件和来源版本 |
| 统一评审提示词.md | 公共评审提示词与项目范围、本次任务上下文的完整组合 |

生成物写入 Workflow 临时目录，不提交到源码仓库。作为 Workflow Artifact 上传，名称应稳定且可区分 PR/Workflow Run。Workflow Summary 展示 Agent.md Head SHA、schema_version、profile、范围变更状态、摘要、Artifact 入口和校验结果。

如果仓库已有 AI Review Job，后续 Job 下载 Artifact 并作为评审输入；如果由外部 Harness 发起，则由 Harness 下载 Artifact 后注入。生成 Artifact 不等于已自动注入所有外部 Agent。

## 5. 处理流程

1. Checkout 本次 PR 的实际 Head Commit。
2. 读取该 Commit 中的 Agent.md，不得误读 base/main 版本。
3. 检查 BEGIN/END 标记恰好各出现一次且顺序正确。
4. 提取 YAML 并解析。
5. 校验 Schema、必填字段、类型、枚举、ID 唯一性和 in_scope/non_goals 冲突。
6. 读取本次 PR 的变更文件清单及任务元数据。
7. 组合项目级范围与本次 SR/PR/Acceptance；任务级范围可以缩小项目级范围，不得扩大。
8. 生成 JSON、评审上下文和统一提示词。
9. 将摘要写入 Workflow Summary。
10. 上传生成物 Artifact。
11. AI Review Job 或外部 Harness 获取 Artifact 并注入评审上下文。

## 6. 失败关闭规则

以下情况必须使 CI 检查失败：Agent.md 缺失；标记缺失、重复或反序；YAML 语法错误；schema_version 不支持；必填字段缺失或类型错误；未知字段；分类值未知或重复；ID 重复；同一 ID 同时出现在 `in_scope` 与 `non_goals`；关键正确性要求或评审策略缺失；base/head/merge-base 无法读取；无法生成完整三份文件。不同 ID 的描述存在语义冲突时，不得尝试自动解释或自动扩大范围，必须显式标记 `SCOPE_DECISION_REQUIRED` 并等待用户确认。

失败时不得生成默认宽松范围，不得将空范围解释成“没有限制”。错误必须定位到 Agent.md 区块或具体文档路径。

## 7. 文档局部范围检查

新增或本次修改的正式架构、设计说明书、SR、验收及决策文档必须声明继承 Agent.md 的 review_scope，并说明本文局部非目标；没有时写“无”。不要求每份文档复制完整全局非目标。存量文档按收敛计划逐步迁移；检查器只对本次新增/修改的正式文档执行强制校验。

## 8. 范围变更检测

如果 PR 修改 review_scope，Workflow Summary 必须显式标记范围变化，生成上下文必须包含变更前后差异，并要求用户/项目负责人审查。YAML 合法不代表范围变更自动获批。是否通过 GitHub Review、标签或 Branch Protection 强制批准，由实施设计决定，本 SR 不假定这些配置已经存在。

## 9. 自动化验收

| ID | 验收要求 | 通过条件 |
|---|---|---|
| AC-REV-01 | 正常解析 | 唯一合法 YAML 区块被解析为标准化 JSON，字段值保持一致 |
| AC-REV-02 | 标记校验 | 缺失、重复、反序标记均使检查失败 |
| AC-REV-03 | YAML/Schema 校验 | 非法 YAML、未知版本、缺字段、错误类型、未知字段和未知枚举均明确失败；所有对象按规范设置 `additionalProperties: false` |
| AC-REV-04 | 冲突检测 | 三组列表 ID 跨组唯一；同一 ID 同时进入 in_scope/non_goals 失败；不同 ID 的语义冲突输出 SCOPE_DECISION_REQUIRED，不自动裁决 |
| AC-REV-05 | 上下文生成 | 包含目标、必须范围、正确性要求、非目标和分类规则 |
| AC-REV-06 | 提示词生成 | 包含统一评审原则和项目范围，不丢失 OUT_OF_SCOPE 等分类 |
| AC-REV-07 | PR 任务上下文 | 引用实际 PR Head SHA 和变更文件，不误读 base 分支 Agent.md |
| AC-REV-08 | 文档头部检查 | 本次适用的新增或修改正式文档缺少继承声明或局部非目标说明时，检查失败并报告文档路径 |
| AC-REV-09 | 范围变更提示 | review_scope 变化时，Summary 和生成上下文展示差异 |
| AC-REV-10 | Artifact 交付 | Workflow 成功后可获取三份生成物；没有 AI Review Job 时不宣称已自动调用外部 Agent |

所有验收必须真实执行。未执行标记 NOT_RUN；环境阻断标记 BLOCKED；不得仅凭代码审查标记 PASS。

### 实现位置与复验

目标仓 ca-agent-next。新增 `scripts/review_context.py`、`.github/workflows/review-context.yml` 与 `tests/test_review_context.py`。测试从本次 checkout 的 Agent.md 派生临时变体，覆盖 §6 全部拒绝条件；不得固化第二份项目范围。工作流在 pull_request 上取事件中的 base/head SHA，以 `git diff --name-status base...head` 的等价参数枚举变更，读取 head 文档；生成器接收两 SHA 与临时输出目录。执行 `python -m unittest discover -s tests -p test_review_context.py -v`，预期各正反例通过、错误用例进程返回非零且指出文件或字段。最后对真实测试 PR 的同一 head 检查 Summary、三份可下载产物和范围差异，记录 Run URL；本地测试只覆盖 AC-REV-01～09 的相应行为。

生成器从仓根调用 `python scripts/review_context.py --base <base-sha> --head <head-sha> --out <临时目录>`。PR 事件提供 base/head 两个 commit SHA。Workflow checkout 必须使用 `fetch-depth: 0`，或显式 fetch 这两个 SHA；生成器先用 `git cat-file -e <sha>^{commit}` 确认对象存在，再计算 `git merge-base <base-sha> <head-sha>`，任何对象缺失或无 merge-base 都失败关闭。取 head 版文档，按 `git diff --name-status --find-renames <merge-base> <head-sha>` 枚举路径。重命名检查新路径，删除只列入变更摘要。对比 base/head 中解析后的范围对象，格式或注释变化不产生范围变更。错误打印到 stderr 并退出非零，失败的 Job 不上传完成态产物。Workflow 从 GitHub 的 PR 事件 JSON（GITHUB_EVENT_PATH）读取 number、title、body，按原文提取已有 SR/Acceptance 标识供三份产物中的 Markdown 使用；没有声明时显式记录未提供。JSON 产物只保存已校验的项目范围对象。使用 review-context-pr-<number>-<run_id>-<run_attempt> 作为 Artifact 名称，Summary 提供对应 Run 和产物入口。真实 PR 的 Summary 和 Artifact 按 AC-REV-10 回填 Run URL。

只接受单独成行的 HTML 注释标记和其间唯一 YAML 围栏。使用 Python 安全 YAML loader，显式拒绝重复 mapping key。顶层只允许 `schema_version`、`profile`、`target`、`in_scope`、`always_required`、`non_goals`、`review_policy`、`finding_classes`；每层对象均拒绝未知字段。`schema_version` 必须满足 `type(value) is int` 且等于 1（不得把 YAML bool 当整数），`profile` 精确等于 `demo_prototype`。`target` 只允许 `description`、`sequence`；description 为非空文本，sequence 为非空且无重复项的文本列表。三组范围列表的每个条目只允许 `id`、`description`，二者均为非空文本，id 跨组唯一。`finding_classes` 必须是治理规范 §11.3 的六种分类且无重复。`review_policy` 只允许 `default_review_target`、`blocker_requires_traceable_requirement`、`blocker_requires_verifiable_evidence`、`missing_non_goal_capability_is_blocking`、`production_best_practice_alone_is_defect`、`scope_change_requires_user_approval`、`unresolved_scope_conflict`、`findings_must_include_requirement_location_evidence_and_current_goal_impact`；其中两个枚举字段分别精确等于 `changed_files_and_direct_dependencies`、`SCOPE_DECISION_REQUIRED`，其余六项必须为 bool。缺键、类型错误或额外字段须定位到对应键。校验器只保存结构及策略约束；范围文字和条目由 head 输入提供。测试通过临时 Git 提交构造新增、重命名、删除和错误输入；断言退出码、具体路径和三份生成物。AC-REV-07 的 SHA 取自 PR 事件，真实 Workflow 用该事件的 head 产物核对。
