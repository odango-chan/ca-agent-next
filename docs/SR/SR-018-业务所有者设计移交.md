## 3. 设计要求

- Owner 是 SM Context、Policy、UPF/PFCP、N1/N2 过程和最终业务状态的权威。
- operations.yaml 是 Owner 侧操作声明源；发布生成 ToolCatalog、IO Schema、Capability、Evidence Guarantee、Receipt/Proof/Reconcile Schema 和 Deployment Binding。
- MUTATION 需要稳定 originalInvocationId、durable Receipt 和 Commit Proof。
- COMMITTED 必须有有效证明；NOT_COMMITTED 必须证明未发生副作用；UNKNOWN 保持 UNKNOWN。
- Receipt 查询和 Reconcile 精确绑定 originalInvocationId、deploymentId、ownerInstanceId 和原业务主体。
- Reconcile 只判定原始事务，不重放 mutation，不换绑新 Session。
- Modify 由 0xC9 输入触发，UPN QoS Delta 走 PFCP 52/53。
- UE-requested Release 由 0xD1 触发，N1 0xD4 与 N2 PDU_RES_REL_RSP 必须绑定同一 generation / releaseTxn / Run。
- Owner 内部的真实状态更新由 Owner 执行，Agent/Plugin 不得模拟。

## 4. 当前实现状态

env-openamsm main 包含 MAS v1alpha4 发布声明、Receipt/Proof/Reconcile 相关代码和 Scheme C 修改/释放实现材料。当前 operations.yaml 的 25 条定义已通过源文件计数核实。Owner 源文档记录真实隔离 ac 环境的 Modify/Release 证据；这些证据不自动等于 Next Plugin/Runtime E2E。

## 5. 验收

- SR018-A：三份 Owner 原始设计迁入并固定源 SHA。
- SR018-B：25 条声明与 23+2 分类在文档中准确；Callable ID、Effect 和 source path 与 YAML 一致。
- SR018-C：Receipt 的 PREPARED/终态持久化、原始调用去重和 Commit Proof 规则有代码/测试定位。
- SR018-D：UNKNOWN 不得映射 COMMITTED；Provider 状态映射不允许危险提升。
- SR018-E：Reconcile 只读取 exact-original 事务身份，不发起 mutation。
- SR018-F：Modify 的 0xC9、QFI/QoS delta、PFCP 52/53 和 N1/N2 响应路径有证据。
- SR018-G：UE Release 的 0xD1、0xD3、0xD4、PDU_RES_REL_CMD / PDU_RES_REL_RSP、generation 和 releaseTxn 绑定有证据。
- SR018-H：Next Runtime 只消费 Owner 结果，不复制 Owner 业务状态。
- SR018-I：真实 Owner E2E、Next E2E 和 Production Qualification 分开报告；本 Demo 不声明 Production Qualification。
