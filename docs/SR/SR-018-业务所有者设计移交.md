## 3. 设计要求

- Owner 是 SM Context、Policy、UPF/PFCP、N1/N2 过程和最终业务状态的权威。
- operations.yaml 是 Owner 侧操作声明源；发布生成 ToolCatalog、IO Schema、Capability、Evidence Guarantee、Receipt/Proof/Reconcile Schema 和 Deployment Binding。
- MUTATION 需要稳定 originalInvocationId、durable Receipt 和 Commit Proof。
- COMMITTED 必须有有效证明；NOT_COMMITTED 必须证明未发生副作用；UNKNOWN 保持 UNKNOWN。
- Receipt Query / Reconcile 必须精确绑定 `originalInvocationId`、`deploymentId`、`ownerInstanceId`、SUPI/UE identity 与 PSI。
- 对 PFCP DELETE TERMINAL UNKNOWN，Receipt 还必须条件性绑定 `sessionRef`、`sessionGeneration`、`stepId`、`correlationId`、`frameEpoch`、`n4Seid`、`releaseGeneration`、`releaseTxn` 和 `upfId`；缺少任一条件必需字段时不得生成可被解释为有效终态的 Receipt。
- `scope.sessionGeneration` 与 `transaction.releaseGeneration` 是不同层次的身份字段；若 Owner 实现选择相同值，必须由 Owner 语义和测试证明其等价，不能只因字段值相等就推断等价。
- Reconcile 只判定原始事务，不重放 mutation，不换绑新 Session；所有决策分支都必须满足 Decision Schema 并显式证明 `reDispatched=false`。
- 当前 Reconcile 输入契约将 `operator` / `reason` 声明为必需字段，Owner 必须将其写入可复核的审计记录；若设计决定不保留这两个字段，必须同步修改操作声明、输入 Schema、Publisher 和测试，不得静默接收后丢弃。
- Modify 由 0xC9 输入触发，UPN QoS Delta 走 PFCP 52/53。
- UE-requested Release 由 0xD1 触发，N1 0xD4 与 N2 PDU_RES_REL_RSP 必须绑定同一 Owner generation / releaseTxn；Host Runtime 将 Owner 结果关联回原始 Host Run，Owner 不消费或保存 Host Run ID。
- Owner 内部的真实状态更新由 Owner 执行，Agent/Plugin 不得模拟。

- SR018-G：UE Release 的 0xD1、0xD3、0xD4、PDU_RES_REL_CMD / PDU_RES_REL_RSP、generation 和 releaseTxn 绑定有证据。
- SR018-H：Next Runtime 只消费 Owner 结果，不复制 Owner 业务状态。
- SR018-I：真实 Owner E2E、Next E2E 和 Production Qualification 分开报告；本 Demo 不声明 Production Qualification。
