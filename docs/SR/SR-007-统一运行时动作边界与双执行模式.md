## 1. 目标

让 Deterministic Procedure Engine 与 LLM Model Loop 共用同一 Runtime Action Boundary，统一执行范围、输入、Effect、Artifact 和 Owner outcome 解释；Host Resource Read 与 Host Script Execution 作为 Host-owned system Action 经同一边界执行。

## 2. 实施范围

- 统一 Runtime Action Request。
- 校验当前 Skill 声明的 Callable Scope、Callable ID、输入 Schema、Effect、Artifact 引用和 Run 状态。
- 区分 READ Observation 与 MUTATION Owner Evidence。
- 按 Owner Receipt/Commit Proof 解释结果，UNKNOWN 保持 UNKNOWN。
- 支持异步 Operation continuation、Reconcile 的正确 Run 关联；Skill 层不定义 Wait / await / polling 作者语法。

## 3. 非目标

- 不允许 LLM 直接调用 Plugin 或扩大 Callable Scope。
- 不把 HTTP 200、IPC 成功或 Delivery 成功解释为 Owner Commit。
- 不复制 Owner 状态映射或业务枚举。

### 5.2 AC-007-05 收据、Proof 与原请求的比对

固定 Owner 审计样本取自 [Receipt Schema](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/v1alpha4/receipt.schema.json)、[Proof Schema](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/v1alpha4/proof.schema.json) 和 [ToolCatalog](https://github.com/odango-chan/env-openamsm/blob/dc83ccbf5be54dcc7112dd43ba95ea6fa5975550/contracts/mas/v1alpha4/tool-catalog.yaml)。以下 JSON Pointer 以单份 Receipt 对象为根。ToolCatalog 的 `mutation.commitProof.path=receipt.commit` 对应 `/commit`。该表是 OpenAMSM 契约的验收样本，通用 Runtime 消费发布包提供的绑定。正式 1.6.0 包与真实收据缺失时，产品 AC 保留 BLOCKED / NOT_RUN。

| Receipt 路径 | 对照来源与断言 |
|---|---|
| `/schemaVersion`、`/receiptId` | 前者匹配 Schema 常量 `openamsm.mas-mutation-receipt/v1`；后者为 Owner 分配的非空收据 ID。以固定 Owner 的 durable record 核对收据身份；重放同一份终态收据应幂等。 |
| `/originalInvocationId`、`/commit/originalInvocationId` | 两者均须等于发起该 mutation 的原 Invocation ID。固定收据只替换 Proof 中的 ID，应判冲突。 |
| `/owner/id`、`/owner/instanceId`、`/owner/buildIdentity`、`/owner/deploymentId` | 分别核对固定 Owner 发布身份，以及本次调用绑定的实例、构建和部署身份；期望值从已记录的绑定取得。 |
| `/operation/callable`、`/operation/mas`、`/operation/op`、`/operation/stepId`、`/operation/effect` | 核对原调用的唯一 Callable、Owner MAS/op、原步骤与已绑定 Effect；此处的 mutation 用例要求 MUTATION。 |
| `/scope/supi`、`/scope/psi`、`/scope/sessionRef`、`/scope/sessionGeneration`、`/scope/smContextRef` | 核对原调用的 Owner 会话范围及其 generation。前四项必填；最后一项按原 Scope 与契约比较，可缺省或为 null。 |
| `/transaction/correlationId`、`/transaction/frameEpoch`、`/transaction/n4Seid`、`/transaction/policyAssocId`、`/transaction/releaseGeneration`、`/transaction/releaseTxn` | 与原事务的相应值逐项比对。correlationId 必填，frameEpoch 可缺省，出现时必须是字符串。其余四项按 Schema 可缺省或为 null；选用适用且有值的原事务构造单字段错配。 |
| `/resultDigest` | 与该原始调用的 Owner 持久结果所记录的摘要一致。固定预期来自同一事务的权威记录；不要使用待测收据里的值为自身作证。 |
| `/phase`、`/state`、`/commit/commitState`、`/failureClass` | 按下表判读相位、收据状态和 Proof 状态。拒绝类负例同时核对该 Callable 的 failureClasses 与 noSideEffect 绑定。 |
| `/commitBasis`、`/preparedAt`、`/terminalAt` | Owner 自身元数据，按 Schema 及具体 Owner 契约校验。它们不是 Invocation 比较键，也不单独证明提交。 |

| 场景 | 两种模式的预期结果 |
|---|---|
| 同一原调用、匹配全部绑定、TERMINAL + COMMITTED + Proof COMMITTED | 认可 Owner 已提交。 |
| 仅将上一行的 `/commit/commitState` 改成 NOT_COMMITTED，收据仍为 COMMITTED | 证据冲突，UNKNOWN/UNRESOLVED。 |
| 同一原调用、TERMINAL + NOT_COMMITTED + Proof NOT_COMMITTED，且 failureClass、Proof 和无副作用条件匹配该 Callable 已发布的拒绝分支 | 认可 Owner 的 NOT_COMMITTED；重放不再触发 mutation。 |
| PREPARED、Owner UNKNOWN、原 ID 不匹配、错版本、缺少必需证据、两份互相冲突的终态收据，或只有传输成功 | 保持 UNKNOWN/UNRESOLVED；不得推断提交或无副作用。 |
| 同一终态收据原样重复到达 | 保留已验证结果，仅计一次；不得新增 mutation。 |

每个身份、Scope、事务与结果绑定路径都从有效样本开始，一次只改一个值并保留其他值，分别核对两种模式的 Outcome 和重放调用计数。另测必填字段缺失、可选字段合法缺省、允许 null 的字段取 null、frameEpoch 取 null；按 Schema 和原调用实际约束分别判定。提交证明不足时不得据此重试原 mutation。
