# Host Artifact Store contract v1

**Document type:** design / cross-repository contract
**Status:** Accepted for implementation (draft PR)
**Contract identity:** `ca-host.artifact-store/v1`
**Consumer:** `odango-chan/ca-client-tools`, Provider `ca-client-tools.sbi`,
protocol `ca-client-tools.provider/v2`, P1 artifact streaming
**Owner:** `ca-agent` (Host integration, Artifact Store and stream adapter)

This document is the authoritative cross-repository contract required by
[ca-client-tools Host integration](https://github.com/odango-chan/ca-client-tools/blob/main/docs/host-integration.md)
and
[Provider payload contract](https://github.com/odango-chan/ca-client-tools/blob/main/docs/provider-payload-extension-v1.md).
It fixes the reference JSON shape, invocation binding, cross-process transfer
mechanism, adapter bootstrap, size/digest metadata, quotas, cancellation,
timeout, expiry, partial-write cleanup, result publication and stable error
mapping, and it ships the shared conformance fixtures.

The contract is provider-agnostic. It is accepted for the `ca-client-tools`
SBI Tool Provider because that Provider is the first artifact-bearing consumer.
Nothing here authorizes Runtime admission, Capability/Scope authorization,
operation onboarding or any production mutation; those remain with their
owners.

## 0. Status vocabulary

`DRAFT` (`Draft PR`), `ACCEPTED` (this document, frozen within v1),
`IMPLEMENTED` (code merged on a branch), `VERIFIED` (acceptance executed at a
recorded head). A status is only promoted with recorded evidence.

## 1. Scope and ownership

| Concern | Owner |
|---|---|
| Reference issuance, resolution, access control, storage, isolation, quota, lifecycle, publication | Host (`ca-agent`, `artifactstore`) |
| Process launch, trusted bootstrap, channel exposure, cancellation/timeout, result finalization | Host (`ca-agent`, `toolprovider` adapter) |
| Consuming references at declared slots, building wire bodies, decoding responses, requesting channel transfers | Provider (`ca-client-tools`) |
| Byte streams | Host channel only. Never NDJSON, never a filesystem path supplied as JSON, never base64, never an arbitrary URL |
| Invocation admission, Capability authorization, Owner Outcome/Evidence | Other owners (`ca-runtime`, deployment policy) |

The Host is the only artifact owner. The Provider keeps no persistent artifact
namespace and never derives a reference from a path, name, Content-ID or hash.

## 2. Reference JSON value

The only approved reference value is a JSON object with exactly one member:

```json
{"artifactRef": "art_<43 base64url characters>"}
```

Normative rules:

1. **Token grammar.** `^art_[A-Za-z0-9_-]{43}$`: the literal `art_` prefix plus
   32 random bytes encoded with unpadded base64url. Tokens are generated only
   by the Host from a CSPRNG.
2. **Closed shape.** Exactly one member, `artifactRef`. No `path`, `url`,
   `mediaType`, `size`, `sha256`, `contentId`, `name` or nesting. Additional
   members make the value invalid.
3. **Opaque.** The Provider treats the token as an uninterpreted string. It
   never parses it, guesses it, persists it, or reuses a token it observed.
4. **Location-bound.** A reference is valid only at one declared slot of one
   invocation in one direction. The Provider must reject a reference value at a
   non-slot location, and must reject a plain string/object at a declared slot
   that requires a reference.
5. **Direction-bound.** Input references (Host → Provider bytes) and output
   references (Provider → Host bytes) are distinct. The channel enforces this;
   a Provider upload token is not a resolvable input token.
6. **No caller-supplied Content-ID mapping.** Upstream `Content-ID` values are
   generated by the Provider for the outbound MIME body and never appear in a
   reference. The Host reference identity is independent of the upstream
   Content-ID. On the inbound side the Provider maps decoded parts to their
   declared slots and publishes Host references; it never echoes a remote
   Content-ID as a reference.

Reference values appear at these locations of one `invoke` request
(`params.arguments`) and result:

| Direction | Catalog declaration | Argument/result location |
|---|---|---|
| Input, binary request body | `generic.body.kind: binary` | `arguments.body` = reference object |
| Input, multipart part | `generic.body.parts[*].name` | `arguments.payloads[<part name>]` = reference object |
| Output, binary response body | non-JSON, non-multipart response media type | `response` = reference object |
| Output, multipart response part | `generic.responseParts[*].jsonPointerField` | the `RefToBinaryData` object at the declared descriptor `artifactSlots.outputs[*].pointer` inside `response` is replaced by the reference object |

JSON Pointer semantics (RFC 6901 escaping of `~`/`/`, nested objects, array
indexes) are preserved for multipart part pointers in both directions.

## 3. Declared slots published to the Host

The Provider catalog descriptor for an artifact-bearing `genericSBI` binding
adds a closed `artifactSlots` member. It is derived from the trusted embedded
Catalog and contains no origin, path, token or Content-ID:

```json
"artifactSlots": {
  "inputs": [
    {"slot": "body", "pointer": "/body", "mediaType": "application/octet-stream", "required": true}
  ],
  "outputs": [
    {"slot": "n2Message", "pointer": "/n2MessageContent", "mediaType": "application/vnd.3gpp.ngap", "required": true}
  ]
}
```

- `slot` is the catalog part name, or the literal `body` for a whole binary
  request/response body.
- `pointer` for an input is the argument location that holds the reference
  object: `/body` for a binary body, `/payloads/<escaped part name>` for a
  multipart part.
- `pointer` for an output is the location inside `response` that holds the
  decoded binary part's `RefToBinaryData` object (for example
  `/messages/0/n2MessageContent`). The Provider keeps the surrounding JSON
  structure (including nested objects and array indexes) and replaces exactly
  the value at that pointer with the reference object. The catalog-internal
  `responseParts[*].jsonPointerField` (the `.../contentId` string used to match
  the upstream MIME part) is a different, private location and is never the
  published slot pointer.
- The empty pointer (`""`) denotes the whole `response` value and is used only
  for a binary response body.
- `mediaType` is the declared part/body media type.
- `required` mirrors the catalog `required` flag.
- `artifactSlots` is present only when at least one direction declares a part.
  A binding with `artifactSlots` is artifact-bearing and is only available when
  the Host has configured an artifact channel for the process.

## 4. Channel: cross-process transfer mechanism

Byte transfer uses a Host-owned loopback HTTP/1.1 channel. It is not an NDJSON
frame and carries no JSON payloads other than the small control responses
below. The Provider process and the Host run on the same machine; the listener
binds `127.0.0.1` on an ephemeral port and is closed when the process is
disposed.

### 4.1 Bootstrap

The Host passes the channel in the `initialize` request:

```json
{
  "hostInstanceId": "host-1",
  "providerInstanceId": "provider-1",
  "limits": {"maxFrameBytes": 8388608, "maxInFlight": 8, "maxCallDurationMs": 5000},
  "artifactChannel": {
    "baseUrl": "http://127.0.0.1:53211",
    "processToken": "<opaque bearer token>",
    "requestTimeoutMs": 3000,
    "maxArtifactBytes": 1048576,
    "maxAggregateBytes": 4194304,
    "maxAttachments": 8
  }
}
```

Rules:

1. `baseUrl` is `http://127.0.0.1:<port>` only: no scheme other than `http`, no
   path, query, fragment or userinfo, host must be `127.0.0.1`, port 1-65535.
   The Provider appends exactly the documented path segments.
2. `processToken` is an opaque secret, 1-512 printable ASCII characters. It is
   never logged, never echoed in a result and never compared by the Provider.
3. `requestTimeoutMs` is the channel request timeout (positive integer, at most
   the invocation maximum). `maxArtifactBytes`, `maxAggregateBytes` and
   `maxAttachments` are positive integers; the Provider enforces them
   independently of the Host and fails closed on a Host that advertises
   smaller bounds than the Provider's own payload limits allow.
4. Absent `artifactChannel` means artifact streaming is not configured.
   Artifact-bearing bindings are then reported unavailable with
   `NOT_CONFIGURED` and any artifact-bearing invoke is rejected with
   `BACKEND_OPERATION_UNSUPPORTED`/`NOT_CONFIGURED` before any remote I/O.
5. A malformed `artifactChannel` is `PROVIDER_CONFIGURATION_INVALID` at
   `initialize`.

### 4.2 Resolve an input artifact

```http
GET {baseUrl}/v1/artifacts/{artifactRef}
Authorization: Bearer {processToken}
X-CA-Invocation: {invocationId}
X-CA-Slot: {slot}
```

Success is `200 OK` with `Content-Type` equal to the stored media type,
`Content-Length` equal to the stored size, `X-CA-Artifact-Sha256` equal to the
lowercase hex SHA-256 of the stored bytes, and the exact bytes as the response
body.

Failure responses use `application/json`:

```json
{"error":{"code":"ARTIFACT_EXPIRED","message":"artifact is not resolvable"}}
```

Messages are fixed safe strings; they never contain a token, path, byte, remote
body or subscriber value.

### 4.3 Stage an output artifact

```http
POST {baseUrl}/v1/artifacts
Authorization: Bearer {processToken}
X-CA-Invocation: {invocationId}
X-CA-Slot: {slot}
Content-Type: {declared part media type}
Content-Length: {exact byte count}
X-CA-Artifact-Sha256: {optional lowercase hex provider digest}
{bytes}
```

`201 Created` with:

```json
{"artifactRef":"art_<43 base64url characters>","size":1234,"sha256":"<64 lowercase hex>"}
```

The returned reference is **staged**, not published. It becomes caller-visible
only if the whole invocation result is accepted by the Host (see §6). A
`Content-Length` that is missing, negative, larger than `maxArtifactBytes` or
larger than the remaining aggregate quota is rejected before reading the body.
The Host computes the digest while receiving, verifies an optional
`X-CA-Artifact-Sha256`, and stores the bytes in Host-owned staging. A body that
is truncated, exceeds the advertised `Content-Length` or is otherwise
incomplete is discarded; the Provider reports `ARTIFACT_TRANSFER_FAILED`.

### 4.4 Channel error registry

| HTTP | `code` | Meaning |
|---|---|---|
| 400 | `ARTIFACT_TRANSFER_INCOMPLETE` | upload truncated, malformed headers or size mismatch |
| 401 | `CHANNEL_UNAUTHORIZED` | missing/invalid process token |
| 403 | `ARTIFACT_FORBIDDEN` | slot not declared, wrong direction, or invocation inactive |
| 404 | `ARTIFACT_NOT_FOUND` | unknown token |
| 409 | `ARTIFACT_INVOCATION_MISMATCH` | token bound to another invocation |
| 409 | `ARTIFACT_SLOT_DUPLICATED` | second upload for the same invocation slot |
| 410 | `ARTIFACT_EXPIRED` | staged/published artifact past expiry |
| 413 | `ARTIFACT_TOO_LARGE` | per-artifact limit exceeded |
| 429 | `ARTIFACT_QUOTA_EXCEEDED` | aggregate bytes or attachment count exceeded |
| 503 | `INVOCATION_CLOSED` | invocation finished, failed, timed out or was cancelled |

The Provider maps a channel `401`, `403`, `404`, `409`, `410` to
`ARTIFACT_REFERENCE_INVALID`; `400`, `413`, `429`, `503`, transport errors and
timeouts to `ARTIFACT_TRANSFER_FAILED`; and a caller cancellation/deadline to
`CALL_CANCELLED`/`CALL_DEADLINE_EXCEEDED`. These are Provider protocol faults;
the Host channel codes never cross to the Runtime caller.

## 5. Input validation before remote I/O

The Provider validates, before opening any remote connection:

1. every declared input slot has the required reference value;
2. every reference token matches the grammar;
3. no reference value appears at an undeclared location;
4. the channel is configured;
5. every input reference resolves through the channel with the declared media
   type and exact size, and the streamed bytes match the advertised digest and
   `Content-Length`.

Any failure aborts the invocation before remote I/O and publishes no output
reference. The Host resolves references only for the invocation that owns them
and only while that invocation is active and unexpired.

## 6. Result validation and publication

On a successful Provider result the Host walks the declared output slots:

1. every required output slot holds exactly a reference object that the Host
   staged for this invocation and slot;
2. no reference object appears outside a declared output slot;
3. no staged output for this invocation is unreferenced.

If all checks pass, the Host publishes exactly those artifacts (they become
caller-visible with the invocation's expiry) and returns the result unchanged.
If any check fails, no reference is published and the Host reports
`HOST_RESULT_INVALID`; every staged artifact for the invocation is discarded.

Publication is atomic per invocation: either all declared outputs are
published together with the accepted result, or none are. On invocation
failure, cancellation, timeout, provider exit or a malformed result, all staged
outputs are deleted and partial files removed. A Provider process restart never
resumes a previous invocation.

## 7. Access control and isolation

- The channel requires the per-process bearer token on every request and
  compares it in constant time.
- Every reference is bound at issuance to `(invocationId, direction, slot)`;
  the channel rejects any mismatch, including a reference minted for another
  invocation.
- Published artifacts are only resolvable through the owning invocation binding
  while that invocation is active; staging files live under
  `<root>/staging/<invocation>/` and published files under
  `<root>/artifacts/<shard>/`.
- File permissions are owner-only. The store root is Host deployment
  configuration, never caller input.
- References, paths, tokens, bytes, media types of sensitive payloads and
  remote bodies never appear in Host or Provider diagnostics. Allowed
  diagnostics: opaque `invocationId`, catalog slot name, size class, fault code.

## 8. Size, digest, quota and lifetime metadata

| Bound | Default | Owner |
|---|---|---|
| `maxArtifactBytes` per artifact | 1 MiB | Host (channel config), Provider enforced |
| `maxAggregateBytes` per invocation | 4 MiB | Host, Provider enforced |
| `maxAttachments` per invocation | 8 | Host, Provider enforced |
| `requestTimeoutMs` channel request | 3000 ms | Host, Provider enforced |
| Invocation deadline | provider protocol `invocation.deadline`, bounded by `maxCallDurationMs` | Host |
| Artifact expiry | 10 minutes after publication | Host |
| Staging expiry | invocation end or 10 minutes, whichever first | Host |

Digest is SHA-256 over the exact artifact bytes, lowercase hex without prefix.
The Host records the size and digest at staging time and verifies both when
serving an input and when finalizing an output. Fixtures in
`conformance/artifact-store/v1/` pin the byte vectors.

## 9. Cancellation, timeout, process exit and cleanup

1. The Host owns the effective invocation context: the caller cancellation or
   the invocation deadline cancels the provider call.
2. On cancellation the Host sends the protocol `cancel` frame for the target
   request, closes in-flight channel requests for the invocation (the Provider
   also cancels its own requests), rejects any further channel request for that
   invocation with `INVOCATION_CLOSED` and discards staged outputs.
3. After a bounded drain grace the Host terminates the Provider process. A
   late result is discarded by request correlation and never published.
4. Provider process exit during an invocation is `HOST_PROVIDER_EXIT`
   (incomplete work, no replay, no publication). The Host restarts the process
   on the next invocation with a fresh channel token.
5. On store open the Host removes stale staging directories (crash cleanup) and
   expired published artifacts.
6. A partially written staging file is never resolvable: its token does not
   exist until the upload completes and is published only via §6.

## 10. Process integration

The Host launches the fixed executable with argv `provider serve`, an explicit
trusted environment (no ambient proxy, no caller environment inheritance), a
bounded stderr capture used only for safe diagnostics, and one resident process
per Host instance. Initialize performs no implicit live health query. The Host
verifies the executable identity and the reported `buildDigest` /
`backendBindingCatalogDigest` against trusted deployment metadata before the
first invoke. The channel `baseUrl` is passed only in `initialize`; it is not a
process argument and not an environment variable.

## 11. Host error taxonomy

Host-local faults returned to the Host consumer (never to the Provider):

| Code | Meaning |
|---|---|
| `HOST_PROVIDER_UNAVAILABLE` | executable missing, failed to start, handshake failed |
| `HOST_PROVIDER_EXIT` | process ended during an invocation |
| `HOST_PROTOCOL_INVALID` | malformed frame, correlation or result envelope |
| `HOST_TIMEOUT` | invocation deadline exceeded |
| `HOST_CANCELLED` | caller cancelled |
| `HOST_RESULT_INVALID` | result failed slot/reference validation |
| `HOST_ARTIFACT_ERROR` | store/channel failure after a valid result |

Provider protocol faults are surfaced as `HOST_PROVIDER_FAULT` with the exact
provider `code` and no provider message content beyond the fixed registry text.

## 12. Shared conformance fixtures

`conformance/artifact-store/v1/` contains provider-neutral JSON fixtures. The
Provider repository pins the exact bytes and their SHA-256 in its own
documentation before P1 is enabled. The fixtures cover:

| Fixture | Purpose |
|---|---|
| `reference-valid.json` | canonical reference object |
| `reference-invalid-*.json` | wrong member, bad token, extra member, nested object |
| `channel-config-valid.json`, `channel-config-invalid-*.json` | bootstrap validation |
| `channel-get-input-*.json` | 200 and each error response |
| `channel-post-output-*.json` | 201 and each error response |
| `slots-binary.json`, `slots-multipart.json` | descriptor slot declarations |
| `arguments-refs-multipart.json` | nested/array pointer input mapping |
| `result-refs-multipart.json` | nested/array pointer output projection |
| `digest-vectors.json` | byte vectors and SHA-256 values |

Fixtures carry no real token, no real Host URL and no secret. They are
normative for wire shape, not for live authorization.

## 13. Appendix A: P1 acceptance fixture bindings

Cross-repository acceptance needs one agreed, acceptance-only vocabulary. These
bindings exist only in the Provider `-tags providerfixture` build (never in a
production binary and never in the embedded production Catalog) and are driven
by the Host acceptance test against a deterministic local HTTP upstream. They
are named here so both sides can implement the same vectors.

| Binding ID | Method + path | Request | Response |
|---|---|---|---|
| `acceptance.artifact.binary.up` | `POST /acceptance/artifact/binary-up` | one binary body, `application/octet-stream` | JSON `{"size":N,"sha256":"<hex>","mediaType":"..."}` echoed by the upstream |
| `acceptance.artifact.binary.down` | `GET /acceptance/artifact/binary-down` | none | one binary body, `application/octet-stream` |
| `acceptance.artifact.multipart.roundtrip` | `POST /acceptance/artifact/multipart-roundtrip` | `multipart/related`, see below | `multipart/related`, see below |

`acceptance.artifact.multipart.roundtrip` request:

- root JSON (the `arguments.body` value; empty `contentId` strings are the
  Content-ID placeholders the Payload Engine fills):
  `{"requestId":"<opaque>","messages":[{"n1MessageContent":{"contentId":""}},{"n2MessageContent":{"contentId":""}}]}`
- parts: `n1Message` → `Content-ID` pointer
  `/messages/0/n1MessageContent/contentId`, media type
  `application/vnd.3gpp.5gnas`, required; `n2Message` → pointer
  `/messages/1/n2MessageContent/contentId`, media type
  `application/vnd.3gpp.ngap`, optional.
- input slots (`artifactSlots.inputs`): `n1Message` at `/payloads/n1Message`,
  `n2Message` at `/payloads/n2Message`.

Response:

- root JSON:
  `{"resultId":"<opaque>","messages":[{"n2MessageContent":{"contentId":"cid-a"}},{"n1MessageContent":{"contentId":"cid-b"}}]}`
- parts: `n2Response` → `Content-ID` pointer
  `/messages/0/n2MessageContent/contentId`, media type
  `application/vnd.3gpp.ngap`, required; `n1Response` → pointer
  `/messages/1/n1MessageContent/contentId`, media type
  `application/vnd.3gpp.5gnas`, required.
- output slots (`artifactSlots.outputs`): `n2Response` at
  `/messages/0/n2MessageContent`, `n1Response` at
  `/messages/1/n1MessageContent`; each publishes a Host reference object in
  place of the `RefToBinaryData` object, preserving the array structure.

The service key is `acceptance-artifact` and is configured through the trusted
`CA_PROVIDER_SERVICE_CONFIG` service file. The upstream is deterministic: it
validates the declared framing and echoes sizes and SHA-256 values; it never
represents a real NF operation and grants no production availability.

## 14. Non-goals

- No arbitrary URL, method, header, path or credential becomes caller-visible.
- No artifact reference is an authorization grant; Runtime admission and
  Capability authorization still apply before dispatch.
- No production mutation is enabled by this contract.
- No real-NF multipart operation is onboarded by this contract; a real
  operation additionally requires its own pinned source evidence.
- Bytes never travel in NDJSON and the Provider never writes response bytes to
  a filesystem path it chose.
