## 1. 目标与仓库职责

**可执行 Skill 的源码与发布归属仍然是 `ca-skills`。** Compiler 是独立工具仓，负责发布 Compiler 二进制和机器契约；它不拥有业务 Skill，也不负责发布某个业务 Skill 的最终 Bundle。

| 仓库 | 权威职责 | 不负责 |
|---|---|---|
| `ca-agent-next` | CA-SL/SKILL、Package、Artifact 消费、导入和运行时边界的唯一设计权威 | 不保存业务 Skill 源码，不在 Agent 内编译 |
| `ca-skills` | CA-SL 作者规范、SKILL 源码、业务 Skill、示例、CI 编译和可执行 Skill Bundle 发布 | 不实现 Compiler Core |
| `ca-skill-compiler` | Compiler Core、CLI/Worker、Build/Verify API、编译产物契约及 Compiler 自身 Release | 不拥有 Skill 源码，不发布业务 Skill Bundle，不执行 Tool/Owner |
| CA Agent Runtime | 导入并消费已发布的运行时 Artifact；按已定义边界选择和执行 Skill | 不内置、不调用 Compiler，不把 Development Artifact 当作可执行发布物 |

Compiler 的 Release 与 Skill 的 Release 是两件事：Compiler Release 提供可调用的工具版本；`ca-skills` Release 提供由该工具编译出的业务 Skill Bundle。

## 2. 发布 Artifact 的位置与内容

- 作者维护的 Skill 源码保留在 `ca-skills`，遵循其正式 package layout。
- 对含有效 `assurance/` 的 Skill，发布流水线调用 Compiler，生成与该 Skill 绑定的版本化 Runtime Artifact。
- 对没有 `assurance/` 的 SKILL.md-only Skill，不调用 Compiler；按 LLM-guided Skill 的源/元数据发布路径处理。
- 可执行 Skill Bundle 由 `ca-skills` 发布和版本化，包含 Agent 运行所需的 Skill 元数据及 Compiler 生成的 Runtime Artifact。作者源中的 Assurance 文件不由 Agent 在运行时重新编译或解释。
- Agent 只导入由 `ca-skills` 发布的有效 Runtime Artifact；导入时执行既定的基本结构、版本、依赖和引用检查，不内置 Compiler。
- `build-development` 产生的 Development Artifact 固定为 `NOT_ADMITTED`，不是 Agent 可执行发布物，禁止进入正式 Skill Bundle。

## 3. 端到端发布流程

~~~mermaid
flowchart TD
    SRC["ca-skills: SKILL.md + optional assurance source"] --> DIFF["CI: identify changed Skill packages"]
    DIFF --> KIND{"Assurance present?"}
    KIND -->|No| SOURCE["Publish source-only / LLM-guided Skill package"]
    KIND -->|Yes| RESOLVE["Resolve latest stable Compiler Release"]
    RESOLVE --> PIN["Pin resolved tag + source SHA for this run"]
    PIN --> INPUT["Prepare exact BuildRequest, immutable Interface snapshots and trusted bindings"]
    INPUT --> CHECK["skillc check"]
    CHECK --> INSPECT["skillc inspect"]
    INSPECT --> BUILD["skillc build"]
    BUILD --> VERIFY["Compiler self-verifies frozen Artifact before writing"]
    VERIFY --> BUNDLE["Assemble Runtime Skill Bundle"]
    BUNDLE --> RELEASE["Publish ca-skills Release / artifact"]
    SOURCE --> RELEASE
    RELEASE --> IMPORT["Agent imports published Artifact; no Compiler in Agent"]
~~~

### 3.1 Compiler 版本解析

CI 使用**最新正式稳定 Release**，不直接跟随 Compiler `main`：

1. 在每次 CI Run 开始时，解析 `ca-skill-compiler` 最新的非 Draft、非 Prerelease Release。
2. 将解析到的 tag、Release commit SHA、下载资产和 `skillc version` 输出固定到本次 Run。
3. 本次 Run 的所有 Skill Build 使用同一个已解析版本；中途不得再次解析 `latest`。
4. 记录 Compiler tag、commit SHA、资产名、`skillc version`、Skill 源 Commit、依赖快照身份和 Build 结果。
5. 若 Release 查询、资产下载、版本核对或构建输入准备失败，CI fail-closed，不回退到 `main`、旧版或未记录的本地二进制。
6. 重跑历史发布时使用原 Run 记录的 Compiler tag/SHA；需要验证最新 Compiler 时创建新的 Build Run，不覆盖旧证据。

截至 2026-11-25，Compiler 最新正式 Release 为 v2.1.0，源码 SHA 为 `b67fbb56c34d15b8d5a0903c8a7ca93d608f8f65`。这只是本次核对快照，不是永久固定版本。

### 3.2 编译输入与依赖

Compiler 不访问网络下载依赖，也不猜测 Owner、Capability、Schema 或 Evidence 契约。CI/调用方必须准备：

- Skill 的准确作者源文件与明确的 Build target；
- 所需 Interface Package 的不可变字节快照及其依赖闭包；
- 精确的 Owner / Capability / Schema / Evidence 绑定；
- 冻结 v1alpha5 BuildRequest 或 CLI 可加载的项目输入；
- 受控的输出目录。

依赖缺失、身份不匹配、Schema 闭包不完整或可信上下文缺失时，Build 必须失败且不得生成可发布 Bundle。不得以合成 fixture 冒充真实 Owner 发布物。

### 3.3 当前 Compiler 命令

冻结 v1alpha5 发布路径使用 Compiler v2.1.0 的普通 CLI：

~~~bash
skillc version
skillc check PROJECT --skill SKILL_NAME --json
skillc inspect PROJECT --skill SKILL_NAME --json
skillc build PROJECT --skill SKILL_NAME --out DIST_DIR --json
~~~

`build` 在写出冻结 Artifact 前自动执行自身验证；CLI 的退出码为 0 成功、1 编译/Artifact/Verify 失败、2 输入/用法/I/O 错误。失败时 CI 不得继续组装或发布 Bundle。

Development API 的 `build-development` / `verify-development` 只用于开发期接口闭包与互操作检查；其 `NOT_ADMITTED` 产物不得被当作 Agent Runtime Artifact 发布。

## 4. when 与版本门槛

`contract.yaml.when` 属于可选 Assurance Contract 的 Skill 选择表达式，不是执行期 Predicate。该能力必须同时满足语言规范与 Compiler 发布 Artifact 的支持：

- [ca-skills PR #88](https://github.com/odango-chan/ca-skills/pull/88) 当前仍为 OPEN，规范变更尚未成为 main 的正式发布基线。
- [ca-skill-compiler Issue #61](https://github.com/odango-chan/ca-skill-compiler/issues/61) 当前仍为 OPEN；Compiler v2.1.0 的冻结发布 Artifact v1alpha5 不包含 `when` CheckedExpr/DescriptorSet，Development v1alpha1 也不是运行时发布格式。
- 因此当前不能宣称 v2.1.0 已能发布支持 `when` 的可执行 Runtime Artifact。不得把 Development `NOT_ADMITTED` Artifact 绕作正式发布物。
- 当 #88 合并并形成正式规范基线、#61 的新版 Runtime Artifact 契约及 Compiler Release 可用后，`ca-skills` CI 才能对使用 `when` 的 Skill 启用新版 Build/Verify；版本门槛必须由 CI 明确检查。

无 Assurance 的 SKILL.md-only Skill 不调用 Compiler。存在 Assurance 但声明了 Compiler 尚不支持的语法时，必须失败并报告，不得静默降级到 LLM-guided。

## 5. 当前实现状态与差距

截至 2026-11-25 已核对：

| 项目 | 当前证据 | 结论 |
|---|---|---|
| Compiler 产品 | v2.1.0 正式 Release，含冻结 v1alpha5 与 Development v1alpha1 两条路径 | Compiler 产品已发布 |
| ca-skills Source Hygiene | `.github/workflows/source-hygiene.yml` 当前下载 Compiler v2.0.2，执行语法/诊断和缺失 Owner fail-closed 检查 | 仍使用旧 Compiler；不是可执行 Artifact 发布 |
| ca-skills CI Build/Bundle Release | 当前核对的 Source Hygiene Workflow 未执行 Runtime Artifact Build，也未发布可执行 Skill Bundle | NOT_IMPLEMENTED / NOT_VERIFIED |
| CA-SL when | ca-skills PR #88 OPEN | 规范候选，未成为主线 |
| when Runtime Artifact | Compiler Issue #61 OPEN | 新版发布产物未完成 |
| Agent 运行时 | 设计为只导入已发布 Artifact | 不调用 Compiler |

因此，本说明书定义的是目标发布架构与迁移步骤，不把当前 Source Hygiene 检查冒充 Build/Release 验收。下一步应在 `ca-skills` 建立独立实施 Issue，并在该仓实现 CI 的稳定版 Compiler 解析、版本固定、真实依赖输入、Build/Verify、Bundle 组装和 Release 发布；该实现完成前，Executable Skill Release 保持 NOT_IMPLEMENTED。

## 6. 验收条件

- REL-01：Skill 源码和最终 Skill Bundle 的发布归属均为 `ca-skills`；Compiler 仓只发布 Compiler。
- REL-02：每个编译 Run 解析最新正式 Compiler Release 一次，并固定 tag、commit SHA、资产和 `skillc version` 输出。
- REL-03：Build 输入使用精确 Skill source、immutable Interface snapshots、完整依赖闭包和可信绑定；缺失时 fail-closed。
- REL-04：对含 Assurance 的受支持 Skill 运行 Check → Inspect → Build；构建成功后自验证；失败不得发布部分 Artifact。
- REL-05：SKILL.md-only 无 Assurance 不调用 Compiler；Development `NOT_ADMITTED` Artifact 不得进入运行时发布。
- REL-06：新版 `when` 仅在语言规范与 Compiler Runtime Artifact 两侧都正式发布后启用。
- REL-07：发布 Bundle 可由 Agent 导入；Agent 运行时不内置、不调用 Compiler。
- REL-08：PR CI 产物和正式 Release 分开；正式 Release 记录 Skill 源 Commit、Compiler tag/SHA、依赖快照身份、构建结果和 Artifact 文件清单。
- REL-09：不引入生产级 Skill Admission、签名、额外 SHA-256、Trust Registry 或生产资格认证。
