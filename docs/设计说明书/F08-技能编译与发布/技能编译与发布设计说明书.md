## 1. 仓库职责与发布对象

| 组件 | 权威职责 | 不负责 |
|---|---|---|
| ca-skills | CA-SL 作者规范、SKILL.md、Assurance 作者源、Skill Bundle 组装与发布 | 不维护 Compiler 内部实现 |
| ca-skill-compiler | Check、Schema/CEL 静态检查、Build、Verify、新版 Runtime Artifact Schema 与 Compiler Release | 不负责 Skill 业务内容、Agent 导入和运行时选择 |
| ca-agent-next | 项目群设计权威；F02/SR-004/005/006 消费发布 Bundle | 不内置、不调用 Compiler，不实现 Skill Admission |
| ca-agent-demo | 既有参考实现和测试证据 | 不改变 Next/Compiler 的契约所有权 |

必须区分三个产物：

1. **Compiler Runtime Artifact**：Compiler 生成的确定性运行时文件，包含 Procedure、所有已声明 Contract.requestSchema 的规范化 G.4 Schema 根/闭包，以及有 when Skill 的 CheckedExpr/DescriptorSet。
2. **Published Skill Bundle**：ca-skills 发布流程按作者/发布契约组装 SKILL.md 与 Compiler Runtime Artifact。
3. **Agent SkillCatalog**：Next 导入成功后在内存中形成的运行时快照，不是 Compiler 产物。

## 2. when 编译与发布路径

作者源位置固定为 skills/<skill-name>/assurance/contract.yaml 的可选顶层 when。SKILL.md Front Matter 不增加 when；predicates.yaml 只承载执行期 Predicate。

~~~text
ca-skills Author Source
  ├── SKILL.md
  └── assurance/
      ├── contract.yaml       # optional top-level when
      ├── procedure.yaml
      └── predicates.yaml
            |
            v
ca-skill-compiler (single Go Core)
  ├── Parse / ContractAST
  ├── Schema Registry / Request Schema closure
  ├── CEL G.4 static check / guard analysis
  ├── Normalized Request Schema root + full $ref closure (if declared)
  ├── CheckedExpr + FileDescriptorSet (if when is declared)
  ├── Build versioned Runtime Artifact
  └── Verify / deterministic comparison
            |
            v
ca-skills Bundle Assembly
  ├── SKILL.md
  └── Compiler Runtime Artifact
            |
            v
ca-agent-next Skill Importer
  ├── validates published Bundle shape and local references
  ├── constructs Program and type environment once from CheckedExpr/DescriptorSet
  └── returns validated candidate with Program, type environment and Schema closure
            |
            v
ca-agent-next SkillCatalog (SR-005)
  └── builds an immutable generation and atomically activates it after all candidates validate
~~~

Compiler 对 when 的静态检查、nullable lowering、Any type URL、DescriptorSet 和 Artifact 结构详见 [EC02 Compiler 设计说明书 §3–7](../EC02-Compiler/Compiler设计说明书.md)。Next 消费行为详见 [F02 §2–11](../F02-Skill管理与选择/Skill管理与选择设计说明书.md)；本设计不复制消费端逻辑。

## 3. Compiler Runtime Artifact 契约

- 已发布 Artifact v1alpha5 保持冻结字节和语义不变。
- Development Artifact v1alpha1 保持冻结并 NOT_ADMITTED，不得用于 Agent Bundle。
- 新版 Runtime Artifact 使用独立版本化 API，BuildResult 也使用独立版本化结果契约；中央设计固定：languageTarget=`connectionagent.io/v1.6.0`；BuildRequest=`connectionagent.io/compiler-build-request/2`；DependencyInspection=`connectionagent.io/compiler-dependency-inspection/2`；BuildResult=`connectionagent.io/compiler-build-result/2`；Runtime Artifact=`connectionagent.io/compiler-artifact/2`。Compiler 新 Release 目标 SemVer=`3.0.0`。这些是 Next 的设计目标，未发布前产品验收仍 NOT_RUN；生产仓必须按此实现，不得自行选择机器标识。新版 Artifact 必须含 SR-029 定义的 Capability→Callable Binding；既有 Compiler #61 v1alpha5 when 设计不自动构成 1.6.0 发行证据。新 Compiler 版本采用**仅支持 1.6.0 的固定 API 集**，不得在同一二进制中双轨解析/构建旧作者语法、旧 Build DTO 或旧/新 Artifact。
- EC02 已由 Next 固定 `connectionagent.io/compiler-artifact/2`；Compiler Owner 的职责是实现和发布，不再拥有更改公共 API 名称的单方决定权。若有不可实现证据，先回到 Next 修订设计。
- 每个声明 Contract.requestSchema 的 Skill，无论是否声明 when，都必须在 Artifact 中携带规范化 G.4 Request Schema 根与完整 $ref 闭包，供 Host 按 M.3 验证 Event payload。
- Contract.contexts 显式引用的 Schema-only Interface Package 必须进入 Schema dependency closure；其 0 Capability / 0 Callable exports 不生成 Capability Binding、Callable allowlist 或 Tool Effect。零 Capability roots 可以与非空 Schema dependency closure 同时成立。
- 有 when 的 Skill 携带标准 CheckedExpr Any 与 CEL DescriptorSet；DescriptorSet 始终包含 event.type，仅当表达式引用 input 时才包含该 Skill Request Schema 类型闭包。DescriptorSet 不替代完整 JSON Schema 断言。
- **1.6.0 Manifest 由 Compiler Owner 重新冻结唯一 Schema**，明确 Skill identity、source/compiled files、Request Schema 根与完整 resources[]、when CheckedExpr/DescriptorSet、唯一 Capability→Callable Binding（含 kind/Effect/Schema/依赖身份）及输出文件清单。允许 Owner 复用合理的字段名称，但**不以兼容旧 Manifest 为目标**；旧版 Manifest、BuildRequest、BuildResult 均不得被新 Compiler/Agent 接受。不新增摘要、签名或 Trust Registry 体系。
- 建议版本化 Schema 路径为 contracts/2/artifact-manifest.schema.json 与 contracts/2/build-result.schema.json；具体字段由 Compiler Owner 在 Compiler 仓冻结后，Next 才按其消费。
- 新 Artifact 只使用新版本契约定义的文件清单和必要的既有构建侧校验，不增加额外 SHA-256、签名、Trust Registry 或生产准入；**不得保留旧格式消费分支**。

### 3.1 新版单版本可评审输入/输出边界

- **Check 输入：**由 ca-skills 发布的唯一 1.6.0 作者 Schema、SKILL.md 与可选 Assurance，源 Contract/Procedure 对外仅 Capability；无旧版 Alias::Callable 或旧 Parser。
- **Link 输入：**明确的依赖 Package 闭包、Publisher/Owner identity、Capability exports、唯一公开 Callable membership、kind/Effect/Input/Output Schema、Schema-only Package 的显式 Schema exports 和 Reconcile 私有绑定信息；Schema-only Package 可有 0 Capability / 0 Callable，不产生任何 Skill-facing Binding；Compiler 不能从 provider backend catalog 推断授权。
- **Build 输入：**单一 1.6.0 BuildRequest / DependencyInspection；旧 v1alpha5 BuildRequest 和 Development v1alpha1 请求均不得进入新 Compiler。所有外部字段由 ca-skills、Compiler、Owner/Provider 在各自发布 PR 冻结；文中示例路径均为设计候选，不是已发布 Schema。
- **Build 输出：**单一 1.6.0 BuildResult/Artifact，Manifest 包含已检查 `capabilityBindings`、Procedure、when CheckedExpr/DescriptorSet（若存在）、Request Schema 根及完整闭包（若声明）、contexts 引用的 Schema-only dependency closure、精确 Callable allowlist 和可用文件列表。Schema-only Package 不生成 Capability Binding / Callable allowlist；无 Assurance 的指导包不产生 Deterministic Artifact。
- **Verify：**独立校验新 Artifact 的文件清单、Schema 与绑定确定性；不调用旧 Compiler 做兼容/迁移。构建或验证失败不组装部分 Bundle；发布后 Agent 只导入对应正式产物。
- **模块验收：**1.6.0 正例含唯一映射、OpenAMSM 事件 Capability 拆分、Provider 闭合 selector，以及 0 Capability / 0 Callable 的 Schema-only Package；负例含多成员/重复 Callable、非法空 Schema-only Package、缺 Schema、未声明 Schema 依赖、损坏 CheckedExpr、旧版本/旧 DTO/旧 Bundle/未知 API，必须全部按拒绝路径记录。真实 Release 的 tag/SHA/asset 和产品 Golden 尚未产生；中央设计目标已固定，未发布时产品验收 `NOT_RUN`。Compiler 目标 Release 为 `3.0.0`，Bundle 目标 Release 为 `1.6.0`。

## 4. ca-skills CI 编译与 Bundle 组装

一次发布流水线必须固定单一 Compiler 输入，不能在同一次运行中动态漂移：

1. 读取 ca-skills 仓库的 `release/bundle-inputs.yaml`，要求其中精确固定 Compiler `3.0.0`、完整 commit SHA、Release asset、languageTarget 和四个 API 标识。
2. 缺少任一固定值、发现浮动 `latest` 或 Release/API 不匹配时立即停止；CI 不得联网解析“最新稳定版”，也不得在一次流水线内重新选择 Compiler。
3. 检查 Compiler 支持的 Artifact API 与 CA-SL languageTarget。**新发布目标必须是 `connectionagent.io/v1.6.0`**；不支持的 API/语言版本直接停止，不回退到冻结旧格式或 Development。
4. 对 SKILL.md-only Skill：只发布 SKILL.md，不调用 Compiler。
5. 对含 assurance/ 的新 Skill：按 **CA-SL 1.6.0**（Issue #40 / SR-029）的 Capability-first 作者契约提交完整源，执行适配 1.6.0 的 Compiler Check、依赖/唯一 Binding 校验、Build 和 Verify；未发布新版编译器前该步骤 BLOCKED。历史 v1alpha5 Build 只属于历史证据。
6. 只有所有目标 Skill 的构建和验证通过，才进入 Bundle 组装。任何 Skill 失败都阻断本次发布，不发布部分成功的 Bundle。
7. 按 ca-skills 自己拥有的 Bundle 契约组装 SKILL.md 与 Compiler Runtime Artifact（其中包含已声明 Request Schema 快照/闭包）；不在 Next 或 Compiler 设计中另造第二种 Bundle 格式。
8. 发布后保留作者源提交、Compiler tag/SHA、Artifact API、languageTarget、Bundle/Release 资产、构建与验证日志。没有发布授权时只可完成预检或候选构建，不得创建 Release。

Compiler Release 的解析必须在流水线开始时固定；禁止某个 Skill 使用较新 Compiler、另一个 Skill 使用旧 Compiler，或 Verify 时重新解析浮动的 latest。

## 5. 发布失败与恢复规则

| 失败点 | 行为 |
|---|---|
| 无稳定 Compiler Release 或无法固定资产 | 停止发布，记录 BLOCKED 和解除条件 |
| Artifact API / languageTarget 不支持 | 停止，不自动转换格式、不回退到 Development |
| Assurance 作者源无效 | Compiler 诊断回传作者，整个受影响发布批次不产生部分 Bundle |
| Build 成功但 Verify 失败 | 不组装、不发布 Bundle |
| Bundle 组装失败 | 不发布 Release，保留已生成的本地证据 |
| 发布授权缺失 | 保留候选产物和日志，不创建 Release |
| Agent 导入失败 | 由 F02/SR-004/005 处理；不得要求 Agent 调用 Compiler 修复 |

## 6.1 1.6.0 Bundle 输入锁定、目录与原子发布

ca-skills 维护唯一输入锁文件 `release/bundle-inputs.yaml`（`apiVersion: connectionagent.io/skill-bundle-inputs/1`）。它不是包管理器，只记录本批构建使用的精确发布输入：

- `languageTarget: connectionagent.io/v1.6.0`；Compiler `version: 3.0.0`、40 位 `commit`、Release asset 名称、BuildRequest / DependencyInspection / BuildResult / Artifact API。
- Echo Interface Package 的 Package ID / SemVer；Owner Interface Package 与 Host Context Schema-only Package 的 Package ID / SemVer，分别取自 SR-008、SR-025、SR-030 的中央设计。
- 所有字段必须是固定值；空值、范围、latest、版本漂移或不在中央 SR 中的 Package identity 一律停止。

首批五个 Skill 根及处理方式固定：

| Skill 根 | Assurance | 依赖与处理 |
|---|---|---|
| `echo-guide` | 否 | 只校验并打包 `SKILL.md` 与声明资源；不得调用 Compiler |
| `echo-assured` | 是 | Capability `example.echo.message.read`；依赖 Next / SR-008 导出的 `urn:example:echo:interface@1.0.0`，Callable `echo.read` 不进入 Skill 作者源 |
| `establish-pdu-session-mas` | 是 | 使用 SR-029 固定的 Owner Capability 集及 SR-030 Host Context Schema-only Package |
| `modify-pdu-session-mas` | 是 | 使用 Owner Capability `mas.ssm.n1.modify.parse`、`mas.upn.up.qos.delta`；它们不是 SR-026 的协议级 Codec Capability |
| `release-pdu-session-mas` | 是 | 使用 SR-029 固定的 Owner Capability 集及 SR-030 Host Context Schema-only Package |

五个作者根必须来自同一个 `ca-skills` commit。对四个 Assurance 根分别执行同一 Compiler 3.0.0 的 Check、DependencyInspection、Build、Verify；`echo-guide` 不进入 Compiler。完整命令行以 Compiler 3.0.0 Release 文档为唯一依据，ca-skills 不复制或重实现 Compiler 逻辑。

每个发布 Skill 根采用以下结构：

~~~text
published-skills/<skill-id>/
  SKILL.md
  resources/...
  runtime-artifact/                 # 仅 Assurance Skill
    manifest.json
    skills/<skill-id>/compiled/...
~~~

`runtime-artifact/` 是单个 Skill 的完整 Compiler Artifact 根，必须原样保留其 Manifest 和全部相对路径；不得只复制部分 `.pb` 或 JSON 文件。不得将作者 `assurance/`、Compiler 可执行文件、开发日志或临时文件混入已发布 Skill 根。

最终发布资产为单一 `skill-bundle-1.6.0.zip`，根目录仅含 `published-skills/` 和五个 Skill 根。外层 Bundle 不另造第二套 Runtime Manifest；每个 Assurance Skill 的 `runtime-artifact/manifest.json` 仍由 Compiler 拥有。`bundle-build-report.json` 作为 CI / Release 证据附件，不作为 Agent 导入输入。

ZIP 使用仓库既有确定性归档规则：路径排序、统一 `/` 分隔符、固定时间戳、拒绝 symlink 与非普通文件；同一源 SHA、Compiler 和依赖输入重复构建必须逐字节一致。不得新增签名、Trust Registry 或额外完整性机制。

发布必须整批原子：五个 Skill 根全部通过源检查、四个 Artifact 全部 Verify、依赖闭包唯一、输出目录无缺失/额外/碰撞后，才生成一个 ZIP 并进入授权发布步骤。任一失败则本批发布资产为零，不上传部分成功目录。Agent Importer 消费解压后的单个 Skill 根，不负责下载/解压整个 Bundle。
