# 公共契约与所有权规范

> 文档类型：跨组件公共契约与职责边界规范  
> 状态：**设计待评审**（CA-SL 1.6.0 Capability-first 增量设计；实施及外部发布仍 NOT_RUN）
> 文档版本：0.2.8
> 全局评审范围：继承根目录 Agent.md 的 review_scope    
> 本文局部非目标：以本文范围与非目标章节为准；无额外扩展  
> 修订日期：2026-11-27  
> 适用范围：ca-agent-next 与其 Plugin、Skill、Tool、Owner 集成

关联需求项见 [IR-004](../IR/IR%20总登记册.md#ir-004)、[IR-005](../IR/IR%20总登记册.md#ir-005)。

## 1. 目标

明确每类契约由谁定义、由谁发布、由谁消费，避免在 Agent Core、Plugin Manifest、Skill、Tool Interface Package 和 Owner 之间复制业务契约。公共契约必须有唯一权威源；其他组件只能引用或消费，不得维护语义相同的第二份定义。

## 2. 契约类型与权威所有者

| 契约 | 权威所有者 | 主要消费者 | 规则 |
|---|---|---|---|
| Agent 架构与公共 Runtime 机制 | ca-agent-next | Core、Host、Plugin 实现 | 本仓唯一架构与公共机制定义 |
| Plugin Manifest / IPC | ca-agent-next | Plugin Manager、Native Plugin | 精确版本，不设别名或兼容映射 |
| Event type / normalized Event payload Schema | Next F06 冻结集成语义映射、payload/discriminator 和 fixtures；Event Plugin 拥有 plugin.yaml 声明与随包发布的 schema 文件，并必须符合 F06 | Host / Skill Resolver | 描述协议输入，不包含 Skill ID、Run ID 或业务 Goal；Host 独占 Run/responseObligation 关联 |
| Provider 公开 Callable / IO Schema / Effect / Capability | Tool Interface Package 所有者 | Runtime、Plugin Manager、Compiler | 唯一公开 Provider Callable 契约来源 |
| Owner 业务契约 / Callable / IO Schema / Outcomes / Receipt / Commit Proof / Reconcile | 业务 Owner（例如 MAS）及其 Owner Contract Package | Skill/Compiler、Provider、Runtime | 定义该业务域拥有的业务能力、输入输出和权威结果；补充标准未定义的业务语义，不得重定义或覆盖外部标准契约 |
| Provider Runtime Bindings / backendOperationId | Provider 包所有者 | Plugin Manager 的 Provider Driver、Runtime | 私有执行映射；不构成公开契约或授权 |
| Provider Backend Binding Catalog v2 | ca-client-tools | Provider 进程内部 | 私有 backend 到 handler/serviceKey/source/Effect/Schema 的执行目录；Host 不解析、不复制、不用作授权 |
| Skill 作者源 / SKILL.md | Skill 作者及 ca-skills | 外部 Compiler、Agent | SKILL.md 是 Agent-facing 指导 |
| CA-SL Assurance / Contract / Procedure / Predicate | ca-skills 规范 | ca-skill-compiler | 语言语义不在 Agent Core 重写 |
| 已发布 Skill Runtime Artifact | ca-skill-compiler | ca-agent-next | Agent 只消费发布物，不调用 Compiler |
| SBI OpenAPI / NAS / NGAP 标准 | 3GPP 规范；具体源版本按 OpenAMSM 实际支持版本固定 | Event Plugin、Compiler、Codec Tool | 标准定义的协议字段、枚举、媒体类型和消息结构以原始标准契约为准；SBI OpenAPI 原件不改写，不复制第二套协议 Schema |
| Host Artifact Handoff | ca-agent-next | Event/Delivery Plugin、Tool Plugin | Host 拥有 ArtifactStore 和引用 |
| 运行时配置与部署绑定 | 部署配置/运行方 | Host、Plugin Manager | 不反向变成业务契约注册中心 |

## 2.1 标准契约优先与业务 Owner 契约补位

本规范采用 **标准优先、领域补位、来源分离、显式组合** 的契约治理原则：

1. **标准已定义的内容，直接消费权威标准契约。** 协议字段、枚举、可选性、约束、媒体类型、消息结构和线格式语义，以对应标准版本为准。3GPP SBI 使用 OpenAMSM 实际支持版本对应的原始 OpenAPI 3.0 源；原件、相对 `$ref` 和标准语义不得由 CA-Agent 改写或另行投影。
2. **标准未定义的业务语义，由对应业务 Owner 定义自己的契约。** 例如 MAS Owner 可以通过自己的 Owner Contract Package 定义 MAS Capability、Callable 输入输出、业务 Outcomes、Receipt、Commit Proof 和 Reconcile。这是领域 Owner 的权威业务契约，不是第二份 3GPP 契约，也不要求新增由 Agent Core 维护的通用 Domain Contract Package 或全局 Contract Registry。
3. **同一 Skill 可以消费多种权威契约，但必须保持来源和职责分离。** 例如 SBI ingress Request 仍由 3GPP 契约定义；MAS Owner Contract 约束 MAS 业务调用及结果。Procedure 必须显式把 Request 字段映射到 MAS Capability arguments，不得把 MAS 字段塞入、改写或伪装成 3GPP JSON 字段。
4. **标准字段不得被领域字段静默覆盖。** 如果外部标准和业务契约出现同名但语义不同的字段，标准契约仍控制协议层含义；业务含义必须由明确独立的领域字段/契约表达。无法无歧义分离时，拒绝猜测并阻塞该设计。
5. **没有适用标准的入站接口，可以使用领域 Owner / Event Plugin 正式发布的领域 Request Schema。** 例如 MAS 可以定义其自有业务事件或接口契约；但不能仅因为 MAS Owner Contract Package 定义了 Callable IO，就推断它同时定义了某个 SBI 入站 Request Schema。

## 3. Skill Contract 与业务输入

Skill Contract 不是独立 Package。它属于可选 assurance/contract.yaml，只对带 Assurance 的 Skill 存在。其职责是声明该 Skill 的确定性目标、输入/Context 需求、依赖、Capability 和可选 when。

- 没有 Assurance 的 Skill 不需要 Contract，也不具备 Deterministic 执行。
- 有有效发布 Assurance Artifact 的 Skill 可以使用 Deterministic 或 LLM-guided。
- Agent 运行时消费发布 Artifact，不加载作者源 Contract 并自行编译。
- when 只用于 Skill 选择；predicates.yaml 只用于执行期业务判断。when 可读取的 `event.type` 是 Ingress/Host 生成的事件元数据，`input` 则是当前 Request Schema 根对应的已验证输入；两者不能混为一个 JSON Body。
- 不增加由 Agent Core 维护的通用 Domain Contract Package、TaskContract Package、第二份 LLM Contract 或全局业务 Contract Registry；业务 Owner 可以发布并维护自己的 Owner Contract Package（例如 MAS），其权威仍归 Owner，Agent 只引用和消费。

### 3.1 Request Schema 与 Owner Contract 的边界

Request 是进入 Agent 的 Event / 用户请求数据；Owner Contract 是 Skill Procedure 调用业务 Owner 时使用的 Capability / Callable 契约。二者可以被同一个 Skill 显式引用，但不是同一个 Schema，也不得互相投影：

- 对 3GPP SBI，Event Plugin 按原始 OAS 3.0 operation / requestBody 处理 HTTP 与 multipart。以 `PostSmContexts` 为例，选定消费面为 `requestBody → multipart/related → jsonData → SmContextCreateData`；Skill 的 `input` 对应 `jsonData` 对象（`SmContextCreateData`），不是完整 multipart envelope，也不包含 N1/N2/N2 Ext1 二进制 part。
- `event.type` 是 Ingress/Host 根据接口身份生成的规范化事件元数据，不是 SBI JSON Body 的字段。若 `requestSchema` 根直接引用 `SmContextCreateData`，则 CEL 的字段路径从该对象根开始，例如 `input.requestType`，不能再人为增加 `input.jsonData` 层。
- SBI JSON Data 直接解析并按原始 OAS 3.0 Schema 校验，不经过 NAS/NGAP Codec。N1/N2/N2 Ext1 保留为独立 Artifact slots；只有选中 Skill 后的 Procedure 确实需要二进制内部字段时，才按需调用对应 Codec READ。
- 若入站接口没有适用的 3GPP / 外部标准契约，`input` 必须引用对应 Owner / Event Plugin 正式发布的领域 Request Schema。MAS Owner Contract Package 只有在明确导出该 Request Schema 时才能作为该输入来源；仅有 Callable IO Schema 不代表它是 Event Request Schema。
- 当一个 Skill 同时依赖 3GPP Request 和 MAS Owner Contract 时，Request Schema 保留标准输入形状，Owner Capability / Callable Schema 保留业务操作形状；Procedure 通过显式 arguments / SourcePath 映射二者。不得自动扁平化、改名、补造字段或把执行期 Codec Result 提前用于 Skill 选择。

## 4. Plugin Manifest 与 Event 契约

Plugin Manifest 只声明 Plugin 身份、进程入口、IPC 版本和 Extensions。Event Extension 声明 Event type、normalized payload Schema 和 Artifact slot。

Manifest/Event 不得声明：

- Skill ID 或 Skill 执行模式；
- 业务 Goal、业务 Procedure 或业务状态机；
- Tool 的完整 Callable/IO Schema；
- Capability Grant 或 Owner 提交结论。

每个新 Event 由 Host Resolver 选择 Skill。Plugin 不得绕过 Host 指定 Skill。

## 5. Tool Interface、Owner Contract、Provider Runtime Bindings 与私有 Backend Catalog

三类跨组件契约职责不同；Provider Backend Binding Catalog 是 Provider 进程内部执行目录。四者不得合并成一份 Next 自维护 ToolCatalog。

### 5.1 Tool Interface Package

Tool Interface Package 是 Provider 对外导出的 Callable 契约权威来源，也是 Skill/Compiler 可见契约来源之一；它不代替业务 Owner Contract Package。ca-client-tools v1.2.0 当前只导出 11 个 READ Tools，Interface ZIP 没有导出 OpenAMSM MAS MUTATION。

- Callable ID 与所属 Capability；
- 输入/输出 Schema；
- Effect 类型（READ / MUTATION）；
- 公开 Artifact Reference 输入/输出约定；
- 包身份、版本、依赖与导出闭包。

Interface Package 的存在不表示 Provider 已安装、当前部署可用或 Skill 获得调用权限。Compiler 使用精确的 resolved dependency snapshot 做静态链接；Runtime 使用部署选定的 Interface Package 校验当前 Skill 的 Callable Scope 和输入输出。此处只适用于该 Interface Package 实际导出的 Callable；不得从 Provider 的私有 Backend Catalog 补造未导出的业务 Callable。

### 5.2 Owner Contract Package

Owner Contract Package 由业务 Owner 发布，是业务 Callable、Effect、输入/输出 Schema、Owner Outcomes、Receipt Schema、Commit Proof、Evidence Guarantee 和 exact-original Reconcile 的权威来源。OpenAMSM 示例使用 env-openamsm 发布的 `urn:openamsm:mas:tool-contracts` v1alpha4，发布物包含 `tool-catalog.yaml`、`capability-contracts.yaml`、`evidence-guarantees.yaml`、Schema 文件和 `manifest.json`。

CA-SL v1alpha5 MAS Skill 通过 `dependencies.mas` 指向该 Owner stable ID，在 `capabilities` 中声明 `mas.*` Capability，并在 Procedure 中使用 `mas::CALLABLE`。该 `mas` dependency 是 Owner Contract snapshot，不是 ca-client-tools Interface ZIP。冻结 v1alpha5 Compiler 从精确 `resolvedDependencies` snapshot 链接 Owner ToolCatalog/Schema，并通过 `trustedBuildContext` 分别验证 Owner binding 与 CapabilityContracts；Development v1alpha1 的 `package.json` / Interface Package / Dependency Lock 是另一 Build profile。

**Capability 的序列化边界：** 冻结 v1alpha5 Artifact 的 `dependencyClosure[].exports[]` 只包含 exportKind/exportId/owner，不包含作者源 `contract.capabilities` 的 Capability ID，也不包含 Development profile 的 `capabilityRequirements`。Compiler Build-time 校验作者源 Capability 与 Owner `CapabilityContracts`；Runtime 的有效 Skill Callable allowlist 仅由 Artifact `operation` / `observation` exports 建立。Runtime 可以按部署固定 Owner Contract 验证 Callable membership / Effect，但不得从 Artifact 读取不存在的 Capability ID，也不得把 Capability ID 当作 Runtime Skill Scope 字段。

**冻结 v1alpha5 Artifact 的依赖 pin 限制：** `manifest.json` 的 `dependencyClosure[]` 只记录 `dependencyId`、`stablePackageId` 和 `exports[]`，不记录 Owner package version 或 snapshotDigest。因此，Agent 不能仅凭 Artifact 声称逐 Skill 的 Owner 字节级依赖锁。当前 Demo 通过 provider.yaml 的 `interfacePackagePath/interfaceSnapshotDigest` 固定 Provider Interface snapshot，并通过 Provider Runtime Bindings sidecar 的 `ownerContract.stableId/version/publicationDigest/manifestDigest` 固定部署使用的 Owner v1alpha4 publication；Host 校验两份已安装发布物与各自绑定一致，并确认 Artifact 所需 exports / Schema 存在。Development v1alpha1 Artifact 虽包含 packageId/version/snapshotDigest Lock，但 `executionStatus=NOT_ADMITTED`，不是当前 Agent 运行输入。若未来需要逐 Skill snapshotDigest pin，必须由新的 Compiler Artifact API/profile 提供，不能修改已冻结 v1alpha5。

Provider Interface Package 不得复制或重写 Owner Callable、Owner Outcomes、Receipt、Commit Proof 或 Reconcile 语义。只有 Owner Receipt 与 Commit Proof 精确绑定原始 Invocation 和 Host scope，Runtime 才能产生 COMMITTED。

### 5.3 Provider Runtime Bindings

Provider Runtime Bindings 是 Provider 包内的私有执行 sidecar，负责声明：

- Runtime/Owner Callable 到 Provider 私有 backendOperationId 的精确映射；
- Provider Effect 与 Owner Callable 的一致性；
- HostInvocation 字段来源、Skill 参数与 Host scope 的绑定；
- Skill 不可见的 privateArguments 注入；
- Provider observation envelope、Receipt 定位和 Reconcile binding；
- sidecar 所引用 Schema 文件的发布身份。

Runtime Bindings 不属于公开 Interface Package，不授予 Skill Capability，不是第二份 ToolCatalog，也不能修改 Owner Contract。对每个 Mutation 的 `commitProof.reconcile.bindingId`，Runtime 必须将其解析到同一 sidecar 中唯一的 READ binding，并将该 binding 派生为 internal-only Reconcile 集合；普通 Skill/LLM dispatch 即使命中 Artifact export 也必须在 Provider IPC 前拒绝，只有 Reconcile Coordinator 内部专用入口可使用原 originalInvocationId 调用。目标缺失、重复或非 READ 时 fail-closed。Provider catalog 响应只用于确认已声明的私有 backend 是否支持/可用，不可扩张公开 Callable 集合。

Plugin Manifest 可以引用公开 Interface Package，但不得复制 Tool Schema、Capability Grant、Owner 结果或 Provider 私有字段。Runtime 组合部署选定的 Provider Interface Package、经 sidecar 校验的 Owner Contract publication 和 Provider Runtime Bindings 完成调用，不建立第二份权威 Registry。

### 5.4 Provider Backend Binding Catalog v2

Provider Backend Binding Catalog v2 由 Provider 所有者维护并嵌入 Provider 可执行文件。它将私有 backendOperationId 映射到固定 Go handler、trusted serviceKey、source pin、Effect、请求/响应媒体类型和参数 Schema。

该 Catalog 只在 Provider 进程内部加载。Host 不读取其文件、不复制其 handler/serviceKey/source 定义，也不将其作为公开 Callable 或 Capability 来源。Host 只能通过 Provider v2 catalog 方法，对 provider.yaml 和 Runtime Bindings 已显式声明的 backendOperationId 集合核对 supported / unsupported。Provider catalog 的存在或 supported 响应不构成 Skill 授权。

## 6. Artifact 与二进制契约

- 原始二进制由 Event Plugin 从协议中提取；Host 负责 staging 和 ArtifactStore。
- Plugin 只提供相对 stagingPath 描述符；Host 校验路径边界和真实 byteLength 后导入。
- Host 生成 opaque artifactRef，并将其与 Event、Run、Invocation 关联。
- Runtime 决定哪个 Action 可以读取/生成 Artifact。
- Tool Plugin 只接收当前 Invocation 已授权的 artifactRef。
- Delivery Plugin 只读取 Host 为当前 responseObligation 暂存的输出文件。
- 原始字节不进入 NDJSON，不用 Base64，不增加 Plugin 自有 Artifact 数据库或额外 SHA-256。

## 7. 身份与关联 ID

以下 ID 必须区分：

| ID | 归属 | 用途 |
|---|---|---|
| messageId | IPC | 当前 IPC 帧 |
| correlationId | IPC | 请求与回复关联 |
| eventId | Event | 逻辑 Event 实例 |
| externalRequestId | 外部协议 | 稳定外部请求/重试身份（若协议提供） |
| responseChannelId | Event Plugin | 当前外部响应通道 |
| runId | Host | 业务执行 Run |
| invocationId | Runtime | 单次 Tool 调用 |
| deliveryId | Delivery | 单次响应交付 |
| responseObligationId | Host | 当前 Event 对应的响应义务 |
| catalogGeneration | SkillCatalog | Skill 快照代际 |

HTTP/2 stream ID 只能用于瞬时传输，不得替代 eventId、externalRequestId 或 runId。

## 8. Owner 结果语义

Owner 是业务状态和提交结果的最终权威。以下结果不得互相混淆：

- Plugin/IPC 成功：仅代表传输/调用链成功。
- HTTP 2xx：仅代表 HTTP 层响应，不自动证明业务 mutation 已提交。
- Delivery 成功：仅代表响应已交付，不改变 Owner outcome。
- Owner Receipt / Commit Proof：按 Owner Contract Package 解释业务提交结果；Provider Runtime Bindings 只声明如何定位和传递这些材料。
- UNKNOWN：必须保持 UNKNOWN，不能被映射为 COMMITTED。

## 9. 禁止重复定义

禁止在 Agent Core 中新增业务路由表、Event→Skill 表、Event→Mode 表、Tool Schema 副本、Owner 状态映射副本、Provider 私有 backend 映射副本、由 Agent Core 自维护的通用 Domain/Task Contract Package、全局业务 Contract Registry 或 Codec Manager。需要新业务时，新增/更新其 Skill、Event Plugin、业务 Owner Contract Package / Tool Interface Package 和部署配置即可；业务 Owner 自有契约不由 Agent Core 代管。

## 10. Capability 与 Callable 的所有权及基数规则

### 10.1 术语和身份

- Capability 是 Owner / Provider Interface Package 面向 Skill 的业务能力身份。Skill Contract 授予 Capability，Procedure 只引用 Capability。
- Callable 是 Package / Compiler / Runtime 使用的稳定公开调用身份，具有 kind、Effect、Input/Output Schema 和所属 Owner / Provider。Callable ID 不属于 Skill 作者接口，也不是模型的选择参数。
- Provider backendOperationId / handler 是 Provider 私有执行身份；一个公开 Callable 可由多个私有 backendOperationId 或 handler 实现，但必须由该 Callable 的封闭、类型化 Input Schema 决定路由。
- Operation / Observation 是 Procedure Node 阶段；Callable.kind 是 Package 导出分类。Operation 阶段匹配 kind=operation；Observation 阶段匹配 kind=observation，且 Effect 必须为 READ。

### 10.2 Skill-facing 一对一不变量

1. 一个 Skill-facing Capability 恰有一个公开 Callable membership。
2. 一个公开 Callable 恰属于一个 Skill-facing Capability。
3. Capability ID、Callable ID、Owner、kind、Effect、Schema 和依赖包身份必须来自同一已解析 Package 快照；禁止跨包拼接。
4. Capability 映射为零个或多个 Callable、Callable 被多个 Capability 共享、依赖闭包中存在歧义或阶段 kind 不匹配，均在 Compiler Link 阶段 fail-closed。
5. 现有 callables[] / capabilities[] 线格式可保留；对 Skill-facing 导出强制 cardinality=1，不额外引入第二套 Catalog 或 Registry。

### 10.3 内部实现自由度与 Reconcile

- Provider 可以在一个公开 Callable 内部使用多个 backendOperationId、handler 或固定实现分支；选择条件必须是 Callable Input Schema 中的封闭 enum / tagged union，不接受任意字符串、LLM 选择或 Provider 动态 Catalog 扩权。
- 若两个入口的业务语义、Input Schema、Effect 或 Evidence Guarantee 不同，应拆成两个 Capability 和两个 Callable；不得仅因名称相近而合并。
- MAS.RECONCILE 保留在 Owner ToolCatalog 和 Mutation Reconcile 契约中，但不作为 Skill-facing Capability 导出。Runtime Coordinator 只能从原 Mutation 的 Reconcile 绑定调用它；普通 Skill / LLM Action 在 Provider IPC 前拒绝。
- Receipt Query 继续保留当前 READ Callable / Capability 语义；不得把 Receipt Query 与 Reconcile 混为一类。

### 10.4 Demo 边界

本规范只要求接口唯一性、静态链接、Schema / Effect / kind 一致性和 fail-closed。不得新增生产 Admission、签名、Trust Registry、额外包级 hash、复杂 IAM 或独立 Capability Manager。

**1.6.0-only 设计评审硬门槛：** Owner/Provider Package 新发布物必须满足一对一，不导入旧 Package。 此章节仅描述目标设计，外部代码/Release/E2E 均 NOT_RUN。
