## 1. 目标与基本原则

建立从设计到实施、再到验收的可追踪关系：

**IR → SR → PR/Commit → Acceptance 证据。** 架构、设计和规范关联 IR，SR 引用具体设计版本与章节。

1. 架构定义系统边界和约束；设计说明书定义机制方案；SR 定义可独立实施和验收的需求单元。
2. [IR 总登记册](../IR/IR%20总登记册.md)定义要解决的问题、预期结果、协作入口和 SR 分解。SR 是实施范围的权威记录。
3. 每个 SR 必须引用明确的设计文档版本和章节、验收 ID、依赖及实施证据。
4. Harness 只能实施状态为 READY 且依赖满足的 SR，不得自行从设计文档推断或扩大实施范围。
5. 设计变更必须先分析影响，再决定复用、创建或替代 SR。
6. 不为 Demo 引入独立需求管理平台、生产级签名、哈希、Trust Registry 或复杂流程系统。

## 3. 文档版本与修订记录

### 3.1 文档版本

每份正式文档必须包含文档版本。新草案可从 0.1.0 起步；各文件独立演进，正式评审确认后可建立 1.0.0 基线。

采用三段式版本：

- 主版本：架构边界、公共契约或核心行为发生不兼容变化。
- 次版本：新增或改变设计行为、接口语义或验收要求。
- 修订版本：文字、排版、链接和不改变需求/验收语义的澄清。

版本表达文档自身变化，不代替 SR 编号，也不表示实现完成。

### 3.2 修订记录

每份正式架构、设计、规范、治理、验收和审计文档必须有“修订记录”章节。每次刷新都追加记录，不覆盖旧行。

| 字段 | 要求 |
|---|---|
| 日期 | YYYY-MM-DD |
| 版本 | 本次文档版本 |
| 修订内容 | 实际变化摘要 |
| 原因 | 为什么需要变化 |
| 影响 SR | 受影响 SR ID；纯编辑填写“无（不影响需求）” |

Git 历史记录具体文件差异；修订记录说明设计意图和需求影响。README.md、Agent.md 等入口文件由 Git 历史管理，不强制增加独立修订表。

## 4. SR 编号与文件格式

- 本仓沿用已有 SR-001，后续使用 SR-002、SR-003……递增；编号全局唯一、永久不复用。
- 文件格式：SR-001-中文主题.md。
- SR ID 一经分配不得重新分配；取消或替代的 SR 仍保留原记录。
- 新需求使用新编号，不通过重命名旧 SR 表达变化。

IR 与 SR 使用独立编号空间，编号永久保留。每项 IR 可关联多个 Issue 并分解多个 SR，SR 至少回链一项 IR。

每份 SR 至少包含：上游 IR、ID、标题、SR 版本、状态、创建日期、设计依据（文档版本与章节）、目标、范围、非目标、依赖、验收条件、Issue/PR/Commit、测试证据、替代关系和修订记录。

SR 记录需求本身，不复制设计说明书的完整方案和规范字段表。

## 5. SR 分解原则

- 一个设计说明书可以分解为多个 SR；一个 SR 可以引用多份设计说明书或规范。
- 按独立实现责任、依赖和验收边界拆分，不按文档章节机械拆分。
- 一个 SR 可以关联多个 Issue/PR/Commit；一个 PR 也可以实现多个紧密相关的 SR，但必须逐项报告验收结果。
- 纯设计讨论、尚未定案的选项不创建 READY SR。
- ca-agent-next 是项目群的统一任务入口。修改任一协作仓前，在 `docs/SR/` 登记或引用已明确覆盖该改动的 SR。消费侧 SR 仅凭依赖引用不足以启动目标仓改动。

## 6. SR 状态与转换

| 状态 | 含义 | 进入条件 |
|---|---|---|
| DRAFT | 草案，尚不可实施 | 设计基线待评审，或范围/依赖/验收条件尚未确认 |
| READY | 已具备实施条件 | 设计已评审确认；范围、责任、依赖和验收条件完整 |
| IN_PROGRESS | 正在实施 | 已开始代码/配置/测试工作，并记录实施关联 |
| IMPLEMENTED | 实施已集成 | 代码已进入指定目标分支或正式集成基线；验收尚未全部通过 |
| VERIFIED | 验收通过 | 所有必需验收条件有真实证据且结果满足 SR |
| BLOCKED | 明确阻塞 | 存在外部依赖、环境或决策阻塞，并记录解除条件 |
| SUPERSEDED | 被新 SR 替代 | 新 SR 明确声明 supersedes，并保留旧记录 |
| CANCELLED | 已取消 | 有明确取消原因和决策依据 |

正常路径为 DRAFT → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED。READY/IN_PROGRESS/IMPLEMENTED 可因真实阻塞转为 BLOCKED；解除后回到原适用状态。SUPERSEDED 和 CANCELLED 为终态。

**IMPLEMENTED 不等于 VERIFIED。** PR 合并只证明代码集成，不自动证明验收通过。未运行测试标记 NOT_RUN；外部依赖未满足标记 BLOCKED 或 NOT_VERIFIED，不得推测 PASS。

## 7. 设计变更与 SR 影响分析

每次正式设计刷新，必须与上一个文档基线做差异分析：

| 变化类型 | 处理 |
|---|---|
| 纯文字、排版、链接、无语义澄清 | 更新文档修订记录；不创建新 SR |
| 新增独立行为或验收要求 | 创建新 SR |
| 改变既有 SR 的范围、行为、接口或验收条件 | 创建新 SR，填写 supersedes；旧 SR 标记 SUPERSEDED |
| 删除既有要求 | 形成取消/替代决策；旧 SR 标记 CANCELLED 或 SUPERSEDED，不删除历史 |
| 不影响既有 SR 的设计补充 | 保留 SR，更新设计依据版本和影响分析结论 |

影响分析必须检查既有 SR 是否仍然有效、哪些 SR 需要新增/替代/拆分/取消、哪些实施中任务需要暂停、哪些已实施需求需要回归验收，以及受影响的规范、Acceptance、Example、Harness 和跨仓消费者。

设计基线更新前先完成影响分析和 SR 关系更新；不得先实施再补追踪。

## 8. GitHub 与实施证据关联

- SR 文件是需求范围和验收条件的权威来源。
- 每批变更开始前必须创建或引用覆盖范围的 GitHub Issue，含文档、配置、测试、迁移和删除。纯治理或文档变更可只关联 Issue。实施 Issue 引用相关 IR、SR 和验收项。
- 实施 PR 必须列出 IR/SR ID、实现范围、Commit 和逐项验收结果。Commit 可在提交说明中引用 SR，或由实施 PR 明确映射到 SR。验收记录包含 SR/Acceptance ID、受测 SHA、命令、环境、结果和证据位置。
- Commit、测试命令、测试输出和 Example 运行结果写回 SR 或对应验收记录。
- PR OPEN 只能证明工作进行中；PR MERGED 也不自动等于 VERIFIED。
- 进入 IN_PROGRESS 时必须记录实际实施 Issue；每份 PR 必须引用 Issue，每个 Commit 通过 PR 或提交正文追溯。跨仓 PR 使用完整 Issue 链接。
- 外部仓库 PR/Issue 只能记录为依赖证据，不能当作 Next SR 的实施完成证据。

### 8.1 跨仓任务

1. 从 [功能树与需求追踪基线](../治理/功能树与需求追踪基线.md) 定位权威仓。在 Next 选择或登记 IR，创建或引用覆盖本次变更的 SR。每个 SR 指定一个实施仓。涉及多个仓时按仓拆分 SR，由同一 IR 和依赖关系串联。
2. SR 记录完整仓名、基线分支及 SHA、变更范围、设计与契约、依赖和验收。已有范围足够的 SR 可复用。明确目标和依赖且经评审达到 READY 后，在目标仓实施。
3. 目标仓 Issue 和 PR 引用 Next SR 链接，Next SR 回填目标仓 PR、实施提交、测试命令、环境及结果。跨仓实现验收和 Next 集成验收分别取证，按各 SR 独立关闭。
4. 对协作仓的修改权限适用于已登记并符合实施门槛的任务。合并、发布及直接改受保护分支遵循各仓规则与明确授权。

### 8.2 使用评审中的固定提交开展受限实施

当规范或设计需要借助实施证据完成评审时，负责人可以批准使用未合并的规范或设计提交。SR 须按阶段登记目标仓、规范或设计 PR 与完整 SHA、批准人及记录、允许的改动和环境、Acceptance ID、退出条件及明确排除项。Harness 从登记的 SHA 读取规范；PR 更新后，仍使用原固定 SHA，除非重新确认差异、影响和适用验收并更新 SR。

READY 可以针对获批阶段。该阶段须独立具备实施条件和目标仓授权。PoC、实现验证和评审证据可先提交到分支或 PR。依赖正式规范、发布资产、主分支可达链接或生产资格的阶段，继续遵守各自的明确门槛。候选规范上的通过结果记录为候选 SHA 证据。正式基线改变时按差异复验，正式符合性和集成状态依据正式基线及对应验收证据。

审查未合并方案时，记录证据能支持哪些决定、尚需哪些验证，以及暂停或回滚条件。合并、发布与跨仓写入授权分别按现行规则处理。

## 9. DeepSeek Harness Goal 与交付门禁

1. 默认使用 Goal 模式。一个 Goal 覆盖同一功能子树或同一端到端能力，可合并多个 READY 且依赖已满足的 SR。先按依赖拓扑排序，同层按功能树与交付顺序排列。已批准的并行豁免按 SR 原文执行；使用 §8.2 的分阶段 READY 时，Goal 只纳入获批阶段，仍须通过本节的文档交付门禁；依赖证据尚未满足的 SR 留在候选清单，重新预检通过后再纳入。循环依赖、冲突或缺失证据须先处理。
2. Goal 清单固定设计 ref/SHA、功能节点、范围与非目标、授权仓库和分支、关联 Issue、逐 SR 执行顺序与依赖证据、Acceptance ID、命令及预期结果、停止与恢复条件。开始前及每个 SR 启动前复核 READY、依赖和仓库状态。
3. 生成、交付执行提示词前，相关文档须通过[文档交付门禁](文档编写与治理规范.md#13-执行提示词交付门禁)。草稿和预检材料仅用于核查。静态结果与真实模型执行分别记录。
4. 执行中遇到设计冲突、契约不明、权限缺失或验收失败，停止该 SR 和受影响的后继 SR。只有明确独立且仍满足条件的已列 SR 可继续。保留已通过证据，逐项记录 FAIL、BLOCKED 或 NOT_RUN、原因、证据和首个安全恢复步骤；恢复时重新验证基线和依赖。
5. 每个 SR 回填 Issue、PR、Commit、受测 SHA、环境、Acceptance ID、命令、预期与实际结果及证据位置，再更新 SR 总索引和实施状态总览。集成后才记录 IMPLEMENTED；全部验收有真实证据才记录 VERIFIED。所有纳入项达到清单完成判据后才关闭 Goal；部分成功按逐项结果报告。
6. Flash 为动态配置。当前官方推荐 `deepseek-flash`，默认显式发送 `low`（Chat Completions 的 `reasoning_effort`、Responses API 的 `reasoning.effort`、Anthropic 格式的 `output_config.effort`）。每次记录时间、接口、发送的别名与实际参数、返回的模型标识和可核实的解析版本；无法确认的字段标记未核实。禁止通过提高推理强度补偿设计缺口。配置无法确认时报告阻塞。[模型与定价](https://api-docs.deepseek.com/quick_start/pricing/) · [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

## 10. 总索引与状态总览

SR 总索引列出所有 SR 的 ID、标题、设计基线、状态、依赖和实施入口；实施状态总览按状态统计并展示阶段、阻塞和验收证据。两份总览是汇总视图，每个 SR 文件是单项权威记录。状态变化先更新 SR 文件，再更新索引和总览。任何汇总不得将 NOT_RUN、NOT_VERIFIED、BLOCKED 推导成 PASS。

## 11. Demo 范围约束

本机制只使用 Markdown、GitHub Issue/PR 和现有测试证据。暂不引入专用需求管理平台、签名、额外 SHA-256、Trust Registry、生产审批流、复杂角色权限或生产级 DFX。基本版本记录、可追溯性、验收和错误可诊断性仍然必须具备。
