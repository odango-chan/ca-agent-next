## 1. 目标与基本原则

建立从设计到实施、再到验收的可追踪关系：

**IR → SR → PR/Commit → Acceptance 证据。** 架构、设计和规范关联 IR，SR 引用具体设计版本与章节。

1. 架构定义系统边界和约束；设计说明书定义机制方案；SR 定义可独立实施和验收的需求单元。
2. [IR 总登记册](../IR/IR%20总登记册.md)定义要解决的问题、预期结果、协作入口和 SR 分解。SR 是实施范围的权威记录。
3. 每个 SR 必须引用明确的设计文档版本和章节、验收 ID、依赖及实施证据。
4. Harness 只能实施状态为 READY 且依赖满足的 SR，不得自行从设计文档推断或扩大实施范围。
5. 设计变更必须先分析影响，再决定复用、创建或替代 SR。
6. 不为 Demo 引入独立需求管理平台、生产级签名、哈希、Trust Registry 或复杂流程系统。

## 3. 文档版本与修订记录

### 3.1 文档版本

每份正式文档必须包含文档版本。新草案可从 0.1.0 起步；各文件独立演进，正式评审确认后可建立 1.0.0 基线。

采用三段式版本：

- 主版本：架构边界、公共契约或核心行为发生不兼容变化。
- 次版本：新增或改变设计行为、接口语义或验收要求。
- 修订版本：文字、排版、链接和不改变需求/验收语义的澄清。

版本表达文档自身变化，不代替 SR 编号，也不表示实现完成。

### 3.2 修订记录

每份正式架构、设计、规范、治理、验收和审计文档必须有“修订记录”章节。每次刷新都追加记录，不覆盖旧行。

| 字段 | 要求 |
|---|---|
| 日期 | YYYY-MM-DD |
| 版本 | 本次文档版本 |
| 修订内容 | 实际变化摘要 |
| 原因 | 为什么需要变化 |
| 影响 SR | 受影响 SR ID；纯编辑填写“无（不影响需求）” |

Git 历史记录具体文件差异；修订记录说明设计意图和需求影响。README.md、Agent.md 等入口文件由 Git 历史管理，不强制增加独立修订表。

## 4. SR 编号与文件格式

- 本仓沿用已有 SR-001，后续使用 SR-002、SR-003……递增；编号全局唯一、永久不复用。
- 文件格式：SR-001-中文主题.md。
- SR ID 一经分配不得重新分配；取消或替代的 SR 仍保留原记录。
- 新需求使用新编号，不通过重命名旧 SR 表达变化。

IR 与 SR 使用独立编号空间，编号永久保留。每项 IR 可关联多个 Issue 并分解多个 SR，SR 至少回链一项 IR。

每份 SR 至少包含：上游 IR、ID、标题、SR 版本、状态、创建日期、设计依据（文档版本与章节）、目标、范围、非目标、依赖、验收条件、Issue/PR/Commit、测试证据、替代关系和修订记录。

SR 记录需求本身，不复制设计说明书的完整方案和规范字段表。

## 5. SR 分解原则

- 一个设计说明书可以分解为多个 SR；一个 SR 可以引用多份设计说明书或规范。
- 按独立实现责任、依赖和验收边界拆分，不按文档章节机械拆分。
- 一个 SR 可以关联多个 Issue/PR/Commit；一个 PR 也可以实现多个紧密相关的 SR，但必须逐项报告验收结果。
- 纯设计讨论、尚未定案的选项不创建 READY SR。
- ca-agent-next 是项目群的统一任务入口。修改任一协作仓前，在 `docs/SR/` 登记或引用已明确覆盖该改动的 SR。消费侧 SR 仅凭依赖引用不足以启动目标仓改动。

## 6. SR 状态与转换

| 状态 | 含义 | 进入条件 |
|---|---|---|
| DRAFT | 草案，尚不可实施 | 设计基线待评审，或范围/依赖/验收条件尚未确认 |
| READY | 本 SR 自身已具备实施条件 | 设计已评审确认；范围、责任、依赖和模块 AC 完整，依赖已按阶段分类；实际启动仍须通过当前阶段实施门禁 |
| IN_PROGRESS | 正在实施 | 已开始代码/配置/测试工作，并记录实施关联 |
| IMPLEMENTED | 实施已集成 | 代码已进入指定目标分支或正式集成基线；验收尚未全部通过 |
| VERIFIED | 验收通过 | 所有必需验收条件有真实证据且结果满足 SR |
| BLOCKED | 当前 SR/阶段明确阻塞 | 当前需要执行的范围整体被直接依赖、环境或决策阻塞，并记录解除条件；不连带阻塞无关 SR/AC |
| SUPERSEDED | 被新 SR 替代 | 新 SR 明确声明 supersedes，并保留旧记录 |
| CANCELLED | 已取消 | 有明确取消原因和决策依据 |

正常路径为 DRAFT → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED。READY/IN_PROGRESS/IMPLEMENTED 可因真实阻塞转为 BLOCKED；解除后回到原适用状态。SUPERSEDED 和 CANCELLED 为终态。

**IMPLEMENTED 不等于 VERIFIED。** PR 合并只证明代码集成，不自动证明验收通过。未运行测试标记 NOT_RUN；外部依赖未满足标记 BLOCKED 或 NOT_VERIFIED，不得推测 PASS。

### 6.1 依赖类型与阶段门禁

SR 的依赖必须分类记录，不得只写无类型的“依赖某 SR”。每条依赖至少说明：提供方 SR/契约及固定版本、消费方阶段或 Acceptance ID、所需证据、阻塞范围和解除条件。

| 依赖类型 | 约束对象 | 是否阻塞设计评审 / READY | 何时阻塞 |
|---|---|---|---|
| 设计依赖 | 设计输入、接口和决策 | 是；只有所需设计输入尚未冻结或存在冲突时才阻塞 | 消费方无法在稳定契约上完成设计时 |
| 实施依赖 | 运行时能力、代码或发布物 | 否；稳定的公开契约足以支持设计评审 | 仅在启动实际消费该能力的实现阶段时 |
| 模块验收依赖 | 某个 AC 所需的上游证据 | 否；不阻塞无关 AC | 仅在执行明确依赖该证据的 AC 时 |
| 系统集成依赖 | 多个模块组合形成的 EX | 否；系统 EX 不作为单个模块 SR 的默认门禁 | 仅在执行该 EX 时，按其列明的模块验收证据检查 |

执行规则：

1. **依赖只阻塞实际消费它的阶段或 AC。** 不得仅凭功能树阶段顺序、文档互相引用、共享接口、同一 IR 或兄弟 SR 关系推断新的前置依赖。
2. **设计评审与 READY 独立判断。** 只要本 SR 的设计、范围、责任和模块 AC 完整，且设计依赖已有稳定权威契约，便可评审并转 READY；下游实施依赖未完成不阻塞设计评审或 READY。
3. **实施启动单独检查实施依赖。** 启动代码前只检查本次实施范围直接消费的实施依赖。依赖未满足时，只暂停受影响的阶段/任务；若 SR 仍有独立可执行范围，保持 READY 并记录阶段等待项；若整个当前 SR 范围均无法推进，才转 BLOCKED。
4. **模块 AC 独立执行。** 本模块实现完成且该 AC 自身依赖满足后即可执行；不得要求无关 SR 完成，也不得要求系统级 EX 先 PASS。
5. **系统 EX 只负责集成验收。** EX 按其声明的 SR/AC 证据执行；不得反向成为单个模块 SR 的 READY、代码实施或模块 AC 前置条件。
6. **禁止传递性扩大阻塞。** 某依赖未满足时，只阻塞直接消费它的 SR 阶段/AC；只有显式登记且可证明的下游依赖才继续受影响。

SR 文件应分别记录设计依赖、实施依赖、模块 AC 依赖和系统 EX 依赖。索引与 Goal 清单不得把这些类型折叠为一个全局“依赖未满足”。

## 7. 设计变更与 SR 影响分析

每次正式设计刷新，必须与上一个文档基线做差异分析：

| 变化类型 | 处理 |
|---|---|
| 纯文字、排版、链接、无语义澄清 | 更新文档修订记录；不创建新 SR |
| 新增独立行为或验收要求 | 创建新 SR |
| 改变既有 SR 的范围、行为、接口或验收条件 | 创建新 SR，填写 supersedes；旧 SR 标记 SUPERSEDED |
| 删除既有要求 | 形成取消/替代决策；旧 SR 标记 CANCELLED 或 SUPERSEDED，不删除历史 |
| 不影响既有 SR 的设计补充 | 保留 SR，更新设计依据版本和影响分析结论 |

影响分析必须检查既有 SR 是否仍然有效、哪些 SR 需要新增/替代/拆分/取消、哪些实施中任务需要暂停、哪些已实施需求需要回归验收，以及受影响的规范、Acceptance、Example、Harness 和跨仓消费者。

设计基线更新前先完成影响分析和 SR 关系更新；不得先实施再补追踪。

## 8. GitHub 与实施证据关联

- SR 文件是需求范围和验收条件的权威来源。
- 每批变更开始前必须创建或引用覆盖范围的 GitHub Issue，含文档、配置、测试、迁移和删除。纯治理或文档变更可只关联 Issue。实施 Issue 引用相关 IR、SR 和验收项。
- **设计/治理 Issue 与实施 Issue 分开。** 设计 Issue 追踪设计修订和评审；只有 SR 达到 READY 后，才创建独立实施 Issue，并在任何代码/配置实施开始前登记。不得把设计 Issue、设计 PR 当作实施授权或实施 Issue。
- 实施 PR 必须列出 IR/SR ID、实现范围、Commit 和逐项验收结果。Commit 可在提交说明中引用 SR，或由实施 PR 明确映射到 SR。验收记录包含 SR/Acceptance ID、受测 SHA、命令、环境、结果和证据位置。
- Commit、测试命令、测试输出和 Example 运行结果写回 SR 或对应验收记录。
- PR OPEN 只能证明工作进行中；PR MERGED 也不自动等于 VERIFIED。
- 进入 IN_PROGRESS 时必须记录实际实施 Issue；每份 PR 必须引用 Issue，每个 Commit 通过 PR 或提交正文追溯。跨仓 PR 使用完整 Issue 链接。
- 外部仓库 PR/Issue 只能记录为依赖证据，不能当作 Next SR 的实施完成证据。

### 8.1 跨仓任务

1. 从 [功能树与需求追踪基线](../治理/功能树与需求追踪基线.md) 定位权威仓。在 Next 选择或登记 IR，创建或引用覆盖本次变更的 SR。每个 SR 指定一个实施仓。涉及多个仓时按仓拆分 SR，由同一 IR 和依赖关系串联。
2. SR 记录完整仓名、基线分支及 SHA、变更范围、设计与契约、依赖和验收。已有范围足够的 SR 可复用。明确目标和依赖且经评审达到 READY 后，在目标仓实施。
3. 目标仓 Issue 和 PR 引用 Next SR 链接，Next SR 回填目标仓 PR、实施提交、测试命令、环境及结果。跨仓实现验收和 Next 集成验收分别取证，按各 SR 独立关闭。
4. 对协作仓的修改权限适用于已登记并符合实施门槛的任务。合并、发布及直接改受保护分支遵循各仓规则与明确授权。

### 8.2 使用评审中的固定提交开展受限实施

当规范或设计需要借助实施证据完成评审时，负责人可以批准使用未合并的规范或设计提交。SR 须按阶段登记目标仓、规范或设计 PR 与完整 SHA、批准人及记录、允许的改动和环境、Acceptance ID、退出条件及明确排除项。

§8.2 是例外路径，不是常规 READY 门禁的替代品，也不能用于绕过缺失的设计、范围或验收契约。只有当某项设计判断确实需要一个可隔离、可回滚的实现证据时才可使用；不得以广泛代码实施代替正常设计评审，也不得仅凭受限阶段的 PASS 宣称正式基线已完成。Harness 从登记的 SHA 读取规范；PR 更新后，仍使用原固定 SHA，除非重新确认差异、影响和适用验收并更新 SR。

READY 可以针对获批阶段。该阶段须独立具备实施条件和目标仓授权。PoC、实现验证和评审证据可先提交到分支或 PR。依赖正式规范、发布资产、主分支可达链接或生产资格的阶段，继续遵守各自的明确门槛。候选规范上的通过结果记录为候选 SHA 证据。正式基线改变时按差异复验，正式符合性和集成状态依据正式基线及对应验收证据。

审查未合并方案时，记录证据能支持哪些决定、尚需哪些验证，以及暂停或回滚条件。合并、发布与跨仓写入授权分别按现行规则处理。

### 8.3 正式评审结果必须持久化到 GitHub

凡是用于确认设计/架构/实现质量、关闭评审问题、改变 SR 阶段或生成实施 Goal 的**正式独立评审**，必须在 GitHub 留存可追溯的正式结果。仅存在于 ChatGPT/DeepSeek 对话、终端输出、临时文件或口头结论中的评审，均视为**未完成**；不得据此变更 SR 状态、登记 READY、创建实施 Issue 或交付实施 Goal。

1. **默认最新并固定本轮评审快照。** 每轮独立评审开始时，默认读取当时 PR 的最新 Head 与 Base，记录完整 40 位 SHA、PR 状态、目标分支、评审范围、轮次和开始时间，作为本轮不可变 Review Snapshot。新一轮默认重新读取最新版本，无需因普通 Head 前进逐次向用户申请确认。评审内容必须从该 Snapshot 读取，不能混用后续提交；每份报告必须注明完整 Head/Base。PR 在评审期间继续新增 Commit 不构成阻塞：只要 Base 未变化、PR 仍为 OPEN，且原 Snapshot 仍是当前 PR Head 的祖先/仍属于该 PR 提交历史，就继续评审原 Snapshot。只有 Base 改变、PR 关闭或合并，或 force-push/历史改写使 Snapshot 不再属于该 PR 历史时，才暂停尚未开始的评审；不得自动漂移到新 SHA，应建立新评审轮次并捕获最新快照。GitHub inline comment 必须绑定实际评审 Snapshot；若平台不允许对该快照定位，记录 `INLINE_COMMENT_NOT_RECORDED`，不得静默改绑最新 Head。已完成的评审结论继续绑定其原始 Snapshot，不因后续提交自动重评或改写。
2. **提交正式 GitHub 记录。** 对 PR 评审，使用 GitHub Pull Request Review 提交 `APPROVE`、`REQUEST_CHANGES` 或 `COMMENT`，并在 Review body 中写完整结论；若报告过长，可将完整报告放在独立归档 PR/分支或 GitHub 可访问的不可变文件中，Review body 必须包含摘要、完整报告链接及其归档 SHA。无 PR 的评审写入对应 GitHub Issue 评论。必须给出实际 GitHub Review/Comment URL 或 ID。
3. **逐项可审计。** 报告至少包含评审者身份/模型、时间、完整被评审 SHA、Base SHA、范围、总体结论，以及每个 SR/阶段/AC 的结论、获批范围、未通过/未运行 AC、P0/P1/P2 发现、证据位置、直接依赖、责任仓/Owner、解除条件和是否允许进入 READY。不能用总评替代逐 SR 结论；`NOT_RUN`、`NOT_VERIFIED`、`BLOCKED_EXTERNAL_INPUT` 不得写成 PASS。
**独立性判定以评审模型和评审上下文为准，不以 GitHub 登录账号是否与 PR 作者相同为准。** 本项目允许用户保证由不同模型承担作者与独立评审；报告必须记录实际评审模型/版本、评审任务和固定 SHA。相同 GitHub 账号不构成否定独立性的理由，也不得仅因账号相同把模型评审降格为作者自评。

模型评审结论与 GitHub Review event 是两个独立字段。模型认为整个 PR 可批准时，应尝试提交 `APPROVE`；若 GitHub 因 PR 作者账号规则拒绝该事件，则以 `COMMENT` 提交完整评审报告，并在报告中明确记录模型结论（例如 `APPROVE_FOR_READY` 或 PR 级批准建议）及平台实际接受的 event=`COMMENT`。该记录仍是独立模型评审，不得称为作者自评；但不得声称 GitHub 已产生 `APPROVED` 状态。若平台接受 `APPROVE`，按实际返回记录。严禁伪造其他账号或虚报 Review 状态。

4. **正确记录模型结论与 GitHub Review event。** 模型级评审结论和 GitHub event 分开记录。模型认为当前 PR 变更范围整体满足评审目标时，尝试 `APPROVE`；存在需修订的 P0/P1 时使用 `REQUEST_CHANGES`；仅部分范围获批、外部输入阻塞或结论混合时使用 `COMMENT`。若 GitHub 因 PR 作者账号规则拒绝 `APPROVE`，必须以 `COMMENT` 提交完整报告，并同时记录模型级结论与平台 event；该记录仍是独立模型评审，不得称为作者自评，也不得声称平台已产生 `APPROVED`。同一 GitHub 账号不构成模型评审不独立的理由；严禁伪造其他账号或虚报 Review 状态。
5. **行内问题定位。** 能定位到变更文件和行的发现，必须使用 GitHub Review inline comment 指向实际 diff 行；Review body 保留发现汇总和逐 SR 矩阵。不要用无法定位的泛泛评论代替具体问题。
6. **评审报告与被评审基线分离。** 不得为了保存评审报告而向正在被评审的 Head/分支追加提交，否则会改变评审对象。优先将完整报告写入 GitHub Review body；确需归档文件时，使用独立报告分支/PR，文件必须引用原评审 SHA，归档 PR 不得改变原评审分支。评审完成后若需更新 SR 状态、索引或回填报告链接，另建后续治理提交/PR，明确引用已提交的 Review URL 和原评审 SHA。
7. **权限或服务失败。** 如果无法提交 GitHub Review，至少尝试在对应 PR/Issue 留下完整评论并说明无法提交 Review 的原因。若两种方式都失败，明确标记 `REVIEW_NOT_RECORDED`，保留本地报告但不得声称评审完成；在 GitHub 留存成功前不得推进 SR 状态或实施门禁。
8. **报告发现与后续修订闭环。** 每个发现必须有唯一编号或稳定引用；修订 PR/Commit 应回链原 Review/Comment，并逐项说明修复或不采纳理由。评审者复核修订后再次在 GitHub 提交新 Review，绑定新 Head。SR 状态更新必须在评审记录成功持久化之后进行，并同步 SR 文件、总索引和实施状态总览。

GitHub Review 的状态只表达对该 PR 变更的审查结果；`APPROVE_FOR_READY` 是 SR/阶段的设计结论，两者不可互相替代。PR 已获 APPROVE 也不代表产品 AC、系统 EX/OM 或外部 Release 已 PASS。

## 9. DeepSeek Harness Goal 与交付门禁

1. 默认使用 Goal 模式。一个 Goal 覆盖同一功能子树或同一端到端能力，可合并多个 READY 且当前实施门禁已满足的 SR。先按**实施依赖**拓扑排序，同层按功能树与交付顺序排列；设计评审不受未完成的实施依赖阻塞。某个 SR/AC 的依赖未满足时，只将该消费者留在候选清单或暂停，不得连带阻塞仍独立且门禁已满足的 SR/AC。使用 §8.2 的分阶段 READY 时，Goal 只纳入获批阶段。循环依赖、冲突或缺失的直接依赖证据须先处理。
2. Goal 清单固定设计 ref/SHA、功能节点、范围与非目标、授权仓库和分支、关联实施 Issue、逐 SR 执行顺序、分类型依赖证据、Acceptance ID、命令及预期结果、停止与恢复条件。长时间运行或多工作项 Goal 还必须按 §9.1 在实质性工作开始前建立并核验 GitHub 检查点。开始前及每个 SR 启动前复核 READY、当前阶段实施依赖和仓库状态。
3. 生成、交付执行提示词前，相关文档须通过[文档交付门禁](文档编写与治理规范.md#13-执行提示词交付门禁)。草稿和预检材料仅用于核查。静态结果与真实模型执行分别记录。
4. 执行中遇到设计冲突、契约不明、权限缺失或验收失败，停止该 SR 和受影响的后继 SR。只有明确独立且仍满足条件的已列 SR 可继续。保留已通过证据，逐项记录 FAIL、BLOCKED 或 NOT_RUN、原因、证据和首个安全恢复步骤；恢复时按 §9.2 从 GitHub 检查点读取进度，验证固定快照仍属于目标 PR 历史、Base 未变化及直接依赖仍满足。PR Head 正常前进不要求改用新快照。
5. 每个 SR 回填设计 Issue、实施 Issue、PR、Commit、受测 SHA、环境、Acceptance ID、命令、预期与实际结果及证据位置，再更新 SR 总索引和实施状态总览。每个实现批次必须形成可追溯 Commit 并 Push 到远端分支；Push 后核对远端 ref SHA 与预期提交一致。未确认远端更新不得报告已推送。PR 合并不自动关闭实施 Issue；只有全部必需模块 AC 有真实证据并达到 VERIFIED 后才关闭实施 Issue/Goal。不得未经单独授权合并 PR、发布 Release 或写入 main。
6. Flash 为动态配置。当前官方推荐 `deepseek-flash`，默认显式发送 `low`（Chat Completions 的 `reasoning_effort`、Responses API 的 `reasoning.effort`、Anthropic 格式的 `output_config.effort`）。每次记录时间、接口、发送的别名与实际参数、返回的模型标识和可核实的解析版本；无法确认的字段标记未核实。禁止通过提高推理强度补偿设计缺口。配置无法确认时报告阻塞。[模型与定价](https://api-docs.deepseek.com/quick_start/pricing/) · [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

### 9.1 长时间运行 Goal 的启动检查点与进度持久化

长时间运行、多阶段、多 SR、多仓库或预计可能跨上下文/执行会话的 Goal，必须在开始任何实质性工作前建立 GitHub 可恢复检查点。短小、一次性且无需跨步骤恢复的问答不要求额外创建检查点。

1. **创建或复用追踪 Issue。** 优先复用已覆盖本任务范围的中央 Issue；已有检查点时更新，不重复创建 Issue。没有合适 Issue 时，先创建任务 Issue，并回链父 Issue、相关 SR/PR。
2. **写入检查点。** 至少记录以下字段：

   | 字段 | 要求 |
   |---|---|
   | Task ID | 稳定任务标识；可使用 Issue 编号 |
   | Goal / Parent | 当前 Goal 名称或引用、父 Goal/父 Issue |
   | Repository / Branch | 目标仓库、目标分支 |
   | Start Ref | 开始时目标分支/提交的完整 SHA |
   | Review Snapshot | 适用时记录完整 Head 与 Base SHA |
   | Scope | 本次范围、非目标和授权边界 |
   | Work Items | 有序工作项及各自状态 |
   | Completed | 已完成项及可访问证据链接 |
   | In Progress | 当前工作项和已完成子步骤 |
   | Blocked | 阻塞原因、影响范围、责任方和解除条件 |
   | Not Started | 尚未开始的工作项 |
   | Next Action | 唯一、明确、可执行的下一步 |
   | Acceptance | 验收条件、命令和结果 |
   | Last Checkpoint | 最近一次持久化更新时间 |

3. **写入后重新读取核验。** 必须重新读取 GitHub Issue，确认任务范围、基线、工作项和 Next Action 已完整保存。若创建/更新失败或读回不一致，停止实质性工作并报告 `CHECKPOINT_NOT_ESTABLISHED`；不得先大量执行再补写。
4. **执行期间增量更新。** 每完成一个独立工作项，立即更新检查点并核验；开始长时间操作、切换仓库/分支、遇到阻塞或变更范围前，也先持久化当前状态。Commit/Push 任务必须记录并核验远端 SHA。
5. **状态词汇固定。** 工作项只使用 `NOT_STARTED`、`IN_PROGRESS`、`COMPLETED`、`BLOCKED`、`SUPERSEDED`。只有交付证据已持久化且验收条件满足时才可标记 `COMPLETED`；部分完成不得冒充完成；`SUPERSEDED` 必须链接替代任务，不删除历史。
6. **GitHub 是进度权威。** Goal 对话、模型上下文、终端输出和临时文件不能作为唯一进度存储。GitHub Issue/PR/Commit/验收证据是恢复时的权威依据。

### 9.2 Goal 中断后的恢复与续跑

Goal 因上下文耗尽、执行环境退出、用户切换会话或进入 BLOCKED 而中断时，按以下顺序处理：

1. 先读取中央追踪 Issue 和相关子 Issue，核对最后一个已验证检查点；不得仅根据旧对话或模型记忆推测进度。
2. 若原 Goal 在执行平台仍可恢复，优先恢复原 Goal，保留原执行历史和任务身份。
3. 若原 Goal 不可恢复，创建**续跑 Goal**，明确关联原 Goal、父 Issue、中央追踪 Issue、已完成子任务和当前 Review Snapshot。续跑 Goal 只处理未完成/未开始工作项，不重启整批，不创建重复实施或评审任务。
4. 只有检查点中具有 GitHub 可访问交付证据的工作项才视为已完成。已完成项不重复执行；部分完成项从其最后一个已验证子步骤继续；阻塞项记录解除条件，但不得阻止无直接依赖关系的工作项。
5. 恢复后必须写回新的 `In Progress`、`Blocked` 和唯一 `Next Action`，重新读取核验，再继续执行。原范围、权限和基线未发生实质变化时，不要求重复向用户索取已明确授予的授权；如范围、目标仓、权限或 Base 改变，先暂停并请求必要决策。

### 9.3 批量评审的快照与逐项推进

1. 新一轮评审默认读取目标 PR 当时最新 Head/Base，并将完整 SHA 固定为该轮 Review Snapshot；同一轮所有独立 SR 共用该快照，除非任务明确划分不同快照批次。
2. 评审期间 PR 正常新增 Commit 时，只要 Base 未变化、PR 仍 OPEN 且快照仍是当前 Head 的祖先/属于 PR 历史，就继续评审快照，不要求冻结分支或重新开始。
3. Base 改变、PR 关闭/合并或快照脱离 PR 历史时，暂停尚未开始的评审；不得自动漂移到新快照。建立新轮次时重新捕获最新 Head/Base，并说明旧轮次已完成和未完成项。
4. 每个 SR 独立评审、独立留痕。完成一项后先将报告写入对应 GitHub Issue、提交必要的 PR Review/Inline Comment、核验 URL/ID，再更新中央检查点并继续下一项。一个 SR 的 `CHANGES_REQUESTED` 或 `BLOCKED_EXTERNAL_INPUT` 只阻塞其自身及已证明的直接依赖。
5. 已完成评审始终保留原报告和原快照，不得改写成使用新快照；只有明确开启新一轮复评才重新评审。

## 10. 总索引与状态总览

SR 总索引列出所有 SR 的 ID、标题、设计基线、状态、依赖和实施入口；实施状态总览按状态统计并展示阶段、阻塞和验收证据。长任务的 Goal/工作项进度由中央追踪 Issue 的检查点持久化；Goal 本身不是进度权威存储。两份总览是汇总视图，每个 SR 文件是单项权威记录。状态变化先更新 SR 文件，再更新索引和总览。任何汇总不得将 NOT_RUN、NOT_VERIFIED、BLOCKED 推导成 PASS。

## 11. Demo 范围约束

本机制只使用 Markdown、GitHub Issue/PR 和现有测试证据。暂不引入专用需求管理平台、签名、额外 SHA-256、Trust Registry、生产审批流、复杂角色权限或生产级 DFX。基本版本记录、可追溯性、验收和错误可诊断性仍然必须具备。

## 12. 证据默认自动归档与上传规则

根目录 [Agent.md §7](../../Agent.md#7-证据默认自动归档规则2026-11-27) 为任务入口。本节适用于所有实施任务、SR 验收、AC 验收、独立评审、整改和复验。除本节列明的例外，证据**默认自动**归档，不需要负责人逐次提醒或批准。

### 12.1 默认自动归档

1. 所有实施任务、SR 验收、AC 验收、独立评审、整改和复验产生的有效原始证据必须自动归档到对应 Issue。
2. 不需要负责人逐次提醒或批准。
3. 证据应在对应任务阶段完成后及时上传，不得等整个项目结束才集中归档。
4. 一个 AC 对应一组明确的证据，必须能够从 Issue 追溯到原始文件。
5. PR 必须链接对应 Issue 的证据归档评论。
6. 多轮复验应保留各轮固定 SHA、Run ID 和证据，不得覆盖旧证据。
7. 本地路径、终端截图和文字总结不能替代可访问的原始证据。
8. CI Artifact 应优先直接链接；必要时另行归档，避免重复上传大型文件。
9. 证据上传前必须进行敏感信息检查（Token、密码、Cookie、认证信息、个人路径等）；必要时脱敏并记录脱敏范围，且不得破坏证据间对比关系（如 A→B→A 的逐字一致性）。
10. 证据上传失败时，任务状态必须标记为 `EVIDENCE_PENDING`（或相应未完成状态），对应 AC 不得标记 PASS，SR 不得标记 VERIFIED。
11. 证据清单必须包含文件、AC、来源 SHA、测试命令、退出码和验证结果。
12. 不引入新的签名、Trust Registry、包完整性校验或生产级证据平台。

### 12.2 归档目标与格式

- 归档评论至少包含：固定受测 SHA、可访问的证据下载入口、文件数量与压缩大小、AC 与证据映射、已归档与未归档项、脱敏说明、独立复核入口。
- 归档包使用 `SR-<编号>_AC-<编号或清单索引>_<受测SHA前12位>_<运行标识>.zip`。CI 以 Run ID 和 attempt 组成运行标识（例如 `45955482682-a1`）；本地复验使用 UTC 时间戳及必要的轮次号。清单记录完整仓库、受测 SHA、运行标识、每个 AC 与包内原始相对路径。保留 CI 和文件原来的名字，直接链接无需改名。
- 打包附件上限为 20 MB（20,000,000 字节）；超过时按原序分卷，每卷不超过这一上限，文件名追加 `.part001`、`.part002` 等后缀。清单记录原包、分卷文件名、顺序、字节数及还原命令。
- 上传前按仓库、完整受测 SHA、Run ID/attempt 或本地运行标识、源路径查找既有归档。入口可访问且来源与清单一致时，其他 Issue/AC 或同轮重试直接引用原归档评论；同一 SHA 上的独立复跑保留新的运行标识。记录生成证据的实际命令、退出码及来源。缺任一必要来源时记录待补项并标记 `EVIDENCE_PENDING`。
- 仓库托管文件链接固定到完整提交 SHA，CI Artifact 记录 Run ID、attempt、Artifact 名称/ID 和保留期限；需要长期复核且唯一副本将到期时，在到期前将该副本移交到可持续下载的位置并回链原运行。
- GitHub 官方 REST API 当前不提供 Issue 附件上传能力。不得以附件文件名或本地路径冒充上传成功；无法上传真实附件时，必须在 Issue 评论中如实说明限制，并提供可访问的原始文件链接（如仓库证据分支或 CI Artifact），且发布后实际验证下载入口可访问。
- 归档评论发布后应实际打开下载入口，确认可访问并核对大小/摘要。

### 12.3 例外与边界

- 涉及未授权公开的敏感数据、他人个人信息或安全响应细节时，可暂不上传该部分，但必须将其标记为 `EVIDENCE_PENDING`，在 Issue 记录原因与受限位置，且不得据此将 AC 判 PASS。
- 纯设计文档评审结论按 §8.3 持久化；其原始证据同样遵循本节。
- 本节不改变 §8.3 的正式评审留存要求，也不替代各 SR 自身的 Acceptance 证据定义。
