## 1. 目标与基本原则

建立从变更到实施、再到验收的可追踪关系：

**变更批次 → Issue →（适用时 IR → SR）→ PR/Commit → Acceptance 证据。** Issue 是每次变更的强制协作入口；IR/SR 用于表达需求意图与可独立实施的需求，不要求纯文字或纯治理变更制造 SR。架构、设计和规范关联功能节点/IR，SR 引用具体设计文档版本与章节。

1. 总体架构定义系统级边界；领域/模块架构定义子系统结构；设计说明书定义机制方案；SR 定义可独立实施和验收的需求单元。
2. [IR 总登记册](../IR/IR%20总登记册.md)定义需求意图、预期结果和 SR 分解；GitHub Issue 是所有变更批次的强制入口。
3. 每个 SR 必须引用明确的功能节点、设计文档版本与章节、验收 ID、依赖及实施证据。
4. Harness 只能实施状态为 READY 且依赖满足的 SR，不得自行从设计文档推断或扩大实施范围。
5. 设计变更必须先分析影响，再决定复用、创建或替代 SR；纯编辑不创建无意义 SR，但仍必须关联 Issue。
6. 不为 Demo 引入独立需求管理平台、生产级签名、哈希、Trust Registry 或复杂流程系统。

## 2. 文档层级与存放位置

| 类型 | 目录 | 权威职责 |
|---|---|---|
| 架构设计 | docs/架构设计/ | 唯一总体架构，以及多份领域/子系统/模块架构；按功能树分层归档 |
| 设计说明书 | docs/设计说明书/ | 机制、接口行为、流程和错误处理 |
| 规范 | docs/规范/ | 格式、字段、协议和治理强制规则 |
| IR 登记册 | docs/IR/ | IR-NNN、需求意图、预期结果、Issue 链接和 SR 分解 |
| SR 记录 | docs/SR/ | 可独立实施的需求、验收条件和实施证据 |
| 文档治理 | docs/治理/ | 文档索引、SR 总索引、实施状态总览和变更影响 |
| 验收与实施 | docs/验收与实施/ | Demo Acceptance、实施阶段和 Harness 指令 |
| 参考与审计 | docs/参考与审计/ | 外部状态与复用证据，不作为本仓规范源 |

架构设计与设计说明书保持同级。总体架构全局只允许一份；领域、子系统和模块架构可以有多份，允许不同目录深度。功能节点与文档为多对多关系：一个节点可关联多篇架构/设计文档，一篇文档也可覆盖多个紧密关联节点。SR 不嵌入设计说明书，也不把 SR 正文复制到 GitHub Issue。

## 3. 文档版本与修订记录

### 3.1 文档版本

每份正式文档必须包含文档版本。新草案可从 0.1.0 起步；各文件独立演进，正式评审确认后可建立 1.0.0 基线。

采用三段式版本：

- 主版本：架构边界、公共契约或核心行为发生不兼容变化。
- 次版本：新增或改变设计行为、接口语义或验收要求。
- 修订版本：文字、排版、链接和不改变需求/验收语义的澄清。

版本表达文档自身变化，不代替 SR 编号，也不表示实现完成。

### 3.2 修订记录

每份正式架构、设计、规范、治理、验收和审计文档必须有“修订记录”章节。每次刷新都追加记录，不覆盖旧行。每份文档还必须声明其覆盖的功能树节点、上游来源（适用时记录外部仓库/Commit/原路径）及关联 Issue；有 IR/SR 时同时记录。

| 字段 | 要求 |
|---|---|
| 日期 | YYYY-MM-DD |
| 版本 | 本次文档版本 |
| 修订内容 | 实际变化摘要 |
| 原因 | 为什么需要变化 |
| 影响 SR | 受影响 SR ID；纯编辑填写“无（不影响需求）” |

Git 历史记录具体文件差异；修订记录说明设计意图和需求影响。README.md、Agent.md 等入口文件由 Git 历史管理，不强制增加独立修订表。

## 4. SR 编号与文件格式

- 本仓沿用已有 SR-001，后续使用 SR-002、SR-003……递增；编号全局唯一、永久不复用。
- 文件格式：SR-001-中文主题.md。
- SR ID 一经分配不得重新分配；取消或替代的 SR 仍保留原记录。
- 新需求使用新编号，不通过重命名旧 SR 表达变化。

IR 与 SR 使用独立编号空间，编号永久保留。每项 IR 可关联多个 Issue 并分解多个 SR，SR 至少回链一项 IR。

每份 SR 至少包含：上游 IR、ID、标题、SR 版本、状态、创建日期、设计依据（文档版本与章节）、目标、范围、非目标、依赖、验收条件、Issue/PR/Commit、测试证据、替代关系和修订记录。

SR 记录需求本身，不复制设计说明书的完整方案和规范字段表。

## 5. SR 分解原则

- 一个设计说明书可以分解为多个 SR；一个 SR 可以引用多份设计说明书或规范。
- 按独立实现责任、依赖和验收边界拆分，不按文档章节机械拆分。
- 一个 SR 可以关联多个 Issue/PR/Commit；一个 PR 也可以实现多个紧密相关的 SR，但必须逐项报告验收结果。
- 纯设计讨论、尚未定案的选项不创建 READY SR。
- ca-agent-next 是项目群的统一任务入口。修改任一协作仓前，在 `docs/SR/` 登记或引用已明确覆盖该改动的 SR。消费侧 SR 仅凭依赖引用不足以启动目标仓改动。

## 6. SR 状态与转换

| 状态 | 含义 | 进入条件 |
|---|---|---|
| DRAFT | 草案，尚不可实施 | 设计基线待评审，或范围/依赖/验收条件尚未确认 |
| READY | 已具备实施条件 | 设计已评审确认；范围、责任、依赖和验收条件完整 |
| IN_PROGRESS | 正在实施 | 已开始代码/配置/测试工作，并记录实施关联 |
| IMPLEMENTED | 实施已集成 | 代码已进入指定目标分支或正式集成基线；验收尚未全部通过 |
| VERIFIED | 验收通过 | 所有必需验收条件有真实证据且结果满足 SR |
| BLOCKED | 明确阻塞 | 存在外部依赖、环境或决策阻塞，并记录解除条件 |
| SUPERSEDED | 被新 SR 替代 | 新 SR 明确声明 supersedes，并保留旧记录 |
| CANCELLED | 已取消 | 有明确取消原因和决策依据 |

正常路径为 DRAFT → READY → IN_PROGRESS → IMPLEMENTED → VERIFIED。READY/IN_PROGRESS/IMPLEMENTED 可因真实阻塞转为 BLOCKED；解除后回到原适用状态。SUPERSEDED 和 CANCELLED 为终态。

**IMPLEMENTED 不等于 VERIFIED。** PR 合并只证明代码集成，不自动证明验收通过。未运行测试标记 NOT_RUN；外部依赖未满足标记 BLOCKED 或 NOT_VERIFIED，不得推测 PASS。

## 7. 设计变更与 SR 影响分析

每次正式设计刷新，必须与上一个文档基线做差异分析：

| 变化类型 | 处理 |
|---|---|
| 纯文字、排版、链接、无语义澄清 | 更新文档修订记录；不创建新 SR |
| 新增独立行为或验收要求 | 创建新 SR |
| 改变既有 SR 的范围、行为、接口或验收条件 | 创建新 SR，填写 supersedes；旧 SR 标记 SUPERSEDED |
| 删除既有要求 | 形成取消/替代决策；旧 SR 标记 CANCELLED 或 SUPERSEDED，不删除历史 |
| 不影响既有 SR 的设计补充 | 保留 SR，更新设计依据版本和影响分析结论 |

影响分析必须检查既有 SR 是否仍然有效、哪些 SR 需要新增/替代/拆分/取消、哪些实施中任务需要暂停、哪些已实施需求需要回归验收，以及受影响的规范、Acceptance、Example、Harness 和跨仓消费者。

设计基线更新前先完成影响分析和 SR 关系更新；不得先实施再补追踪。

## 8. GitHub 与实施证据关联

- SR 文件是需求范围和验收条件的权威来源；Issue 是每个变更批次的强制协作入口。
- **任何变更开始前必须存在覆盖本次变更的 GitHub Issue。** 范围包括架构/设计/规范文档、README/Agent.md、源码、配置、Schema、测试、CI/CD、依赖升级、文档迁移、删除、重命名、重构和缺陷修复。没有 Issue 不得先改后补。
- 一个 Issue 可以覆盖同一目标下的多份文件、多个紧密相关 SR 或多个 PR；一个 SR 也可以关联多个 Issue。Issue 必须明确列出所覆盖的仓库、功能节点、IR/SR（适用时）、范围、非目标和验收。范围变化先更新 Issue。
- 每个 PR 正文必须通过 `Refs #N`、`Closes #N` 等明确语法关联一个或多个 Issue；PR 所含 Commit 通过该 PR 追溯到 Issue。Commit message 建议包含 Issue 编号；禁止无 Issue 的孤立 PR/提交。
- 纯文字、格式、索引和治理刷新必须有关联 Issue，但如果不改变需求、行为或验收，不强制创建 IR/SR。新增/改变需求、行为、接口或验收时，必须同步更新 IR/SR。
- Issue 正文引用相关 IR；有 SR 时逐项列出 SR。PR 必须列出 IR/SR ID、实现范围、Commit 和逐项验收结果。验收记录包含 SR/Acceptance ID、受测 SHA、命令、环境、结果和证据位置。
- Commit、测试命令、测试输出和 Example 运行结果写回 SR 或对应验收记录；纯文档变更的检查结果写回 Issue/PR。
- PR OPEN 只能证明工作进行中；PR MERGED 也不自动等于 VERIFIED。Issue 的关闭必须依据其验收条件和交付状态。
- 外部仓库 PR/Issue 可以作为本次任务的实现入口，但必须链接到 Next 的中央 Issue；不能把外部 Issue/PR 自动当作 Next SR 的实施完成证据。

### 8.1 跨仓任务

1. 从 [功能树与需求追踪基线](../治理/功能树与需求追踪基线.md) 定位权威仓。在 Next 选择或登记 IR，创建或引用覆盖本次变更的 SR。每个 SR 指定一个实施仓。涉及多个仓时按仓拆分 SR，由同一 IR 和依赖关系串联。
2. SR 记录完整仓名、基线分支及 SHA、变更范围、设计与契约、依赖和验收。已有范围足够的 SR 可复用。明确目标和依赖且经评审达到 READY 后，在目标仓实施。
3. 目标仓 Issue 和 PR 引用 Next SR 链接，Next SR 回填目标仓 PR、实施提交、测试命令、环境及结果。跨仓实现验收和 Next 集成验收分别取证，按各 SR 独立关闭。
4. 对协作仓的修改权限适用于已登记并符合实施门槛的任务。合并、发布及直接改受保护分支遵循各仓规则与明确授权。

## 9. Harness 实施约束

1. 先确认覆盖本次变更的 GitHub Issue 已存在；再阅读 Agent.md、SR 管理规范、SR 总索引、目标 SR、对应的全部架构/设计文档、规范和 Acceptance。
2. 只执行状态为 READY 且依赖满足的 SR。文档执行资格默认使用 DeepSeek 最新 Flash alias `deepseek-flash`，并显式设置 `reasoning_effort=low`；具体记录方式以文档编写与治理规范为准。
3. 每个实施批次明确声明 SR ID、范围、非目标和 Acceptance ID；不得顺手扩展到其他 DRAFT SR。
4. 发现设计冲突、缺少验收条件或外部契约不明确时停止相关工作，提交差异和建议，不自行创造规范。
5. 实施中更新 SR 的 Issue/PR/Commit/测试证据和状态。
6. 代码集成后标记 IMPLEMENTED；只有全部验收条件有真实证据才标记 VERIFIED。
7. 每轮结束更新 SR 总索引和实施状态总览。

## 10. 总索引与状态总览

SR 总索引列出所有 SR 的 ID、标题、设计基线、状态、依赖和实施入口；实施状态总览按状态统计并展示阶段、阻塞和验收证据。两份总览是汇总视图，每个 SR 文件是单项权威记录。状态变化先更新 SR 文件，再更新索引和总览。任何汇总不得将 NOT_RUN、NOT_VERIFIED、BLOCKED 推导成 PASS。

## 11. Demo 范围约束

本机制只使用 Markdown、GitHub Issue/PR 和现有测试证据。暂不引入专用需求管理平台、签名、额外 SHA-256、Trust Registry、生产审批流、复杂角色权限或生产级 DFX。基本版本记录、可追溯性、验收和错误可诊断性仍然必须具备。
