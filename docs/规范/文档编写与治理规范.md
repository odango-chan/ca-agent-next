## 1. 基本原则

1. 本仓所有文档正文使用中文。协议名、字段名、API、代码符号、命令、文件名和必要的英文术语保留原文。
2. 项目级总体架构保持唯一；docs/架构设计/ 可另设领域、子系统与模块架构。架构和设计文档与功能树节点采用多对多映射，双向登记权威章节。
3. 详细机制由设计说明书承载；架构文档不得复制字段级契约、算法细节和完整状态机。
4. 架构设计目录与设计说明书目录在 docs 下同级，不把设计说明书嵌套在架构目录中。
5. 文件/字段/协议等强约束放在 docs/规范/；不得只写在 README 或设计说明书中。
6. README.md 和 Agent.md 只做入口与协作规则，不成为第二份架构文档。
7. 每个新增文档必须进入文档总目录，标明状态、权威来源和关联文档。
8. 所有文档都应去 AI 化。直接写清决策、依据、适用条件、行为和结果，保留读者理解与执行所需的细节。删去套话、空泛评价、重复总结、机械排比和无实质内容的标题。统一术语，核实事实、引用和示例，保留必要的来源、修订记录与真实验收证据。新增或修改文档时，提交前逐段检查本次改动。

| 文档类型 | 目录 | 主要职责 |

## 3. 文件命名与语言

- 普通文档文件名使用中文主题名，按类型使用“XXX 架构设计.md”“XXX 设计说明书.md”“XXX 规范.md”“XXX 验收基线.md”等；Plugin、Runtime、Artifact 等可翻译的词在文件名中优先使用中文。
- README.md、Agent.md 是仓库入口的固定名称。
- SKILL.md、plugin.yaml、contract.yaml、procedure.yaml、predicates.yaml、OpenAPI、代码文件、工作流文件和工具强制要求的名称不翻译。
- 不使用“新文档”“最终版2”“临时说明”等无法表达内容和状态的名称。
- 文档标题、表格说明、图注和叙述使用中文；代码示例、标准标识和接口字段保持精确原文。

## 4. 文档状态

每份文档开头必须说明状态。统一使用：

- 已确认：架构/契约决策已确认，仍需遵守。
- 待评审：已经形成完整提案，等待评审。
- 待决策：存在多个方案，尚未定案。
- 实现证据：记录真实代码、命令、测试和结果。
- 已废弃：被明确替代，不再作为实现依据。
- 历史参考：保留历史证据，不代表当前设计。

不得把“待评审设计”写成“已实现”，不得把单元测试 PASS 写成端到端 PASS，不得把 Demo 通过写成 Production Qualification。

## 5. 设计说明书编写规则

参考 env-openamsm/document/已完成 中成熟说明书的章节组织、决策摘录、场景分析、接口说明、实现差距和验收组织方式。Next 使用 Demo 精简版，不复制生产级 DFX 章节。

建议结构：

1. 文档元信息、状态、适用范围和权威依据。
2. 背景与目标。
3. 范围与非目标。
4. 设计原则与决策。
5. 总体设计和组件职责。
6. 接口、数据结构和契约引用。
7. 核心流程（必要时使用时序图/流程图）。
8. 状态与错误处理。
9. 配置和可运行示例。
10. 实现要求、外部依赖和未决事项。
11. 验收标准。
12. 修订记录。

按主题裁剪，不机械填满。字段级规范写在规范目录，设计说明书引用，不维护第二份规范。

## 6. 图表与示例

- 系统边界使用上下文图；组件关系使用组件图；跨进程交互使用时序图；条件分支使用流程图；状态变化使用状态图。
- 图中标明责任主体、消息方向、关键关联 ID 和错误路径。
- Mermaid 源与文档一起维护。
- YAML/JSON 示例必须与规范一致，标注其为规范示例、伪代码或真实实现证据。
- 示例中不允许重复 YAML key、虚构字段或与实际协议不一致的路径。

## 7. 需求—设计—实现—验收追踪

每项核心机制至少能追溯到：

IR → SR → PR/Commit → Acceptance。架构、设计与规范关联 IR，SR 引用设计版本和章节；Issue 承载协作。

SR 必须引用设计文档及其修订版本，并给出可验证的模块验收条件。每个 SR 使用稳定且不复用的 ID；SR 文件是需求范围权威来源，GitHub Issue 是每批变更的必需追踪入口。设计刷新时必须进行基线比较和 SR 影响分析：新增要求创建新 SR；改变既有范围、行为或验收条件时创建替代 SR 并保留旧记录；纯文字编辑不创建新 SR。Harness 只能实施 READY 且当前实施阶段的实施依赖满足的 SR；依赖类型和阻塞范围以《SR 管理规范》§6.1 为准。

追踪矩阵只记录必要的 ID、链接、状态和证据，不引入复杂需求管理平台。实现证据必须记录仓库、Commit/PR、测试命令、实际结果和覆盖范围。

## 8. 跨仓权威规则

ca-agent-next 统一维护项目群设计和规范；各实现仓维护代码、机器契约、发行、测试、运行和部署。外部标准与业务 Owner 的事实权威按各自契约保留。每项迁移固定原发布版本、中央章节和历史记录，在中央目标可用且对应 SR 达到 READY 后才替换重复正文。见[跨仓设计资产迁移与一致性审计](../参考与审计/跨仓设计资产迁移与一致性审计.md)。

## 9. 变更与废弃

架构边界变化更新唯一架构设计和索引；机制行为变化更新设计说明书；字段/接口变化更新规范并检查消费者；实现变化更新实现仓证据和验收结果。被替代文档先迁移有效内容，再标记废弃或归档，不直接删除唯一证据。

每次正式文档刷新都必须更新文档版本和修订记录，写明变化原因及影响 SR。纯文字、排版或链接修订记录“无（不影响需求）”，仅更新该文档及直接受影响的引用。涉及需求范围、行为、实施状态或验收变化时，完成 SR 影响分析，并按实际影响更新 SR 总索引、实施状态总览、Acceptance、Harness 指令和交叉链接。

## 10. Demo DFX 边界

可靠性与安全暂按 Demo 场景描述，不写生产级 HA/DR、SLA、签名、Trust Registry、生产密钥体系和复杂多租户方案。基本输入校验、路径边界、错误可诊断、fail-closed、状态语义正确、最小日志和自动化测试仍是功能要求。


## 11. 统一评审范围与规则

### 11.1 权威范围来源

项目级评审范围只在根目录 Agent.md 的 review_scope 区块维护。该区块使用固定 BEGIN/END 标记和版本化 YAML，作为 CI 提取的唯一权威来源。

- Agent.md 定义项目整体目标、必须范围、始终必须满足的正确性要求、非目标和评审策略。
- 本次 SR、PR 和 Acceptance 定义任务级范围；可以缩小全局范围，不得自行扩大。
- 架构设计定义总体边界；设计说明书定义机制行为；SR 定义可实施要求；Acceptance 定义通过条件和证据。
- 各文档只声明继承全局范围，并写明本文局部非目标，不复制完整全局范围。
- 依据冲突时停止并报告，不得由评审 Agent 自行创造第三套设计。

### 11.2 Demo 评审原则

评审必须严格检查当前承诺的目标，但不能把 Demo 评审扩大成生产级产品审计。

当前必须正确的内容包括：基本输入/Schema/版本/路径校验、明确错误、fail-closed、Runtime Capability/callable scope、Owner Receipt/Commit Proof、UNKNOWN、Continuation/Replay、二进制载荷保真、业务中立性，以及必需 Example 和 Acceptance。

生产级 HA/DR、SLA、容量规划、企业级 IAM/SSO、多租户治理、独立 Skill Admission、Owner Trust、Trust Registry、包签名、额外完整性体系、生产密钥管理、SIEM、Marketplace、自动下载、通用热更新、完整 3GPP 全量符合性和 Production Qualification 属于当前非目标。其缺失本身不得认定为当前缺陷或 P0/P1 阻塞。

如果某项非目标被认为是当前目标成立的必要条件，必须证明它阻断了哪个已声明目标或 Acceptance，标记 SCOPE_DECISION_REQUIRED，等待用户确认，不得擅自扩展范围。

### 11.3 问题分类与阻塞规则

| 分类 | 定义 | 默认处理 |
|---|---|---|
| BLOCKER | 有可复核证据证明违反当前必须要求、破坏核心架构边界或导致必需 Acceptance 无法通过 | 阻塞当前交付 |
| NON_BLOCKING | 属于当前范围，但不阻止本次目标或验收闭合 | 记录并安排处理 |
| OUT_OF_SCOPE | 属于 Agent.md 明确排除的能力，且没有证据证明其缺失阻断当前目标 | 不阻塞，不要求当前实施 |
| DEFERRED | 已明确留待后续阶段处理 | 记录后续阶段 |
| UNVERIFIED | 证据不足，暂时无法判断 | 保持未知，不得写 PASS 或确定缺陷 |
| SCOPE_DECISION_REQUIRED | 非目标与当前目标可能存在真实冲突，需要用户决定是否改变范围 | 暂停范围判断，不擅自升级为 BLOCKER |

BLOCKER 必须指出具体架构/设计/SR/Acceptance 要求、具体位置或设计矛盾、可复核证据以及对当前目标的实际影响。“生产环境通常需要”“最佳实践建议”或未来风险本身不足以构成 BLOCKER，也不足以单独构成 P0/P1。

### 11.4 每条评审发现的必填内容

每条发现必须包含：分类和适用时的优先级、对应架构/设计/SR/Acceptance 要求、具体文件/符号/行号、预期与实际行为、可复核证据、对当前目标的影响、处理建议和阻塞理由。证据不足标记 UNVERIFIED；必需测试未运行标记 NOT_RUN/BLOCKED，不得推断 PASS。

### 11.5 公共评审提示词

所有评审 Agent 使用同一原则。CI 生成完整提示词时，将本模板与 Agent.md 的 review_scope、本次 PR 变更文件和任务级 SR/Acceptance 组合。

~~~text
你是 CA Agent Next 的独立架构与实现评审 Agent。

开始前必须阅读 Agent.md、文档编写与治理规范、CI 生成的评审上下文（如存在）、本次任务的 SR/PR/Acceptance、对应架构和设计说明书，以及本次变更涉及的实现和测试。

严格遵守 Agent.md 的项目目标、必须范围、非目标和架构约束。本次任务范围可以更窄，不得自行扩大。默认只评审本次变更及其直接依赖。

必须检查当前目标路径、架构责任边界、接口和 Schema、状态转换、调用链、基本输入/路径校验、fail-closed、Runtime Action Boundary、Owner Receipt/Commit Proof、UNKNOWN、Continuation、二进制载荷保真，以及必需 Example/Acceptance。

对明确排除的生产级能力，不得因其缺失认定为当前缺陷、P0/P1 或阻塞。基本正确性要求仍必须严格检查。如果认为某项非目标阻断当前目标，标记 SCOPE_DECISION_REQUIRED，提供证据并等待用户确认。

每条发现必须引用具体要求，给出位置、可复核证据、实际影响、处理建议和阻塞判断。推测和最佳实践建议不能直接认定为缺陷。未运行测试不得标记 PASS。

分类：BLOCKER、NON_BLOCKING、OUT_OF_SCOPE、DEFERRED、UNVERIFIED、SCOPE_DECISION_REQUIRED。分类与 P0/P1/P2 优先级分开判断。

输出总体结论、评审范围、逐条发现、未验证项和明确非目标。评审目标是验证当前阶段承诺的目标是否正确实现，而不是把 Demo 改造成生产级平台。未经用户确认，不得修改项目范围。
~~~

### 11.6 CI 自动提取与生成

CI 从 Agent.md 的 BEGIN/END 标记中提取 YAML，不从普通段落猜测范围，不维护第二份项目级配置。校验后生成：

| 生成物 | 用途 |
|---|---|
| review-scope.json | 供 Harness 和其他自动化消费的标准化范围 |
| 评审上下文.md | 项目目标、必须范围、正确性要求、非目标、分类和本次变更文件 |
| 统一评审提示词.md | 公共评审提示词与项目范围、任务上下文的完整组合 |

生成物写入 Workflow 临时目录，不提交到源码仓库。PR Workflow Summary 展示摘要，并将生成物作为 Workflow Artifact 保存，供后续 Review Job 或人工交接使用。GitHub Actions Workflow Artifact 可保存工作流输出并在 Job 之间传递，参见 [官方文档](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts)。

如果仓库已有 AI Review Job，必须把生成物作为评审输入；如果评审由外部 Harness 发起，则由 Harness 下载 Artifact 后注入。CI 不能自动注入一个完全不与 CI 集成的外部 Agent。

CI 必须校验标记唯一性、YAML/Schema、必填字段、枚举、ID 唯一性、in_scope/non_goals 冲突和关键字段完整性。解析失败必须使检查失败，不得生成默认宽松范围。

如果 PR 修改 review_scope，CI 必须显式展示前后差异并要求用户/项目负责人审查；YAML 合法不代表范围变更自动获批。

CI 只负责解析、校验、生成和分发，不负责批准范围变更，不替代评审。SR-001 负责评审上下文的解析、校验、生成与交付。已有评审 Job 或外部 Harness 可消费生成物，新增模型调用工作流须另行定义。

### 11.7 正式文档范围声明

新增或本次修改的正式架构、设计说明书、SR、验收和决策文档，头部必须简短声明：

~~~markdown
> 全局评审范围：继承根目录 Agent.md 的 review_scope。
> 本文局部非目标：无；如有特殊排除项，在此列明。
~~~

不在每份文档复制完整非目标清单。存量文档按收敛计划逐步迁移，不一次性制造无关阻塞。

## 12. SR 管理与文档版本规则

SR 编号、字段、状态转换、GitHub 关联、依赖分类和 Harness 执行规则以[SR 管理规范](SR%20管理规范.md)为唯一权威，尤其遵守 §6.1 的阶段门禁和 AC/EX 分层。SR 记录存放于 docs/SR/；总索引和实施状态总览存放于 docs/治理/。

正式文档采用三段式版本：主版本表示不兼容边界变化，次版本表示新增/改变设计行为或验收要求，修订版本表示不改变需求语义的澄清。待评审基线使用 0.x；评审确认后建立 1.0.0。每次刷新必须追加修订记录，不得覆盖历史。


## 13. 执行提示词交付门禁

- 固定相关文档及来源的 ref/SHA，检查 Markdown 结构、仓内路径及锚点、外部依据、版本与修订记录、索引数量和状态、功能树映射及 Issue/SR/Acceptance 追踪。
- 执行提示词必须明确实施 Issue、目标仓、基线分支与 SHA、实施分支命名、设计 ref/SHA、分类型依赖、逐项 AC、系统 EX 的排除/后置条件、停止条件，以及 Commit + Push 和远端 SHA 核对要求；不得把设计 Issue 当作实施 Issue。
- 对照架构、详细设计、规范、SR、接口与外部发布契约完成一致性检查。逐项确认目标、范围、非目标、职责、接口及 Schema、数据/状态/流程/异常、实施仓及代码位置、步骤、命令、预期结果、验收证据和冲突停止条件齐备。
- 将上述检查结果和所需审查结论绑定到同一设计 SHA，记录审查来源、未解决项和证据。缺项、未审查、必需检查失败或依据发生变化时暂停生成与交付，修复后重验。真实 Harness 执行另行记录，未运行记为 NOT_RUN。

## 14. 分支命名与生命周期

分支使用 `<type>/issue-<本仓编号>[-sr-<数字>]-<slug>`。slug 仅用小写 ASCII 字母、数字及单连字符，使用有意义的动作或对象；SR 段可标主 SR（多 SR 在 PR 正文列齐）。`release` 可用版本号 slug（如 `release/issue-32-v1-2-0`）。

| 类型 | 用途 | 示例 |
|---|---|---|
| feature | 新功能 | `feature/issue-24-sr-004-import-skill-bundle` |
| fix | 常规缺陷修复 | `fix/issue-25-validate-request-schema` |
| docs | 文档或治理 | `docs/issue-5-central-governance` |
| refactor | 保持外部行为的重构 | `refactor/issue-26-simplify-resolver` |
| test | 独立测试变更 | `test/issue-27-add-bundle-fixtures` |
| chore | 构建、依赖或维护 | `chore/issue-28-update-ci` |
| release | 发布准备 | `release/issue-32-v1-2-0` |
| hotfix | 紧急修补已发布版本 | `hotfix/issue-33-restore-bundle-import` |

跨仓任务在每仓使用本仓 Issue 编号，PR 引用本仓 Issue、Next SR 与中央追踪 Issue 的完整链接。从最新目标基线创建短期分支；发布维护与 hotfix 从对应维护分支或发布标签派生，按维护关系回移修复。PR 记录 Issue、SR、基线、提交与验收证据；合并或废弃且后继分支完成迁移后清理分支。已存在的评审分支保留原名。禁止无语义、仅日期或人名的随意命名。主干与受保护维护分支通过 PR、要求的审查及 CI 更新，禁止直接推送、强推或绕过保护。
