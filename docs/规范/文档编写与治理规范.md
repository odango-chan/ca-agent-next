# 文档编写与治理规范

> 文档类型：仓库级规范  
> 状态：本轮文档收敛基线，待 PR #1 评审  
> 修订日期：2026-11-25  
> 适用范围：ca-agent-next 全部架构、设计、规范、治理、验收和审计文档

## 1. 基本原则

1. 本仓所有文档正文使用中文。协议名、字段名、API、代码符号、命令、文件名和必要的英文术语保留原文。
2. 总体架构文档只能有一份，放在 docs/架构设计/。
3. 详细机制由设计说明书承载；架构文档不得复制字段级契约、算法细节和完整状态机。
4. 架构设计目录与设计说明书目录在 docs 下同级，不把设计说明书嵌套在架构目录中。
5. 文件/字段/协议等强约束放在 docs/规范/；不得只写在 README 或设计说明书中。
6. README.md 和 Agent.md 只做入口与协作规则，不成为第二份架构文档。
7. 每个新增文档必须进入文档总目录，标明状态、权威来源和关联文档。

## 2. 文档分类与目录

| 文档类型 | 目录 | 主要职责 |
|---|---|---|
| 总体架构 | docs/架构设计/ | 目标、边界、组件、主要流程、仓库职责和关键约束 |
| 设计说明书 | docs/设计说明书/ | 机制背景、组件责任、接口行为、流程、异常、实现要求和验收 |
| 规范 | docs/规范/ | 文件结构、字段、格式、协议、公共契约和命名等强制规则 |
| 决策记录 | docs/决策记录/ | 重大决策的背景、选项、结论、影响和变更历史；当前阶段不强制拆成多份 ADR |
| 文档治理 | docs/治理/ | 文档总目录、状态台账、收敛计划和跨仓权威关系 |
| 验收与实施 | docs/验收与实施/ | Demo 验收基线、实施阶段、Harness 提示词和执行结果 |
| 参考与审计 | docs/参考与审计/ | 代码复用审计、跨仓依赖、外部证据和历史分析；不作为规范源 |

## 3. 文件命名与语言

- 普通文档文件名使用中文主题名，按类型使用“XXX 架构设计.md”“XXX 设计说明书.md”“XXX 规范.md”“XXX 验收基线.md”等。
- README.md、Agent.md 是仓库入口的固定名称。
- SKILL.md、plugin.yaml、contract.yaml、procedure.yaml、predicates.yaml、OpenAPI、代码文件、工作流文件和工具强制要求的名称不翻译。
- 不使用“新文档”“最终版2”“临时说明”等无法表达内容和状态的名称。
- 文档标题、表格说明、图注和叙述使用中文；代码示例、标准标识和接口字段保持精确原文。

## 4. 文档状态

每份文档开头必须说明状态。统一使用：

- 已确认：架构/契约决策已确认，仍需遵守。
- 待评审：已经形成完整提案，等待评审。
- 待决策：存在多个方案，尚未定案。
- 实现证据：记录真实代码、命令、测试和结果。
- 已废弃：被明确替代，不再作为实现依据。
- 历史参考：保留历史证据，不代表当前设计。

不得把“待评审设计”写成“已实现”，不得把单元测试 PASS 写成端到端 PASS，不得把 Demo 通过写成 Production Qualification。

## 5. 设计说明书编写规则

参考 env-openamsm/document/已完成 中成熟说明书的章节组织、决策摘录、场景分析、接口说明、实现差距和验收组织方式。Next 使用 Demo 精简版，不复制生产级 DFX 章节。

建议结构：

1. 文档元信息、状态、适用范围和权威依据。
2. 背景与目标。
3. 范围与非目标。
4. 设计原则与决策。
5. 总体设计和组件职责。
6. 接口、数据结构和契约引用。
7. 核心流程（必要时使用时序图/流程图）。
8. 状态与错误处理。
9. 配置和可运行示例。
10. 实现要求、外部依赖和未决事项。
11. 验收标准。
12. 修订记录。

按主题裁剪，不机械填满。字段级规范写在规范目录，设计说明书引用，不维护第二份规范。

## 6. 图表与示例

- 系统边界使用上下文图；组件关系使用组件图；跨进程交互使用时序图；条件分支使用流程图；状态变化使用状态图。
- 图中标明责任主体、消息方向、关键关联 ID 和错误路径。
- Mermaid 源与文档一起维护。
- YAML/JSON 示例必须与规范一致，标注其为规范示例、伪代码或真实实现证据。
- 示例中不允许重复 YAML key、虚构字段或与实际协议不一致的路径。

## 7. 需求—设计—实现—验收追踪

每项核心机制至少能追溯到：

总体架构目标 → 设计说明书/规范 → 实现仓库和接口 → 可运行 Example → Acceptance。

追踪矩阵只记录必要的 ID、链接、状态和证据，不引入复杂需求管理平台。实现证据必须记录仓库、Commit/PR、测试命令、实际结果和覆盖范围。

## 8. 跨仓权威规则

- ca-agent-next 是 Agent 架构、Plugin/Runtime 公共机制和本仓规范的权威源。
- ca-skill-compiler 是 CA-SL 编译、链接、Artifact 构建与发布契约的权威源。
- ca-skills 是 Skill 作者源和 CA-SL 规范发布入口。
- ca-client-tools 是 Tool Interface Package、Callable 定义和 Owner 交互契约的权威源。
- ca-openamsm-plugin 是 OpenAMSM SBI Event ingress/Delivery 的实现与协议映射权威源。
- ca-agent-demo 是既有 Python 代码与测试证据来源，不是 Next 的最终架构权威。
- 其他仓库只维护本仓实现、集成、操作和验收材料，并引用本仓相应规范与基线 Commit。
- ca-docs 的公开文档清单不属于 Agent Runtime 公共契约。

## 9. 变更与废弃

架构边界变化更新唯一架构设计和索引；机制行为变化更新设计说明书；字段/接口变化更新规范并检查消费者；实现变化更新实现仓证据和验收结果。被替代文档先迁移有效内容，再标记废弃或归档，不直接删除唯一证据。

每轮文档变更都更新总索引、文档状态、权威依据和交叉链接。

## 10. Demo DFX 边界

可靠性与安全暂按 Demo 场景描述，不写生产级 HA/DR、SLA、签名、Trust Registry、生产密钥体系和复杂多租户方案。基本输入校验、路径边界、错误可诊断、fail-closed、状态语义正确、最小日志和自动化测试仍是功能要求。
