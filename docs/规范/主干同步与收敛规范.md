# 主干同步与收敛规范

> 文档类型：仓库治理规范  
> 文档版本：0.1.0  
> 状态：DRAFT / 待独立评审  
> 关联 Issue：[ #50 主干同步政策与收敛审计](https://github.com/odango-chan/ca-agent-next/issues/50)  
> 上位治理：[Issue #5](https://github.com/odango-chan/ca-agent-next/issues/5)、[Issue #12](https://github.com/odango-chan/ca-agent-next/issues/12)

## 1. 目的与适用范围

本规范补充《文档编写与治理规范》中的分支命名与生命周期要求，专门约束 ca-agent-next 的 mainline synchronization、集成分支和 Stacked PR。

本规范只定义治理门槛，不代表任何 PR 已获批准，也不授权直接推送 main、合并 PR、发布 Release、强推、rebase 或删除现有分支。

## 2. 唯一正式集成基线

1. main 是仓库唯一正式、默认、可供新工作引用的集成基线。
2. 任何长期工作分支、恢复分支、评审分支或集成分支都不是第二个 main；其内容只有经过 PR 合并后才进入正式基线。
3. 临时集成分支必须有明确 Issue、用途、基线 SHA、负责范围、退出条件和目标 PR。不得无限期以集成分支替代 main。
4. SR 的 IMPLEMENTED / VERIFIED 状态必须按实际集成目标和验收证据记录。合入临时集成分支不等于合入 main；合并 PR 本身也不自动等于 VERIFIED。

## 3. 同步触发条件

出现以下任一情况时，应建立或刷新主干收敛计划：

- 一个功能批次的设计、实施或验收已经形成可独立评审的闭合单元；
- 某个分支已成为其他多个分支的共同依赖；
- 长期分支开始累积多个功能、多个 SR 或跨模块文档，导致变更边界难以辨认；
- main 与实际工作基线出现明显偏离，继续从旧 main 创建分支会重复劳动或产生冲突；
- 新的并行任务需要依赖尚未合入 main 的成果；
- 用户要求进行主干同步、版本集成或分支清理。

同步按功能闭合和依赖拓扑推进，不要求等待所有 SR、所有 Feature 或整个项目全部完成。独立且满足门禁的功能可以先合并；未闭合的消费者继续留在分支。

## 4. 收敛分类

每次审计必须对所有相关分支和 PR 分类：

| 分类 | 含义 | 处理 |
|---|---|---|
| A | 依赖闭合、评审和必需验收齐备，可进入 main | 可排入当前合并批次 |
| B | 有明确的前置 PR 或分支依赖 | 按依赖拓扑自底向上处理 |
| C | 正在实施、评审、补证或仍有未决设计 | 保留分支，不进入当前合并批次 |
| D | 已被替代、重复、已集成或不再适用 | 不直接合并；保留审计记录，确认无后继依赖后再归档 |

分类针对当前审计快照，不是永久状态。每次合并、推送、PR 更新、Review 或 CI 变化后，必须重新检查受影响项。

## 5. PR 合并门槛

进入 main 的每个 PR 必须同时满足：

1. **追踪完整**：PR 引用本仓 Issue；如涉及 SR，列出全部 SR、Feature、Acceptance 和中央追踪 Issue。
2. **基线明确**：记录 base branch、base SHA、head branch、完整 head SHA；说明是否为 Stacked PR，以及直接前置 PR。
3. **差异可审**：PR 处于非 Draft 状态；当前 base/head 关系正确；无未解释冲突；评审者看到的 Files changed 与本次目标一致。
4. **设计门禁通过**：涉及设计或规范时，必须绑定精确 SHA 的独立评审结论。REVIEW_REQUESTED、作者自审、Review Context CI 成功均不等于独立批准。
5. **独立性如实记录**：评审模型/版本和任务角色必须与作者模型区分，评审报告绑定完整 Head/Base SHA。若 GitHub 因作者账号限制不能提交 APPROVE，可提交 COMMENT 保存独立模型结论；必须明确 GitHub 状态仍是 COMMENTED，不得伪称 APPROVED。
6. **CI 与验收真实**：当前 head 上所有必需 CI 通过；真实测试、Harness、模块 AC、系统 EX 分开记录。Review Context 或文档静态检查不能替代产品测试。
7. **依赖闭合**：直接依赖已合入目标基线，或已在下层 Stacked PR 中声明并按顺序处理。不得通过合并上层 PR 隐式引入未审查依赖。
8. **状态一致**：SR、Issue、功能树、总索引、实施状态总览和 PR 描述没有互相矛盾的状态或过期 SHA。
9. **合并授权**：合并操作仍需遵守用户对具体 PR 的授权；本规范本身不构成合并授权。

任何一项缺失时，PR 保持 Draft、BLOCKED 或其他真实状态，不得为了推进主干而降低门槛。

## 6. Stacked PR 规则

1. 每层 PR 只承载一个可独立审查的功能或设计增量；PR 正文必须明确前置 PR 和固定 base。
2. 合并顺序严格按依赖拓扑自底向上。下层 PR 未合并时，上层 PR 不得单独进入 main。
3. 下层 PR 合并后，上层 PR 必须重新指向最新目标基线，并核对新的 base SHA、head SHA、三点差异、文件范围和依赖。
4. 更新 base 或 head 后，旧 Review/CI 不能自动沿用。对变化的文件和受影响的 AC 执行增量复评，并在新 SHA 上重新运行必需检查。
5. 如果上层分支基于旧 base SHA，或 GitHub 显示 mergeable=false，先查明原因；不得把旧 base 当作已验证的当前基线。
6. 不得未经授权强推、重写或覆盖仍被其他分支依赖的提交。优先通过新提交、显式 merge 或新分支保留历史。

## 7. 大型恢复分支与批次集成

大型恢复分支不因提交数量多而自动拒绝，但不得仅凭“分支已存在很久”或“所有提交都在同一分支”直接整体合入 main。

当集成分支包含大量提交或跨多个功能时，主干 PR 必须提供：

- 逐功能/逐 SR 的变更矩阵；
- 已合并到该集成分支的 PR、对应 Issue 和精确 merge commit；
- 尚未经过独立评审的 residual diff；
- 与 main 的精确比较基线、文件统计和冲突状态；
- 代码、文档、Schema、CI、测试及证据各自的验收状态；
- 本批明确不合入的分支、文件和 SR。

优先按依赖闭合的功能批次形成多个 PR。若客观上只能形成一个大型集成 PR，则必须证明其所有子变更已有可追溯的评审/验收，且剩余差异作为一个完整范围接受独立评审。不得把历史 PR 已合入临时集成分支误报为已合入 main。

## 8. 分支创建、保留与归档

1. 新工作分支原则上从最新 main 创建。
2. 如果任务必须依赖未合入成果，允许从对应下层 PR 分支创建，但必须明确声明 Stacked PR、上层依赖和最终回归 main 的计划。
3. 临时集成分支必须绑定 Issue，并记录开始 SHA、当前 SHA、纳入的 PR 和退出条件。
4. PR 合并后，只有在所有下游分支完成迁移、无未提交工作、审计记录已归档时，才可删除或归档原分支。
5. 被替代、重复或长期未更新的分支先标记 D 并检查是否仍被依赖；不得仅凭分支名或日期直接删除。
6. 任何分支归档/删除都不得抹除提交、PR、Review 或验收证据。

## 9. main 保护要求

正式执行主干同步前，main 应启用适当的 GitHub Branch Protection / Ruleset，至少要求：

- 通过 PR 更新 main，禁止直接推送；
- 禁止 force push 和删除 main；
- 要求适用的 CI / status checks；
- 要求独立评审，或使用已登记的模型级独立评审记录与 GitHub Review 事件组合满足治理要求；
- 管理员也不得无记录绕过规则。

如果平台配置暂时不能满足上述要求，必须在主干收敛计划中标记为治理风险，并由用户明确决定是否允许一次性例外；不得默认为已保护。

## 10. 停止与恢复条件

出现以下任一情况，停止当前批次及其受影响的后继 PR：

- main、base 或 head SHA 与审计快照不一致；
- 分支在审计期间被其他任务推进，或发生未解释的分叉；
- PR 出现冲突、mergeable=false 或 Files changed 意外扩大；
- 必需 Review、CI、模块 AC 或直接依赖缺失；
- 设计、SR 状态、功能树、文档索引或验收证据相互矛盾；
- 出现未登记的文件覆盖、删除、强推或权限变化。

恢复时重新读取远端状态，建立新的审计快照，说明差异和影响，再继续。保留已通过的独立证据，不得将旧 SHA 的通过结果外推到新 SHA。

## 11. 每次收敛必须归档的记录

《主干收敛计划》至少包含：审计日期、仓库、main SHA、所有纳入分支的完整 SHA、分支保护状态、开放/已合并/已关闭 PR、Issue/SR 关系、Review/CI 状态、依赖图、A/B/C/D 分类、合并顺序、未合入范围、停止条件和最终 main merge SHA。

合并后必须刷新功能树、SR 总索引、实施状态总览、文档目录、跨仓审计和相关版本/修订记录。main 的最终 SHA 与各 PR merge commit 必须回填到对应 Issue、PR 和 SR。

## 12. 本规范当前状态

本文件 0.1.0 是待评审草案。Issue #50 完成文档与审计不等于本规范已经正式生效，也不等于任何 PR 已获准合并。首次正式执行前，必须由独立评审确认本规范，并按最新远端状态刷新收敛计划。
