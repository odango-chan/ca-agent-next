## 0. 实施前检查

开始任何阶段前：

1. 读取 README.md、Agent.md、总体架构、对应设计说明书、规范、Demo 验收基线。
2. 核对当前分支、工作区状态、HEAD、PR 状态和依赖版本。
3. Agent Core、Host、Agent Model Loop、Skill Importer、Resolver、Runtime 固定使用 Python。
4. ca-agent-demo 只作为只读代码/测试证据来源，逐文件选择性复用。
5. 跨仓改动须有本仓登记的 READY SR，执行范围以目标仓和验收条件为准。
6. OpenAMSM 集成必须在 Echo 通过后开始。
7. Next 只消费外部发布的 Skill Artifact，不调用 Compiler，不做 Skill Admission。
8. 外部 Agent 评审必须遵守 Agent.md review_scope 和文档编写与治理规范；SR-001 自动生成机制完成前，手动提供范围区块和公共评审提示词。

## 1. Phase A — Python Core 基础骨架

- 建立 Python 包结构、Host 入口、Agent Model Loop、基础 Context 和 Run 类型。
- 明确 Host、Resolver、Runtime、Plugin Manager 的模块边界。
- 复用 ca-agent-demo 的 Python 代码前先核对依赖、测试和业务耦合。
- 不迁移整个 ca-agent-demo，不引入 OpenAMSM 专用逻辑。

退出条件：Python Host 能启动；模块边界和公开入口稳定；基础测试通过。

## 2. Phase B — 唯一 Plugin Manager

- 实现 Plugin Manifest v1alpha1 加载、基础字段/Schema/路径检查。
- 实现 Plugin 进程启动、握手、NDJSON IPC、关联和关闭。
- 支持 event.ingress、event.delivery、tools 三种 Extension。
- 一个 Plugin 进程可以同时导出多种 Extension。
- 将 ca-client-tools provider/v2 适配封装在同一个 Plugin Manager 内，不建立第二 Provider Manager。
- Tool 调用前由 Runtime 做当前 Skill 声明 Callable Scope 检查。

退出条件：同一个 Echo Plugin 进程与测试 Host 通过握手及三类 Extension 的协议测试；业务全链路由 Phase F 验收；错误版本、路径逃逸和关联错误有测试。

## 3. Phase C — 已发布 Skill Artifact 消费

- 实现 SKILL.md-only Skill 导入。
- 实现 published Artifact 导入：必需文件、格式标识、路径、引用、类型数据和 Tool/Capability 依赖检查。
- Agent 不调用 Compiler Check/Build/Inspect/Verify。
- 不实现 Skill Admission、Owner Trust 或生产级授权。
- SKILL.md-only 包独立导入；Assurance 包仅消费 Compiler #61 / SR-013 发布的新 Runtime Artifact API，并由 ca-skills / SR-027 提供正式 Bundle。冻结 Artifact v1alpha5 和 Development Artifact v1alpha1 不作为当前正例。新版包中的 when CheckedExpr 只在导入时反序列化一次；SR-005 负责 Catalog generation 缓存。
- 无效发布 Artifact 必须导入失败，不降级成 SKILL.md-only。

外部依赖：ca-skills v1alpha5 规范 SHA 已固定；Assurance 路径还必须等待 Compiler #61 / SR-013 正式 Runtime Artifact API 与 ca-skills SR-027 正式 Bundle 资产、布局和匹配 Verify 日志。冻结 Artifact v1alpha5 缺少 Request Schema/when 数据，Development v1alpha1 为 NOT_ADMITTED；二者都不是当前正例。若 API/Bundle 契约未就绪，对应 AC-004-03/04 标记 BLOCKED，不得自造格式或临时拼装成功包。

退出条件：AC-004-01～06 全部有真实证据；SKILL.md-only 与正式 published Runtime Artifact 两条路径行为正确；依赖闭包精确解析；Agent 没有 Compiler 子进程或 Compiler 命令依赖。未发布正式 Bundle 前，不得将 Assurance 正例标为 PASS。

## 4. Phase D — SkillCatalog 与 Resolver

- SkillCatalog 由 Python Core/Host 拥有，保存所有已导入 Skill。
- 保存完整 SKILL.md、轻量候选元数据、Artifact 引用、已反序列化 when Program 和类型环境。
- 精确 Continuation 优先。新 Event 固定 generation，对每项声明 requestSchema 的 Skill 先验证输入；失败排除该项。仅对通过校验的有 when 候选求值；无精确匹配时再从合格的无 when 候选语义选择。
- when false/error 的 Skill 排除；多 true 只在精确候选集合内消歧。
- Continuation 先恢复原 Run，不重新选择 Skill。
- 显式导入/更新构建候选 generation，成功后原子切换；失败保留旧 generation。
- references/ 和大型知识资产按需加载。

退出条件：EX-21～EX-29 全部通过；Event 热路径无文件读取、目录扫描和 Compiler 调用。

## 5. Phase E — Runtime Action Boundary

- Deterministic Procedure Engine 和 LLM Model Loop 都输出同一 Runtime Action Request。
- Runtime 校验当前 Skill 的声明 Callable Scope、Callable ID、输入 Schema、Effect、Artifact 引用和 Run 状态。
- Plugin Manager 只负责分发，不做 Skill 选择或 Owner outcome 判断。
- READ Tool 结果保留 Observation 来源；MUTATION 结果按 Owner Receipt/Commit Proof 解释。
- UNKNOWN 保持 UNKNOWN；HTTP 200、IPC 成功和 Delivery 成功不等于 COMMITTED。

退出条件：EX-13～EX-16、EX-19 和对应失败路径测试通过。

## 6. Phase F — Echo 垂直 E2E

- 将 Echo 作为首个可运行 Example。
- 一个 Go Plugin 同时暴露 Event、Delivery 和 Tool。
- 一个 SKILL.md-only Skill 走 LLM-guided。
- 一个含已发布 Assurance Artifact 的 Skill 分别走 Deterministic 和 LLM-guided。
- 覆盖发布 Artifact 导入失败、Skill 选择、Action Scope、Outcome/Evidence 和响应交付。
- 运行 EX-01～EX-19、EX-21～EX-29；EX-20 留给 OpenAMSM 第二业务证明。
- 清理冗余脚手架、重复 Registry 和过渡适配代码。

退出条件：Generic Echo E2E PASS，且不依赖 OpenAMSM 业务代码。

## 7. Phase G — OpenAMSM Plugin 与业务集成

仅在 Echo 通过后启动。

- 对齐 ca-openamsm-plugin 与 Next Plugin Package/IPC v1alpha1。
- Go Event Plugin 负责 SBI HTTP/2、JSON/multipart、Content-ID、原始 N1/N2 和 Delivery。
- 共享 UpdateSMContext 只提取 Skill 选择所需的最小 NAS discriminator；不做完整业务解码，不在 Plugin 里选 Skill。
- ca-client-tools 通过同一个 Plugin Manager tools Extension 接入。
- Codec Tool 只有在 Interface Package 发布且消息子集验收后才能被 Skill 调用。
- 导入已有 Establish、Modify、UE-requested Release Skills 的已发布 Artifact。
- Host 管理 ArtifactStore、Run、continuation、responseObligation 和重试关联。
- 对照 OpenAMSM OpenAPI 冻结 Operation、Event 字段、externalRequestId 和响应映射。

退出条件：OM-01～OM-08、OM-10、OM-13～OM-15 在精确协议 fixture 上通过；不含 Skill 选择、Owner 操作或 Runtime 逻辑的 Event Plugin。

## 8. Phase H — 真实 OpenAMSM Create → Modify → Release

- 使用一个真实隔离 OpenAMSM Owner/SMF 和一个 UE/PSI。
- 经 Next Host 和 Go Plugin 执行 Create、Modify、UE-requested Release。
- 保留原始 N1/N2 字节和 Content-ID，经 Host ArtifactStore 和 Tool invocation 传递。
- 证明 Release continuation 恢复精确原 Run/generation，校验 N1 Release Complete（0xD4）及适用的 N2 Release Response。
- 校验 Owner Receipt/Commit Proof/Reconcile、最终状态、响应状态和零重复 mutation。
- Synthetic Owner 测试与真实隔离 Owner 证据分开报告。

退出条件：OM-11 真实隔离 E2E PASS。不得把 Synthetic G5 或离线 fixture 当作真实 OpenAMSM E2E，不声明 Production Qualification。

## 9. 全阶段禁止项

- 不把 Agent Core 改成 Go。
- 不复制 ca-skill-compiler 或 ca-client-tools 的 Go 实现。
- 不建立独立 Provider Manager、Tool Registry、Codec Manager。
- 不增加 Domain Contract Package、TaskContract Package、第二份 Skill Descriptor 或 supportedModes。
- 不增加 Event→Skill 或 Event→Mode 表。
- 不增加额外 SHA-256、包签名、Trust Registry、分布式缓存、文件监听、自动下载或通用热更新。
- 不在 Next 调用 Compiler，不建立 Skill Admission。
- 不在每个 Event 读取 Skill 文件、解析 CEL 或启动 Compiler。
- 不编译单个 LLM Action，不允许 LLM 直接调用 Plugin 或声明 Owner Commit。
- 不在 Echo 通过前开始 OpenAMSM 集成。
- 未真实执行的测试不得标记 PASS。
