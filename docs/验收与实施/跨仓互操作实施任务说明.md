## 1. 固定本次评审输入

从同一设计提交读取[总体架构 §15](../架构设计/CA%20Agent%20Next%20架构设计.md)、[CA-SL 1.6.0 中央语言设计](../规范/CA-SL%201.6.0完整语言规范.md)、[SR-029](../SR/SR-029-Capability-first-Skill作者接口与Callable一对一绑定.md)和本批目标 SR。登记完整设计 SHA、目标仓与功能、设计 Issue、拟核查的 AC 和外部输入出处。历史 v1alpha5 与 Compiler v2.1.0 只用于溯源和旧输入拒绝测试。1.6.0 的机器标识、DTO、Schema、路径和 Golden 以各生产者冻结的版本为准。

## 3. 模块命令与证据

命令从各自 SR 的固定版本读取。SR-013 §3～§8 给出 Go/Python、Go Native、WASM 和 Chromium 的环境与命令；SR-004 §5.2、SR-005/006 §5.1 定义 Next 的模块测试，在各自仓根执行。逐条记录测试向量、受测 SHA、工具版本、发现数、退出码、期望、实测和日志位置。零发现、未运行或仅检查源代码，均不能填 PASS。生产方的 Release、Next 的模块 AC、系统 EX 分别取证。

## 4. 何时能交给 DeepSeek Harness

评审时逐项标明可独立核查的 AC、直接消费的契约及缺项的责任方。例如，新 Compiler Release 是 SR-013 的输出，也是 SR-027 的输入；SR-004 的正式 Assurance 正例消费 SR-027 的发布资产。SKILL.md-only 不消费这些资产。顺序相邻的阶段不会自动形成实施前置。

实施批次须符合[SR 管理规范 §9](../规范/SR%20管理规范.md#9-deepseek-harness-goal-与交付门禁)和[文档交付门禁](../规范/文档编写与治理规范.md#13-执行提示词交付门禁)。固定获批设计 SHA、阶段 READY 记录、目标仓实施 Issue/分支、直接依赖、逐 AC 命令和预期后，才生成 Goal。Flash 使用 low；记录请求模型与返回标识。每批完成后立即 Commit、Push，核对远端 ref SHA 与受测提交。缺少契约则暂停消费它的 AC，记录 BLOCKED、Owner、所缺资产和恢复步骤；未运行项记 NOT_RUN。合并和发布使用各自的授权。
